## F3a (коммит 2): кернел `BoidNeighborForceSorted` и переключатель `-m3d_walk`

### Зачем

В профиле B расходятся 85% инструкций, частичных чтений 96%: соседние потоки обходят случайные ячейки (поток идёт по исходному индексу частицы). Новый кернел ставит поток на **слот отсортированного массива**, тогда соседние потоки делят ячейки.

### Что нужно сохранить буквально (иначе стаи изменятся без объявления)

1. **Порядок посещения и семантика капа.** Ячейки по порядку `k = (start + n) % 9`, `start = i % 9`, где `i` **исходный индекс частицы** (`SortedIndices[slot]`), не слот; внутри ячейки слоты по возрастанию; шаг `dy = k / 3 - 1`, `dx = k % 3 - 1`; пропуск `r2 < 1e-6`; проверка капа `visited >= MaxNeighbors` **до** инкремента и до проверки радиуса; `break` выходит из обхода (`capped`). `CountCapHits` считается так же.
2. Множитель `inter`, радиусы по командам, `min(team, 7)`, итоговые суммы и нормализация без изменений. Запись `velocity[i] += float3(force.x, 0, force.y)` (по исходному индексу `i`).
3. Поведение `HashWrap = 0`: выход за границу пропускается (`continue`) без изменения порядка остальных ячеек.

### Что меняется

1. **Поток на слот.** `slot0 = id.x`; `i = SortedIndices[slot0]`; своя позиция и команда из `SortedPositions[slot0]`, `SortedTeams[slot0]` (то же значение, что `position[i].xz` и `teamId[i]`, потому что снимок строится в том же кадре перед силой).
2. **Объединение подряд идущих диапазонов.** Идти по ячейкам в том же порядке, держать накопленный диапазон `[rs, re)`; следующую ячейку присоединять к нему **только если** `CellStarts[next] == re` **и** вектор сдвига тора у неё такой же; иначе закрыть диапазон и начать новый. Конкатенация диапазонов даёт ровно ту же последовательность слотов, что обход девяти ячеек по отдельности. Условие про одинаковый сдвиг обязательно: слоты могут идти подряд и у ячеек из разных мест тора (если между ними пустые), а сдвиги у них разные.
3. **Сдвиг тора на ячейку вместо `MinImage` на кандидата.** Для ячейки с «сырыми» координатами `raw = cell + (dx, dy)` и `wrapped = ((raw % res) + res) % res` сдвиг по оси `(raw - wrapped) * размер_ячейки` (при `raw.x = -1` сдвиг `-S`, при `raw.x = res.x` сдвиг `+S`; формула верна при `res ≥ 3`, как требует валидатор). Тогда `d = SortedPositions[slot] - self + сдвиг`. Целочисленные `%` и деления по выбору ячейки заменить условным прибавлением и вычитанием размера сетки. При `HashWrap = 0` сдвиг ноль.
4. **Переключатель `-m3d_walk <0|1|2>`** (по образцу `-m3d_maxn`). В `BoidNeighborForcePass`: сериализуемое поле `walkMode` (0 = прежний кернел, 1 = `BoidNeighborForceSorted`, 2 = то же плюс упакованная запись, часть F3b), по умолчанию **0**. Режим можно менять **во время работы без пересоздания мира** (харнесс применяет его, когда мир найден, как `maxn`). Диспатч одной размерности. Прежний кернел и его поведение не меняются.
5. **Харнесс и скрипты.** `PerfArgs` + тесты парсера; поле `walk` в `args` строки `M3D_PERF_INFO` и в строку `M3D_PERF` (в конец списка полей, прежний порядок не менять); `summarize.ps1` группирует по `walk`; **`run-series.ps1` принимает токены `<режим><walk>`**, например `-Series "A0 A1 A0 A1 B0 B1 B0 B1"` (токен без цифры означает «walk не задан, значение ассета»); в `summary.md` колонка `walk`. Каждый токен это отдельный запуск приложения, как сейчас.

### Тесты (новый файл, например `BoidNeighborForceSortedTests.cs`)

Допуск как в существующем оракуле: `1e-4 + 1e-4 · |ожидаемое|` по компонентам силы. Каждый сценарий сравнивает **GPU `walk 1` с GPU `walk 0` на одном и том же снимке** и, где есть готовый CPU-оракул из `BoidNeighborForceTests.cs`, с ним:
1. Две команды (как `Oracle_TwoTeams_MatchesGpu`).
2. Кап выключен и включён; **плотный случай, где кап срабатывает** (как `CapDense...`); доля капа совпадает с `walk 0`.
3. Шов тора (`Seam_Wrap...`) и сетка без тора (`NoWrap...`).
4. `TeamId > 7`.
5. Число частиц не кратно 64; все частицы в одной ячейке; пустые ячейки между занятыми.
6. **Случайная проверка:** не менее 30 зёрен, `N` от 500 до 3000, тор и без, кап 0 / 16 / 48, сравнение `walk 0` и `walk 1`. Она ловит ошибки объединения диапазонов и сдвига на шве.
7. Переключение `walk` во время работы (0 → 1 → 0) без исключений и без изменения результата `walk 0`.
Существующие тесты проходят без правок. Тесты оракула и тесты пресетов остаются зелёными.

## F3b (коммит 3): упакованная запись соседа (`walk 2`)

1. В `HashScatter` дополнительно писать запись 16 байт на слот в буфер `SortedPacked` (`uint4`): `pos.x`, `pos.z`, `dir.x`, `dir.y` как биты `float`, а **команда (3 бита, значение `min(team, 7)`) кладётся в три младших бита `dir.x`**, восстановление `asfloat(bits & ~7u)` и `bits & 7u`. Ошибка `dir.x` около 1e-6, допуск 1e-4 соблюдается с запасом. **Не использовать snorm16**: ошибка 1,5e-5 на компоненту накапливается в сумме направлений и при малой по модулю сумме может выйти за допуск. Запись включается только флагом, который выставляет `walkMode == 2` (`ISpatialHashConsumer`/`SpatialHashSet`, `walk 0` и `walk 1` не платят за пакет). Старые буферы (`SortedPositions`, `SortedDirections`, `SortedTeams`, `SortedIndices`) пишутся как раньше; `SortedIndices` остаётся отдельным `uint`.
2. Кернел `BoidNeighborForceSorted` в режиме 2 читает **одну** запись 16 байт на кандидата (вместо позиции отдельно и команды/направления по условию). Логика, порядок и допуск те же.
3. Те же тесты с `walk 2`, плюс проверка, что восстановление команды из трёх бит верно для `team = 0..7` и для `team > 7` (даёт 7).
4. Гейт F3b: как F3a; EditMode зелёный; `walk 0` и `walk 1` не изменились (побитово/в допуске).
