Формулы взять из текущего `frag` дословно (включая `min(teamId, teamCount-1)`, строку `(t+0.5)/max(teamCount,1)` и ветку без команд).

Только под `#if UNITY_EDITOR`, не чаще раза в 8 кадров: считать сигнатуру градиентов (режим градиента, ключи цвета и альфы с временами, по каждой из ≤8 команд, с учётом отката на градиент эффекта и на `DefaultFireGradient`). ## A4. Палитры двух стай: разрыв `HeadingToValue` и схождение к белому

**Зачем.** `HeadingToValue` пишет `value = atan2(h.z, h.x) / 2π + 0.5`. Разрыв стоит на курсе −x: `value` прыгает между 0 и 1. Лёд стартует ровно на −x, знак микро-компоненты Z переключает цвет между концами градиента. Огонь на том же разрыве раскалывается на чёрный и бледно-жёлтый. Верхние концы огня (1, 0.95, 0.55) и льда (0.75, 0.95, 1) почти белые, команды там различаются плохо. Это вывод из кода, на скриншотах не проверен: **в начале фазы** запросить у владельца подтверждение, видно ли крап в ледяной стае, и записать ответ в ADR-043.

**Ограничения.** `HeadingToValue`, `DefaultFireGradient()` и ассет/сцену `Boids_hash` не менять (ADR-041 §4: вид одной стаи остаётся). Правим только создатель пресета двух стай.

**Сделать.**
1. В `M3DDemoTools.CreateBoidsHashTwoTeamsAsset` заменить градиенты команд на **циклические** (цвет в `t = 0` равен цвету в `t = 1`), локальными методами создателя (как сейчас `IceGradient()`).
2. Требования к градиентам:
   - цвет на концах совпадает (допуск `ChannelTolerance`);
   - ни одной точки чёрного или близкого к нему (минимальная яркость выше порога, выбрать и записать порог; частица должна быть видна на тёмном фоне камеры);
   - ни одной точки близкой к белому (сумма каналов < 2,7);
   - у команд разные семейства оттенков по всему диапазону (огонь тёплый, лёд холодный).
3. Каждая стая самая яркая на своём стартовом курсе. Огонь стартует на +x (`value` 0,5), лёд на −x (`value` 0/1). Поэтому у огня пик яркости в середине, у льда на концах (и тёмная впадина в середине).
4. Предложение по ключам (допустимо подобрать иначе, оставаясь в требованиях):
   - Огонь: 0 `(0.55, 0.08, 0.00)`, 0.5 `(1.00, 0.70, 0.10)`, 1 `(0.55, 0.08, 0.00)`, промежуточные ключи по 0.25 и 0.75 `(0.85, 0.30, 0.00)`.
   - Лёд: 0 и 1 `(0.45, 0.85, 1.00)`, 0.5 `(0.05, 0.15, 0.55)`, промежуточные по 0.25 и 0.75 `(0.15, 0.50, 0.95)`.
5. `particleGradient` эффекта (запасной) оставить как есть.
6. Тесты: в `BoidsHashTwoTeamsPresetTests` обновить проверки цветов команд; добавить тест свойств градиентов (концы совпадают, минимальная яркость, максимум суммы каналов, разный оттенок). Эти правки относятся к тесту самого пресета, поэтому допустимы.
7. Пересоздать ассет через меню `Create Boids Hash 2 Teams Effect`. В коммит только `Boids_hash_2teams.asset` (+meta). Сцену `Boids_Hash_2Teams.unity` коммитить, только если она реально изменилась. Показать `git diff --stat` по ней.
8. Play: скриншот на 3,7 с и 5 с. Ледяная стая без крапа, команды различимы.
9. В `Techdebt.md`: «Boids_hash и `HeadingToValue` оставлены с разрывом на −x» (известное ограничение одной стаи).

## B2. ADR-044: стабильный симметричный отбор соседей (кернел и пасс, пресеты не меняются)

**Зачем.** Сейчас кап считает **посещённых** соседей и обрывает обход в порядке ячеек, а не по расстоянию. При доле капа ~98% сила считается по случайному куску соседей, и чужие частицы, от которых зависит расхождение стай, часто не попадают в выборку. Отбор «i видит j» и «j видит i» не согласован. Предложение из `plan-Reynolds-Boids-v2.md` §5: включать пару по симметричному хэшу.

**Результаты модели** (4 зерна по 3 прогона, 3000 частиц, dt 1/60, ×4; «контакт» = доля частиц с чужой в радиусе 3 м на 5 с):

| Вариант | контакт на 5 с | стай на 15 с |
|---|---|---|
| текущий (кап 48 по посещённым) | 65% | 8,7 |
| симметричный стабильный ключ, кап 48 | 12% | 4,7 |
| без капа | 8,5% | 4,3 |

Это CPU-модель с перемешанным порядком слотов, не GPU. Ориентир, не гарантия.

**Сделать.**
1. **Режим на пассе.** В `BoidNeighborForcePass` добавить перечисление `NeighborSelection { VisitedCap = 0, StableSymmetric = 1 }` и сериализуемое поле, **по умолчанию `VisitedCap`**. Существующие ассеты (в том числе `Boids_hash`) без поля десериализуются в `VisitedCap`, их поведение не меняется. Передавать в кернел как `uint NeighborMode` через существующий механизм `PushParams`.
2. **Кернел `BoidNeighborForce`** (`BoidsPasses.compute`). Режим 0: код **без изменений**. Режим 1:
   - привязать `SortedIndices` (отсортированный `sortedIndex` из `SpatialHashSet`; найти реальное имя и способ привязки, как для `SortedPositions`);
   - до цикла посчитать `n9` = сумма `CellCounts` по 9 ячейкам (с тем же заворотом по модулю, что и в обходе; при `res >= 3` дубликатов нет);
   - `subsample = MaxNeighbors > 0 && n9 > MaxNeighbors`; `keep = subsample ? MaxNeighbors / n9 : 1`;
   - обходить **все** 9 ячеек без раннего `break`; порядок вращения по `id % 9` можно сохранить, он здесь ни на что не влияет;
   - в цикле после проверки `r2 < 1e-6`: `other = SortedIndices[slot]`; если `subsample` и `PairHash01(min(id, other), max(id, other)) >= keep`, перейти к следующему кандидату;
   - остальная математика (separation, alignment, cohesion, `inter`, итог силы) **без изменений**;
   - `capped` в режиме 1 означает `subsample` (для `CountCapHits`); смысл `LastCapHitFraction` для режима 1: доля частиц с `n9 > MaxNeighbors`.
3. **Хэш пары** (одинаков в HLSL и в C#-эталоне, uint с переполнением):
   ```hlsl
   float PairHash01(uint a, uint b)
   {
       uint h = (a * 73856093u) ^ (b * 19349663u);
       h ^= h >> 13;
       h *= 0x5bd1e995u;
       h ^= h >> 15;
       return (h & 0xFFFFFFu) * (1.0 / 16777216.0);
   }
   ```
   Порог зависит от `n9` частицы `i`, поэтому полная симметрия точна только при равных `n9` у обеих сторон. Это приближение записать в ADR-044.
4. **Валидатор.** Новых ошибок нет. `MaxNeighbors == 0` в режиме 1 допустим (без отбора, поведение как без капа). Предупреждение или ошибку не добавлять.
5. **Цена** (записать в ADR-044 как известный риск, без утверждений о цифрах): режим 1 обходит все кандидаты (`n9`, на плотных стаях порядка сотен), а не первые `MaxNeighbors`. Цена растёт с плотностью, не с `N`. По умолчанию режим не включается. Замер на S10 (P7) обязателен до того, как режим станет умолчанием.
6. **Тесты** (новый файл `BoidNeighborForceStableSelectionTests.cs`; существующие тесты 5a/5b не править):
   - режим 0 даёт то же, что и раньше (опора на существующие тесты, плюс проверка десериализации `Boids_hash` в `VisitedCap`);
   - режим 1 при `n9 <= MaxNeighbors` совпадает с режимом 0 и с CPU O(N²) эталоном без капа;
   - режим 1 при `n9 > MaxNeighbors`: GPU-сила совпадает с CPU-эталоном, реализующим тот же хэш (допуск как у существующих тестов силы, порядок суммирования недетерминирован);
   - два прогона с одними входами дают силу в пределах допуска (стабильность, независимость от порядка слотов);
   - свойство `PairHash01(a, b)` через `min/max` не зависит от порядка аргументов;
   - команды: чужая частица попадает в отбор с той же вероятностью, что и своя (тест на статистике по большому числу пар, допуск широкий);
   - через шов тора (`wrap = true`) отбор работает так же.
7. Docs: `pass-catalog.md` (новое поле пасса), `capabilities.md`, `status.md`, `Techdebt.md`.

**Файлы:** `BoidsPasses.compute`, `BoidNeighborForcePass.cs` (имя файла уточнить), при необходимости `SpatialHash.hlsl` (только добавление `PairHash01`, если удобнее держать там), новый тестовый файл, `ADR-044-Stable-Symmetric-Neighbor-Selection.md`, docs.

# Приложение A. CPU-модель (референс для приёмки)

Файл `boids_model.cpp` (положить в `DOC/MEASURE/p6-cpu-model/boids_model.cpp`, это не часть сборки Unity). Порт формул `BoidNeighborForce`, `TeamHeadingSteer`, `Integrate`, `BoxBounds Wrap` и спавна дисков. Порядок слотов в ячейке перемешивается каждый кадр.

Сборка и запуск:

```
g++ -O2 -o boids_model boids_model.cpp
./boids_model <dt> <mult> <cap> <seed> <T> <perTeam> <discR> <mode>
./boids_model 0.016667 4 48 1 15 1500 12 0     # текущий пресет
./boids_model 0.016667 4 48 1 15 1500 12 3     # стабильный симметричный ключ
```

`mode`: 0 кап по посещённым (текущее), 1 кап по принятым соседям, 2 своя ячейка первой, 3 симметричный стабильный ключ. `cap = 0` значит без капа. Вывод: время, расстояние между центрами стай, доля контакта, доля чужих среди соседей, доля капа, число стай. Колонки центров (`fireCx`, `iceCx`) выводятся с сдвигом +45 по X, для отчётов их не использовать.

Ограничения модели:
- не GPU: порядок атомиков и точное время кадра не воспроизводятся;
- `dt` фиксирован, в Unity он переменный;
- зерно спавна не совпадает с `System.Random` в `SwarmSource`;
- результаты усреднены по 3–4 зёрнам.
