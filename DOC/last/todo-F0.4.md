## ТЗ для Grok — F0.4 (точечные дефекты и гигиена сьюта)

### Контекст

Тикет без ADR: набор независимых точечных фиксов, каждый со своим обоснованием. Ничего архитектурного, порядок между пунктами свободный. Единственное, что связывает — все они должны быть закрыты до фазы F1, потому что F1 опирается на тесты как на механизм DoD.

Пункт 1 приоритетнее остальных: пока в сьюте четыре красных, утверждение «тесты прошли» не является проверяемым, и следующая регрессия останется незамеченной.

### 1. Четыре красных теста — guard с предупреждением в `VfxParticleBinder`

Диагноз установлен, гипотеза про выключенные пассы **неверна** и снята: все четыре падают одинаково, включая `Build_AllP2GPassesEnabled_Succeeds`, а `AutoRegisterAttributes` не смотрит на `Enabled` и регистрирует `Position` безусловно (`SimulationWorld.cs` ~580–583). Буфер существует.

Настоящая причина: тест создаёт голый `VisualEffect` без графа. При `particles.Count > 0` (Cube, res=4) `VfxParticleBinder.Initialize` безусловно зовёт `SetGraphicsBuffer("PositionBuffer", …)`, Unity пишет `Value of name 'PositionBuffer' was not found` уровня Error, и `LogAssert.NoUnexpectedReceived` валит тест. Ожидание теста «disabled P2G не бросает» при этом остаётся валидным — падает не то, что тест проверяет.

Фикс — guard в `VfxParticleBinder`: не вызывать `SetGraphicsBuffer`, если свойства нет. Прецедент на `Has*`-семейство в коде рядом: `visualEffect.HasFloat("SpawnCount")` (`SimulationWorld.cs:530`); проверить наличие `HasGraphicsBuffer` в Unity 6 и отчитаться, каким методом сделано.

**Guard обязан быть с предупреждением, не молча.** Мир с частицами и VFX-ассетом без `PositionBuffer` — это настоящая ошибка конфигурации; голый guard заменит один молчаливый отказ другим, и эффект просто ничего не отрисует, не сказав почему. Поэтому `Debug.LogWarning` с именем свойства и ассета, а в тесте — явный `LogAssert.Expect(LogType.Warning, …)`. Тогда диагностика специфицирована тестом, а не терпится им.

`NoUnexpectedReceived` на warning реагировать не должен — проверить и отчитаться; если реагирует, `Expect` тем более обязателен.

Инициализировать выключенные пассы не нужно, **ADR-015 §4 не пересматривается**.

DoD: сьют зелёный целиком, ноль красных.

### 2. NaN в `HeadingSteer`

`DynamicsPasses.compute:96`:

```hlsl
h = normalize(lerp(h, desired, k));
h.y = 0.0;
float flat = length(h);
if (flat < 1e-6) { h = float3(1, 0, 0); } else { h = h / flat; }
```

Дефект: при `h ≈ −desired` и `k ≈ 0.5` аргумент `lerp` обращается в нуль, `normalize(0)` даёт `0/0 = NaN`. Существующий guard на строке 99 его **не ловит**: `length(NaN)` есть `NaN`, сравнение `NaN < 1e-6` ложно, поэтому берётся ветка `else` и `NaN/NaN` уходит в `heading` и `velocity`. Дальше NaN живёт в буфере вечно — это разворот на 180°, для боидов совершенно штатная ситуация.

Фикс — проверять длину **до** нормализации и использовать инвертированное сравнение, при котором NaN попадает в безопасную ветку:

```hlsl
float3 blended = lerp(h, desired, k);
float blendedLen = length(blended);
h = !(blendedLen > 1e-6) ? desired : blended / blendedLen;
```

Второй guard (после `h.y = 0.0`) нужен и остаётся — вертикальный heading при уплощении даёт нуль, — но его сравнение тоже перевести в форму `!(flat > 1e-6)`.

**Перевести на `!(len > eps)` все проверки длины в этом кернеле, включая `forceLen` и `hLen` на строках 82–88.** Иначе фикс закрывает только вход: если в `heading` уже лежит NaN с предыдущих кадров, `hLen < 1e-6` снова ложно, управление уходит в `h = h / hLen`, и буфер не самоочищается. Разница между «не порождать NaN» и «восстанавливаться из заражённого состояния» здесь существенна, потому что буфер живёт между кадрами.

DoD: тест на харнесе не нужен, это particle-пасс. Достаточно юнит-проверки формы или прогона пресета `Boids_mk1` с явным заданием `heading = −desired` и `TurnSpeed·dt = 0.5`; отчитаться, что NaN не появляется. Если проверка требует particle-readback, которого в харнесе нет, — сказать это, а не изобретать его в этом тикете.

### 3. NaN в `BoxBounds` (wrap)

`DynamicsPasses.compute:194`:

```hlsl
float3 size = BoundsExtents * 2.0;
float3 local = p - minCorner;
local -= size * floor(local / size);
```

При нулевой компоненте `BoundsExtents` получается `0/0 = NaN` в позиции. Для 2D-эффекта на плоскости `extents.y = 0` — естественная настройка, то есть это не теоретический случай.

Фикс — покомпонентный select, оставляющий оси нулевой протяжённости нетронутыми (частица сохраняет свою координату в плоскости):

```hlsl
float3 wrapped = local - size * floor(local / size);
local = (size > 1e-6) ? wrapped : local;
```

`max(size, eps)` не подходит: это завернуло бы частицу в бесконечно тонкую ячейку.

DoD: `extents.y = 0` в `BoxBoundsPass` с режимом Wrap не порождает NaN.

Рядом, **в скоуп не брать**: режим Bounce при `extents.y = 0` всё равно зажмёт `p.y` в `BoundsCenter.y`, потому что цикл по осям получает `minCorner == maxCorner`. Для 2D-эффекта на плоскости это чаще всего безвредно. Одна строка в отчёт и в `Techdebt.md` — чтобы F1 не принял фикс wrap-режима за полное решение.

### 4. `RenderTexture.active` при освобождении поля

`FieldSet.cs:86–90`:

```csharp
private static void ClearOne(CommandBuffer cmd, RenderTexture rt, Color clear)
{
    cmd.SetRenderTarget(rt);
    cmd.ClearRenderTarget(false, true, clear);
}
```

Render target не восстанавливается, отсюда предупреждение `Releasing render texture that is set to be RenderTexture.active!` (Techdebt A1). Сообщение возникает в момент `Release()`, поэтому минимальный и точный фикс — снять активность перед освобождением, в `FieldSet.Release`:

```csharp
if (RenderTexture.active == rt) { RenderTexture.active = null; }
```

Если предупреждение останется — диагностировать, откуда именно приходит активная ссылка (порядок `Teardown`, или состояние после `Graphics.ExecuteCommandBuffer`), и отчитаться.

**Вне скоупа:** замена `SetRenderTarget`+`ClearRenderTarget` на compute-очистку. Она правильнее по духу фреймворка и сняла бы связь с render-target состоянием целиком, но требует дать `FieldSet` доступ к библиотеке кернелов (сейчас `Allocate` принимает только `CommandBuffer`) — это изменение дизайна, не точечный фикс. Отметить в `Techdebt.md` как предложенное направление.

DoD: предупреждение не появляется при входе и выходе из Play Mode на любом пресете с полями.

### 5. Физическая вилка вместо калиброванной в тесте адвекции

Сейчас `HarnessAdvectTests` (случай Gaussian) утверждает `dCOM` в вилке, центр которой пришёл из измерения — то есть ровно то, что ADR-014 §7 называет плохим оракулом. Появилось замкнутое предсказание, которое это снимает.

При self-advection каждый элемент возмущения переносится своей локальной скоростью, поэтому смещение центра масс добавки за `N` шагов равно `N·⟨δ⟩`, где `⟨δ⟩ = Σδ²/Σδ`. Для гауссиана это считается точно и **не зависит от σ**: в 2D `⟨δ⟩ = A/2`, в 1D `A/√2`. Значит бездиссипативный потолок overshoot при `amp = 0.05`, 8 шагов, 2D-профиле равен `8 · 0.05 / 2 = 0.200`. Диссипация может только уменьшать величину: билинейная интерполяция — выпуклая комбинация, максимум-принцип держится, амплитуда падает, профиль расплывается.

Заменить утверждение на физическое, не привязанное ни к формату, ни к машине:

```
0 < overshoot < 8 * amp * 0.5      // (0, 0.200) при amp = 0.05, 8 шагов, 2D-гауссиан
```

Нижняя граница проверяет содержательное утверждение ADR-013 («self-advection систематически обгоняет пассивный носитель»), верхняя — что схема диссипативна, а не накачивает энергию. Измеренные `0.100` (R32) и `0.26` (R16) оставить в комментарии и отчёте как документацию, не как ожидание.

Тест на `R16G16F` сохранить, но переформулировать: `0.26` **превышает** бездиссипативный потолок `0.200`, чего диссипативная схема дать не может, — то есть тест документирует, что в боевом формате overshoot измерять нельзя. Это полезное знание, а не падающий тест. Строгая граница без опоры на форму профиля — `8·A = 0.4`, в неё `0.26` формально попадает; аргумент именно в несовместимости с расплывающимся гауссианом, так и записать.

Заодно дописать в `ADR-013` и `pass-catalog.md`, что эта оценка — независимое подтверждение непригодности half для данного измерения, более жёсткое, чем прежняя оценка шума «порядка `±0.1`».
