# ТЗ E1: автоматизация замеров на S10 (харнесс, скрипты, Streamline CLI, документы)

**Исполнитель:** Grok. **Ревью:** Claude и владелец. **Куда положить:** `DOC/last/todo-e1-s10-measurement-automation.md`. **Основа:** общие правила §0 из `todo-adr-043-044-p6-fixes.md` (явные `git add`, без `stash`/`checkout`/`restore`/`reset`, существующие тесты не править, отчёт по форме). Три части E1a, E1b, E1c, **по одному коммиту на часть, остановка на гейте после каждой**.

## Зачем

1. **Все замеры до 2026-10-12 сняты в режиме энергосбережения.** Streamline показал, что GPU тогда работал на ~370 МГц (GPU active 3,48 Гцикла за 9,4 с), а после отключения энергосбережения на ~680 МГц (10,9 Гцикла за 16 с). Это почти наверняка объясняет «медленные» и «быстрые» прогоны на 2280×1080 и 3040×1440 и делает прежнюю базу негодной. Нужно переснять базу и впредь **проверять условия до каждой серии**.
2. Время в миллисекундах зависит от частоты GPU, которой мы не управляем. Для сравнения кода нужны **циклы GPU на кадр** (Streamline).
3. Ручное нажатие кнопок и ручной подсчёт дают ошибки. Параметры и итоги должны задаваться и считаться скриптами.

## E1a. Харнесс: параметры командной строки и метаданные (C#)

Файлы: `FPSDisplay.cs` (и новый маленький файл парсера, например `PerfArgs.cs`), новый тестовый файл. Больше ничего.

1. **Параметры** (читать из `Environment.GetCommandLineArgs()`; на Android Unity принимает их через `adb shell am start ... -e unity "<args>"`, проверить на устройстве и записать результат в сдаче):
   - `-m3d_force <0|1>`, `-m3d_render <0|1>`, `-m3d_maxn <int>` (начальные значения вместо кнопок);
   - `-m3d_warmup <с>` (по умолчанию 30), `-m3d_measure <с>` (по умолчанию 30);
   - `-m3d_autorun`: запустить прогон сразу после загрузки сцены, без нажатия кнопки;
   - `-m3d_quit`: вызвать `Application.Quit()` через несколько секунд после `phase=DONE`;
   - `-m3d_tag <строка>`: произвольная метка, попадает в `M3D_PERF_INFO` (хэш сборки, примечание).
     Без параметров поведение харнесса **не меняется** (кнопки и значения по умолчанию как сейчас).
2. **Парсер аргументов** вынести в чистую функцию (`PerfArgs.Parse(string[]) -> PerfArgs`), без обращений к Unity API.
3. **Метаданные** в `M3D_PERF_INFO` (к уже существующим полям, существующие поля и порядок не менять; **строка печатается один раз после применения параметров** (или после тайм-аута 10 с, если мир не найден), чтобы `args` и `applied` отражали реальность): `applied` (1, если параметры силы, рендера и соседей применены или не заданы, 0 при тайм-ауте), `dirtyhash`, `scene` (имя активной сцены), `camera` (ortho size основной камеры, `na` если не ортографическая), `build` (см. ниже), `dirty` (0 или 1), `powersave` (`PowerManager.isPowerSaveMode()` через JNI, как для температуры), `battery` (`SystemInfo.batteryLevel`, проценты), `charging` (`SystemInfo.batteryStatus == Charging`), `tag`.
4. **Хэш сборки и признак грязного дерева.** Простейший способ в пределах ~30 строк: Editor-скрипт `IPreprocessBuildWithReport`, который пишет в `Assets/Resources/m3d_build.txt` (TextAsset, читается через `Resources.Load`; **не в `StreamingAssets`**: на Android он лежит внутри APK, и `System.IO` его не читает) строки `build=<git rev-parse --short HEAD>`, `dirty=<0|1>` (по `git status --porcelain` по путям `Assets`, `Packages`, `ProjectSettings`, неотслеживаемые файлы тоже считаются, они попадают в сборку) и `dirtyhash=<8 hex>` (короткий SHA1 от `git diff HEAD -- Assets Packages ProjectSettings` плюс отсортированный список неотслеживаемых файлов в этих путях): так по логу видно, одинаковым ли было грязное состояние у двух сборок. После записи файла вызвать `AssetDatabase.ImportAsset`, чтобы он попал в сборку. Файл и его `.meta` исключены из git отдельным `.gitignore` в `Assets/Resources/` (**корневой `.gitignore` не править**). Харнесс читает файл при старте. Если файла нет, `build=na dirty=na`. Если выбранный способ окажется сложнее, допустим запасной вариант: брать значение из `-m3d_tag`. Записать выбор в сдаче.
5. **Тесты** (EditMode, новый файл): разбор всех ключей, значения по умолчанию, неизвестные ключи игнорируются, пропущенное значение у ключа не роняет парсер, отрицательные и нечисловые значения заменяются значениями по умолчанию. Режим без аргументов даёт те же значения, что харнесс использовал раньше.
6. **Гейт E1a:** весь EditMode зелёный (число до и после), существующие тесты без правок. Сборка APK для S10 с этим коммитом проверена владельцем: прогон `adb shell am start -n com.slonInc.vfx/com.unity3d.player.UnityPlayerGameActivity -e unity "-m3d_autorun -m3d_force 1 -m3d_render 0 -m3d_warmup 15 -m3d_measure 10 -m3d_quit -m3d_tag test"` запускается сам, печатает `M3D_PERF` с `phase=DONE` и закрывает приложение. (Если Grok не может подключить устройство, он описывает шаги проверки для владельца и ждёт результата.)

## E1b. Скрипты (PowerShell 5.1 или новее, без установки Python и других зависимостей)

Папка `Tools/s10/` (вне `Assets`, Unity её не импортирует), `Tools/s10/.gitignore` с `out/` и `*.apc`. Пути к `adb` и `Streamline-cli.exe` брать из параметров или `PATH`.

1. **`preflight.ps1`** `-Serial <id> [-ExpectRes WxH] [-ExpectCharging <true|false>] [-MinBattery 50] [-MaxBatteryTempC 40]`. Проверки через `adb`:
   - устройство найдено;
   - энергосбережение выключено (`adb shell settings get global low_power` равно 0; если у Samsung есть другой ключ, найти и использовать, записать в сдаче);
   - уровень заряда и статус (`adb shell dumpsys battery`), температура батареи;
   - экран включён (`dumpsys power`, `mWakefulness=Awake`);
   - разрешение (`adb shell wm size`), если задан `-ExpectRes`;
   - состояние ОС по температуре, если доступно (`dumpsys thermalservice`), иначе пропустить с пометкой.
     Выход: таблица «проверка, значение, статус» и код возврата ненулевой при любой неудаче. Скрипт ничего на устройстве не меняет.
2. **`run-series.ps1`** `-Serial <id> [-Adb <путь>] [-ExpectBuild <хэш>] -OutDir <каталог> [-Series ABABC] [-WarmupSec 60] [-MeasureSec 30] [-CooldownSec 60] [-Tag <строка>]`. **Установка не выполняется** (приложение ставит владелец): скрипт проверяет, что пакет установлен (`pm list packages`), печатает время установки (`dumpsys package`) и после первого запуска сверяет `build=` в `M3D_PERF_INFO` с `-ExpectBuild`; при несовпадении серия прерывается. Для каждой точки серии: `adb shell am force-stop`, `adb logcat -c`, запуск активности с аргументами из п. E1a (`-m3d_autorun -m3d_quit -m3d_force/-m3d_render` по буквам серии: `A` = сила 1, рендер 1; `B` = сила 1, рендер 0; `C` = сила 0, рендер 1), ожидание `phase=DONE` в `logcat` (с таймаутом), сохранение строк `M3D_PERF` в `OutDir\<NN>-<режим>.txt`, пауза `-CooldownSec`. Перед серией вызывает `preflight.ps1` и прерывается, если он не прошёл. Серия по умолчанию `ABABC` (чередование, как мы договорились).
3. **`summarize.ps1`** `-Logs <каталог или файлы> [-Baseline <summary.csv>] [-Out summary.md]`. Разбирает строки `M3D_PERF` (формат и поля как в `DOC/MEASURE/ee2ce26/*_logcat.txt`; **учесть обрезанную первую строку и дубли `DONE`**, брать последнюю строку `DONE` каждого прогона по `res`, `force`, `render`), печатает таблицу по режимам: `frameAvg`, `long` для каждого повтора, **медиана по режиму**, разброс (максимум минус минимум), цена рендера (`A` минус `B`), и при `-Baseline` разницу с базой с пометкой «шум» (меньше `max(2 × разброс, 0,5 мс)` или 3 п. п. по `long`). Пишет `summary.md` и `summary.csv`. **Регрессионный тест парсера:** на `DOC/MEASURE/ee2ce26/ee2ce26_logcat.txt` и `m3d_perf.csv` скрипт должен воспроизвести значения таблицы из D2 (например, 1520×720 «сила и рендер вкл» 20,22 и 20,25 мс, `long` 0,198 и 0,209). Записать сравнение в сдаче.
4. **`capture-streamline.ps1`** `-Serial <id> -OutDir <каталог> -Mode <A|B|C> [-WarmupSec 60] [-MeasureSec 25] [-Session <session.xml>]`. Запускает `Streamline-cli.exe -capture` с шаблоном `"Mali-G76 - Bifrost"`, `-package com.slonInc.vfx -activity com.unity3d.player.UnityPlayerGameActivity -activity-args "<m3d-аргументы>" -clean-gatord -duration (warmup+measure+запас) -o <apc>`, затем `-report <apc> -timeline=timeline.csv -start <warmup> -stop <warmup+measure> -default-template with-metrics -format csv -output <каталог>` (если `with-metrics` не отдаёт нужные производные, использовать `-template "Mali-G76 - Bifrost"`). **Захваты `.apc` не коммитить.** `-Session` по умолчанию копия `session.xml` из существующего захвата владельца с `call_stack_unwinding="no"` (профиль CPU не нужен и добавляет накладные расходы), копия лежит в `Tools/s10/session-gpu.xml` и коммитится.
5. **`gpu-metrics.ps1`** `-Timeline <timeline.csv> -FrameAvgMs <число из харнесса>`. По CSV (**имена колонок обнаружить по реальным файлам, начать с отчётов по `Capture.apc` и `Capture_02.apc` владельца**) считает: частоту GPU в МГц (`сумма GPU_ACTIVE / длительность окна`), **циклы GPU на кадр** (частота × `FrameAvgMs`, либо число кадров из длительности и `frameAvg`), долю не-фрагментной очереди (`JS1`) и фрагментной (`JS0`), `COMPUTE_ACTIVE`, **долю расходящихся инструкций** (`EXEC_INSTR_DIVERGED / EXEC_INSTR_COUNT`), **долю частичных чтений** (`LS_MEM_READ_SHORT / (FULL + SHORT)`), атомики на кадр, внешний трафик в МБ на кадр (`L2_EXT_*_BEATS × шина/8`), видимые и отсечённые примитивы (доля видимых). Печатает таблицу и `gpu-metrics.csv`. Проверочный запуск на двух захватах владельца должен воспроизвести значения, прочитанные мной вручную: `Capture.apc` окно 25–35 с даёт около 370 МГц и 99,6% не-фрагментной очереди, `Capture_02.apc` окно примерно 22–38 с даёт около 680 МГц (допуск 5%).
6. **Предупреждение о частоте.** `gpu-metrics.ps1` печатает `ПРЕДУПРЕЖДЕНИЕ`, если частота ниже 600 МГц (порог в параметре): серия при таком режиме считается недействительной.
7. **Гейт E1b:** все скрипты запускаются из `powershell -ExecutionPolicy Bypass -File ...` без ошибок на устройстве владельца (или, если устройства нет, на сохранённых логах и захватах, с пометкой, что запуск на устройстве за владельцем); регрессия парсера пройдена; в сдаче список реальных имён колонок `timeline.csv` и результатов проверок.
