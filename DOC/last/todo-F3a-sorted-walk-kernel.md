# ТЗ F3a: кернел `BoidNeighborForceSorted` и переключатель `-m3d_walk`

**Исполнитель:** Grok. **Ревью:** Claude и владелец.
**Куда положить:** `DOC/last/todo-F3a-sorted-walk-kernel.md`.
**Основа:** `DOC/last/todo-f3-sorted-walk.md` (раздел F3a и «Документы»), ADR-047 (`DOC/ADR/ADR-047-Sorted-Order-Neighbor-Walk.md`, создаётся в этой фазе), `plan-P7-perf-200k.md`, ADR-046. Общие правила §0 из `todo-adr-043-044-p6-fixes.md` действуют. **Один коммит, остановка на гейте.** Часть 0 выполнена (`8b5450f`), F3b (`walk 2`, упакованная запись) в эту фазу **не входит**.

## 1. Зачем

В профиле B расходятся 85% инструкций, частичных чтений 96%: поток идёт по исходному индексу частицы, соседние потоки обходят случайные ячейки. Новый кернел ставит поток на слот отсортированного массива, тогда соседние потоки делят ячейки. `SortedIndices` (сейчас мёртвая запись, Techdebt 10j) начинает читаться.

## 2. Что сохранить буквально (иначе стаи изменятся без объявления)

1. **Порядок посещения и кап.** Ячейки `k = (start + n) % 9`, `start = i % 9`, где `i` **исходный индекс частицы** (`SortedIndices[slot0]`), не слот. Внутри ячейки слоты по возрастанию. Шаг `dy = k / 3 - 1`, `dx = k % 3 - 1`. Пропуск `r2 < 1e-6`. Проверка `visited >= MaxNeighbors` **до** инкремента и **до** проверки радиуса; `break` выходит из всего обхода (`capped`). `CountCapHits` считается так же.
2. Множитель `inter`, радиусы по командам, `min(team, 7)`, суммы и нормализация без изменений. Запись `velocity[i] += float3(force.x, 0, force.y)` по исходному индексу `i`.
3. `HashWrap = 0`: выход за границу даёт `continue` без изменения порядка остальных ячеек.
4. Прежний кернел `BoidNeighborForce` **не менять ни одной строкой** (в `git diff` внутри него нет изменённых строк).

## 3. Что сделать

### 3.1. Кернел `BoidNeighborForceSorted` (`Assets/Shaders/GPU/Passes/BoidsPasses.compute`)

1. `#pragma kernel BoidNeighborForceSorted`. Объявить `StructuredBuffer<uint> SortedIndices`. `slot0 = id.x`; `if (slot0 >= ParticleCount) return;` `i = SortedIndices[slot0]`; `self = SortedPositions[slot0]`; `selfTeam = min(SortedTeams[slot0], 7u)`. `cell = HashCellCoord(self)`.
2. **Объединение диапазонов.** Идти по девяти ячейкам в порядке п. 2.1, держать накопленный диапазон `[rs, re)` и целый сдвиг `(sx, sy)` в `{-1, 0, +1}`. Пустую ячейку (`CellCounts == 0`) **пропускать, не закрывая диапазон**. Непустую присоединять (`re += count`), **только если** `CellStarts[next] == re` и знак сдвига по обеим осям тот же; иначе закрыть диапазон (обработать слоты) и начать новый. Конкатенация диапазонов обязана дать ту же последовательность слотов, что обход девяти ячеек по отдельности. Кап внутри диапазона прерывает всё: открытые и ещё не просмотренные ячейки не обрабатываются.
3. **Сдвиг тора на ячейку.** `raw = cell + int2(dx, dy)`. При `HashWrap != 0`: `raw.x < 0` → `raw.x += HashRes.x`, сдвиг `-HashSize.x`; `raw.x >= HashRes.x` → `raw.x -= HashRes.x`, сдвиг `+HashSize.x`; то же по `y`. Сдвиг по оси равен **`±HashSize`**, не `(raw − wrapped) · HashCellSize`. `d = SortedPositions[slot] - self + сдвиг`. Целочисленных `%` и делений при выборе ячейки быть не должно (допустимо `k` из таблицы или вычитание 9). При `HashWrap = 0` сдвиг ноль, выход за границу `continue`.
4. Реализацию обработки диапазона (функция с `inout`-состоянием или иное) выбирает Grok; обязательны пп. 2.1 и 2.2 и отсутствие предупреждений компилятора. Прежняя проверка радиуса, команда соседа и ветки `same`/`inter` перенесены без изменений.

### 3.2. Пасс `BoidNeighborForcePass`

1. Поле `[SerializeField] private int walkMode` (0 по умолчанию) и свойство `WalkMode` (допустимо 0..2, иначе `ArgumentOutOfRangeException`, как у `MaxNeighbors`). Менять можно во время работы без пересоздания мира.
2. **Хук в `Assets/Scripts/Runtime/SimPass.cs` (разрешён, минимальный).** В `ParticleKernelPass` добавить `protected virtual KernelHandle SelectKernel(SimContext context)` (по умолчанию возвращает кернел из `Initialize`). `Execute` вызывает его один раз в начале и использует выбранный кернел для привязки атрибутов, `SetParams`, `ParticleCount` и `DispatchCompute`. **`BindBuffer` и `Kernel` должны работать с выбранным кернелом**, иначе буферы привяжутся не к тому индексу. Поведение других пассов не меняется.
3. `BoidNeighborForcePass`: в `Initialize` найти и закэшировать оба кернела (`FindKernel("BoidNeighborForceSorted")`); `SelectKernel` возвращает Sorted при `walkMode >= 1`, если защита (п. 3.2.5) не сработала. Дополнительно в `SetParams` привязать `SortedIndices` (`hash.SortedIndices`) для Sorted. Диспатч одной размерности: `(count + 63) / 64` групп.
4. **Режим 2 до F3b.** Режим 2 принимается, выполняет Sorted (как `walk 1`) и один раз пишет предупреждение «walk 2 ещё не реализован, выполняется walk 1». Упакованного буфера в этой фазе нет.
5. **Защита (ADR-047 §2.5).** Пасс не выполняет Sorted, если `max(радиусов команд) > min(HashCellSize.x, HashCellSize.y) · (1 + SpatialHashSet.GridEpsilon)` (то же сравнение, что `TeamRadiusPlayCheck`); тогда выполняется `walk 0`, и пасс **один раз** пишет предупреждение (повтор только при смене значения, по образцу `TeamRadiusPlayCheck`). Условие `HashRes ≥ 3` при торе уже обеспечивает `SpatialHashSet.ValidateLayout`, отдельной проверки не нужно.
6. **CPU-источник максимума радиуса (решение этого ТЗ).** Буфер `Teams` лежит на GPU, пасс радиусов не видит. Добавить в `SimContext` внутреннее поле `TeamMaxRadius` (`float`, `internal set`), которое `SimulationWorld` выставляет рядом с каждым `TeamParams.Upload` (две точки: создание мира и покадровая перезаливка) как `max` по трём радиусам всех команд. Значение `0` (неизвестно, например в тестах, собирающих `SimContext` вручную) означает «защита не проверяет». Тесты, которым нужна защита, выставляют поле сами. `TeamParams` (раскладку и `Upload`) не менять: поле считается в вызывающем коде или в маленьком статическом хелпере рядом.

### 3.3. Переключатель `-m3d_walk <0|1|2>`, харнесс и скрипты

Образец: `-m3d_maxn`. Прочитать, как сделан `maxn`, и повторить.
1. **`PerfArgs`:** `HasWalk`/`Walk`, разбор `-m3d_walk` (допустимо 0..2, иначе предупреждение разбора как у `maxn`), включить в `HasOverride`. В строку `args` поле `walk=` дописывается только если `-m3d_walk` задан (п. 3).
2. **`FPSDisplay.TryApplyOverrides`:** при `HasWalk` и `forcePass == null` вернуть `false` (как для `maxn`), иначе `forcePass.WalkMode = perfArgs.Walk` без пересоздания мира.
3. **Вывод (отклонение: существующий тест `FormatRun` не меняется).** В строку `args` поле `walk=` дописывается только если был задан `-m3d_walk`, как `scene=`. В конец `M3D_PERF_INFO` и `M3D_PERF` всегда пишется `WalkMode` пасса; если пасса силы нет, пишется `na`. Прежний порядок полей не меняется.
4. **`Tools/s10/summarize.ps1`:** группировать по паре режим и `walk`. Строка без поля `walk` относится к группе `na`, старые CSV из `DOC/MEASURE/` разбираются как раньше. В `summary.md` колонка `walk`. **`Tools/s10/run-series.ps1`:** строка без пробелов и без цифр (`ABABC`) разбирается по символам, как раньше. Иначе токены через пробел. Токен `A` значит «walk не задан, значение ассета» (так же строка с пробелами и без цифр, например `A B`). Токен `A0` значит режим A и walk 0. Токен вроде `A0A1` без пробела отклоняется явной ошибкой с понятным текстом, а не разбирается как старая строка. Правило пишется в справке скрипта. Пример: `-Series "A0 A1 A0 A1 B0 B1 B0 B1"`. Каждый токен это отдельный запуск приложения.
5. Тесты парсера в `PerfArgsTests.cs` — **новые тесты в конец или в отдельный файл**, существующие не править. Проверить: нет аргумента, `0/1/2`, `3`, `-1`, `abc`, пропущенное значение, комбинацию с `-m3d_maxn`, `HasOverride`, строку `args`.

### 3.4. Тесты (новый файл `Assets/Tests/Editor/BoidNeighborForceSortedTests.cs` с `.meta`)

Допуск как в существующем оракуле: `1e-4 + 1e-4 · |ожидаемое|` по компонентам. **Хэш строится один раз, оба кернела выполняются на нём** (порядок слотов внутри ячейки задаёт атомик `InterlockedAdd` в `HashScatter`, на двух сборках хэша он может отличаться). Между запусками `velocity` обнуляется (сила прибавляется через `+=`). Существующий `RunForce` строит хэш заново, поэтому нужен **свой помощник** (на основе `Prepare`, без правки существующего файла): собрать мир, выполнить `clear`, `hash`, затем `force` с `WalkMode = 0`, прочитать `velocity`, обнулить, выполнить `force` с `WalkMode = 1` на том же хэше, прочитать, сравнить. Каждый сценарий сравнивает GPU `walk 1` с GPU `walk 0` и, где есть готовый CPU-оракул из `BoidNeighborForceTests.cs` (кап выключен), с ним.

1. Две команды (как `Oracle_TwoTeams_MatchesGpu`).
2. Кап выключен и включён; **плотный случай, где кап срабатывает** (как `CapDense...`); доля капа совпадает с `walk 0`.
3. Шов тора (`Seam_Wrap...`) и сетка без тора (`NoWrap...`).
4. `TeamId > 7`.
5. Число частиц не кратно 64; все частицы в одной ячейке; пустые ячейки между занятыми; **ячейки с подряд идущими слотами и разными сдвигами тора** (сценарий на шве, где между двумя занятыми ячейками разных краёв мира все остальные пусты), чтобы условие про сдвиг ловилось тестом.
6. **Случайная проверка:** не менее 30 зёрен, `N` от 500 до 3000, тор и без, кап 0 / 16 / 48, сравнение `walk 0` и `walk 1`.
7. Переключение `walk` во время работы (0 → 1 → 0) без исключений; результат `walk 0` после возврата тот же в допуске, что и до переключения (на том же хэше).
8. Защита (п. 3.2.5): `SimContext.TeamMaxRadius` больше размера ячейки при `walkMode = 1` даёт ровно одно предупреждение (`LogAssert`) и результат `walk 0` (побитово равен прогону с `WalkMode = 0` на том же хэше); `TeamMaxRadius = 0` защиту не включает. Сценарий `HashRes < 3` при торе недостижим (`ValidateLayout` бросает раньше), отдельного теста не нужно.
9. Режим 2 в этой фазе: один раз предупреждение и результат `walk 1`.
10. **Расхождения в ulp:** во всех сценариях посчитать максимальное расхождение `walk 1` и `walk 0` в ulp и вывести в лог теста (`TestContext.WriteLine`). Побитовое равенство ожидается, но **не жёсткий гейт** (компилятор может по-разному свернуть `fma`); жёсткий гейт допуск 1e-4.

Существующие тесты проходят без правок. Тесты оракула и тесты пресетов остаются зелёными.

## 5. Гейт F3a

1. EditMode зелёный: число **до** и **после** (весь прогон, не только новые тесты).
2. **`walk 0` не изменился.** (а) `git diff` показывает, что внутри `BoidNeighborForce` нет изменённых строк; (б) побитовая проверка на одном сценарии с **одной частицей на ячейку** (решётка с шагом больше размера ячейки: порядок слотов тривиален и результат детерминирован): записать биты `velocity` **до правок** (старый код) и сравнить после; приложить обе записи в сдаче.
3. Play `Boids_Hash` и `Boids_Hash_2Teams`: вид при `-m3d_walk 0` и `1` одинаков (кадры около 1 с и 15 с, сравнивать палитру, не положения). Для `Boids_Hash_2Teams` доля капа `LastCapHitFraction` проверяется так: снять walk 0 дважды и взять Δ00 = |капа₀ₐ − капа₀ᵦ|; порог для walk 1 равен `max(2 · Δ00, 2 / N)`. Все три числа (два прогона walk 0 и прогон walk 1) записать в сдаче. Это проверка здравого смысла, не жёсткий гейт: точное равенство капа walk 0 и walk 1 проверяют EditMode-тесты на одном хэше (сценарий 2). Если Δ00 заметно больше `2 / N`, порог берётся по нему.
4. В консоли нет предупреждений и ошибок шейдера и Unity (в том числе про непривязанные буферы и необъявленные свойства).
5. ADR-047 написан и лежит в `DOC/ADR/`. Приложение собирает владелец.
