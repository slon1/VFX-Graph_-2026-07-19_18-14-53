## 3. Фаза F5.3b-Б. Документы (один коммит)

Расчёт по прогонам, годным по §1.4. Медиана ячейки это среднее двух центральных значений после сортировки при чётном числе прогонов; считать по неокруглённым значениям, в таблицах два знака после запятой, пороги проверять до округления.

1. **`F5-report.md`, шапка.** Определить «экран» через `res` фазы замера. Отдельным абзацем: у шести прогонов 23 октября (`1221/02`, `1228/02`, `1235/01`, `1242/02`, `1242/03`, `1249/01`) `INFO.screen=720x1520` на старте, приложение повернулось до WARMUP, во всех строках замера `res=1520x720`, то есть по ориентации они годны. Пять из них (все, кроме `1249/01`) остаются в таблицах как были. `1249/01` годен по `res`, но в таблицу не входит: ячейка 64 переснята 26 октября и её медиана берётся из `20261026-2325/` (как записано в README). Исключён `1249/02` (`res=720x1520`, чужая сцена).
2. **Серия 1.** Пересчитать таблицу; ячейка 48 по шести прогонам (три плюс три). Добавить колонку «диапазон `walkCost`» по крайним сочетаниям прогонов ячейки: нижняя граница `(min gpuAvg(8) − max gpuAvg(4)) / 4`, верхняя `(max gpuAvg(8) − min gpuAvg(4)) / 4`.
3. **Отношения 128/48 и 192/48.** Указывать отношение медиан и **диапазон при крайних значениях обеих ячеек**: нижняя граница `walkCost_lo(кап) / walkCost_hi(48)`, верхняя `walkCost_hi(кап) / walkCost_lo(48)`. Для сверки, на старых данных до пересъёма: 128/48 даёт 2,52–3,23, 192/48 даёт 3,85–4,92. Фразу «совпало с оценкой 2,7» заменить проверяемой: «оценка 2,7 лежит внутри / вне диапазона». Ту же правку внести в ADR-052 §6 (абзац F5.3) и в строку F5.3 в `DOC/status.md`.
4. **Новый раздел «Кадр режима B при `forcerep` 1».** `gpuAvg` в логах это `FrameTiming.gpuFrameTime`, то есть GPU-время **всего кадра** (хэш, сила, руление, интегрирование, границы, минимальный URP), а повторы `forcerep` добавляют только проход силы. Поэтому `F = gpuAvg(forcerep 4) − 3·walkCost` это GPU-время кадра режима B при `forcerep` 1, а не цена одного прохода. Таблица для серии 1 (все шесть капов) и серии 2 (48, 128, 192): колонки `walkCost`, `F` (оценка), измеренный `gpuAvg(forcerep 1)` там, где есть, «источник» (`измерено` или `оценка`), частота `1000 / max(кадр; 16,72)` и отметки «M1: кадр ≤ 33,3 мс» и «M2: кадр ≤ 16,7 мс». **Отметки ставить по измеренному, а где измерения нет, по `F`.** Частоту называть «потолком частоты игры при этом капе без рендера частиц»: рендер частиц, физика сверх режима B и вывод поверх кадра её только уменьшают. Под таблицей: `F` верхняя оценка (в `gpuAvg(4)` есть обнуление скрэтча, которого при `forcerep` 1 нет).
5. **Сверка оценки с измерением** (капы 128 и 192, и 96, если снят). Три точки `forcerep` 1, 4, 8 решают модель точно, поэтому «линейность подтверждена» не писать. Считать и записать:
   - `walkCost = (gpuAvg(8) − gpuAvg(4)) / 4`;
   - `zeroCost_ms = gpuAvg(4) − gpuAvg(1) − 3·walkCost` (это и есть разность `F` и измерения; в неё входит обнуление скрэтча и любая нелинейность между `forcerep` 1 и 4);
   - долю `zeroCost_ms / gpuAvg(1)` в процентах.
   Если `zeroCost_ms` положительный и не больше 10% кадра, написать «разность между оценкой `F` и измерением не больше 10% кадра, вывод по M1 и M2 по `F` и по измерению одинаков: да/нет». Если больше 10% или отрицательный (первый проход дороже экстраполяции), написать это и пояснить, что оценка `F` для этого капа не используется.
6. **Вывод.** Добавить две фразы без выбора капа: укладывается ли кап 128 и кап 192 в M1 и в M2 по измеренному кадру (там, где он есть). Слов «рекомендуется» и «для поставки» не писать.
