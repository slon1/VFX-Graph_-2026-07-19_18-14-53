### 4.2. Пасс

1. **Не использовать `RepeatCount` пасса.** Базовый `SimPass.RepeatCount` виртуальный (по умолчанию 1), `SimulationWorld` вызывает `Execute` ровно `pass.RepeatCount` раз. Если пасс силы переопределит его, мир прибавит силу к `velocity` `forcerep` раз. Завести отдельный счётчик `BoidNeighborForcePass.ForceRepeatCount` (без `override`, по умолчанию 1, зажать в 1..16), виртуальный `RepeatCount` не трогать.
2. Мир вызывает `Execute` один раз за кадр, повторы внутри него. `ParticleKernelPass.Execute` запечатан, поэтому повторы ставятся в `OnDispatched` сразу после первого диспатча (это тот же вызов `Execute`); чтение `CapHits`, которое уже есть в этом методе, остаётся после повторов, пока у них `CountCapHits = 0`, иначе счётчик умножится на число повторов. Если пасс пишет параметры в командный буфер, `velocity` и `CountCapHits` для повторов менять тем же способом (`cmd.SetCompute…Param`), чтобы порядок параметров относительно диспатчей сохранился: отложенная перепривязка через `cs.Set…` задела бы и первый диспатч, и `velocity` осталась бы без силы (тест §4.4 п. 1 это поймает). Первый диспатч как сейчас. Для k = 2…R в том же `Execute`: тот же выбранный кернел и те же привязки, кроме `velocity` (привязать `ForceScratch`, `float3[particleCount]`, stride равен stride `velocity`, 12 байт; выделяется лениво только при `ForceRepeatCount > 1`, пересоздаётся при смене `particleCount`, освобождается в `Dispose`) и `CountCapHits` (0 на повторах, прежнее значение возвращается после последнего). **`ForceScratch` обнулить перед повторами кадра**, иначе «после прогона не нулевой» не доказывает, что повторный диспатч был.
3. Повторы идут после первого диспатча и до следующего пасса; барьеры как между обычными диспатчами. Скрэтч накапливает силу (`+=`) и не используется нигде, кроме повторов.

## 6. Фаза F5.3. Серия на S10 и отчёт

Условие начала: F5.1 принят, F5.2 принят. Протокол по `.cursor/skills/s10-measure/SKILL.md`; сборка `dirty=0` (чистое дерево), `powersave=0`, экран `1520×720`, камера 46, зарядка включена, заряд выше 15% (Замер 4 шёл при 4–20%, это повторить при нормальном заряде). Три повтора на ячейку, медиана. Прогоны со счётчиком капа (`-m3d_cap 1`) идут **отдельными** прогонами и в циклы не входят.

**Единица цены.** Цена обхода считается в одной единице на обеих точках: либо только циклы, либо только `gpuAvg`. На S200 `walk 1` при `forcerep 1` стоит на vsync, поэтому миллисекунды кадра при `forcerep 1` для цены не использовать. Серии идут при `forcerep` 4 и 8 (оба выше vsync), цена по `gpuAvg` из лога; к циклам её привязывают захваты Streamline на опорных ячейках при `forcerep` 1, 4 и 8 (все три точки в циклах; зачем третья, см. «Цена обхода»).

**Серия 1. S200** (`Boids_Hash_test200k`), сила без рендера (токен `B` автоматизации), `walk 1`, `forcerep` 4 и 8: `maxn` 32 / 48 / 64 / 96 / 128 / 192. Это 6 ячеек × 2 повтора силы × 3 прогона.

**Серия 2. S100×4** (`Boids_Hash_testx4`), сила без рендера, `walk 1`, `forcerep` 4 и 8: `maxn` 48 / 128 / 192. Отдельный прогон со счётчиком капа на каждой ячейке (по одному): `capfrac`.

**Опорные захваты Streamline (делает владелец, по образцу `s200-streamline/`):** S200, `walk 1`, две ячейки: `maxn 48` и принятая в F5.2 (128 или 192; если приняты обе, 128; если ни одна, только `maxn 48`). Сила без рендера при `forcerep` 1, 4 и 8 (6 захватов) и с рендером (токен `A`) при `forcerep` 1 (2 захвата), всего 8 захватов. Захваты одной ячейки снимать подряд в одной сессии в порядке 1, 4, 8, чтобы сравнивать их при одном тепловом состоянии. В захватах для опорной ячейки записать загрузку арифметического конвейера и конвейера загрузки/сохранения в обходе (условие возврата к кернелу `Accepted`, ADR-052 §3). Циклы режима с рендером на S200 раньше не снимались.

**Цена обхода.** Для всех ячеек серий: `walkCost_ms = (gpuAvg(forcerep 8) − gpuAvg(forcerep 4)) / 4`. Для опорных ячеек в циклах основная оценка берётся по паре 4 и 8, контрольная по паре 1 и 4:

- `walkCost_cyc = (cycles(forcerep 8) − cycles(forcerep 4)) / 4` — **основная**: обнуление скрэтча (`SetBufferData`; есть при `forcerep` ≥ 2, нет при 1) входит в оба захвата и вычитается;
- `walkCost_cyc14 = (cycles(forcerep 4) − cycles(forcerep 1)) / 3` — контрольная: содержит ещё треть цены обнуления, если счётчики её учитывают;
- `zeroCost_cyc = (cycles(forcerep 4) − cycles(forcerep 1)) − 3 · walkCost_cyc` — размер этого слагаемого; `d = walkCost_cyc14 / walkCost_cyc − 1`.

Если `|d| ≤ 2%`, оценки совпали: обнуление в используемые счётчики не попадает, в отчёт идёт `walkCost_cyc` с пометкой «совпало с контрольной». Если `|d| > 2%`, в отчёт идёт основная `walkCost_cyc`, рядом `zeroCost_cyc` и `d`. Порог 2% взят из масштаба: один цикл на частицу это около 2,4% от известной точки 41; исполнитель порог не подбирает. Циклы на частицу из захвата при `forcerep 1` от обнуления не зависят. Если захват при `forcerep 8` невозможен (кадр не набирается, захват обрывается), записать причину и взять пару 1 и 4 с пометкой «возможна переоценка на треть цены обнуления».

Отношение циклов к миллисекундам из захвата сверить с `activeMHz` лога. Ячейки с разным `activeMHz` (расхождение больше 5%) не сравнивать, прогон повторить. Оговорка в отчёте: повторы идут по прогретому L2, настоящий кадр читает холодный, цена по повторам нижняя оценка.

**Расстояние до M2 (формулы для отчёта):**
1. Циклы на частицу в режиме «сила без рендера» (на опорных ячейках из захватов, на остальных пересчётом из `gpuAvg`); `циклы на кадр / число частиц`; сравнить с бюджетом M2 из plan-P7 (около 45–58) и с известной точкой `walk 1`, S200, около 41 цикла (8,12 М на кадр, 16,72 мс на vsync).
2. Для двух опорных ячеек: `render` = (с рендером) − (сила без рендера) в циклах на частицу на S200.
3. Время кадра: `frameMs = циклы на кадр / (частота в МГц × 1000)`; частоту указать две: стартовая и устойчивая после падения (Замер 4: 702 → 433 МГц). Сравнить с 16,7 мс.
4. Вывод в трёх строках: достигнута ли M2 в режиме «сила без рендера» (по циклам), достигнута ли M2 с рендером при стартовой и при устойчивой частоте, сколько циклов на частицу не хватает (или остаётся запас). Не закрывать M2 по режиму «сила без рендера».
5. Строка «`walk 2` не понадобился» или «понадобился», с числом (вход для решения об удалении, ADR-048 §2.5).
6. Сравнение измеренной цены обхода по ячейкам (по основной оценке `walkCost_cyc`) с оценкой ADR-052 §1.1 (visited-128 около 2,7 раза слотов visited-48, около 80 циклов на частицу по линейной оценке): записать расхождение и вывод об условии возврата к кернелу `Accepted`.
7. Вывод по капу: какое значение (48 / 128 / 192) выдерживает поведение (Play F5.2, модель) и во что оно обходится в циклах; решение о значении для поставки это отдельный ADR владельца.
8. Строка о проверке скрэтча: `d` и `zeroCost_cyc` для каждой опорной ячейки и вывод «обнуление учитывается счётчиками» или «не учитывается».
