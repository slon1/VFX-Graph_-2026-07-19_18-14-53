## ТЗ для Grok — ADR-015 (World-Owned Repeat Loop)

### Контекст

Прочитать [ADR-015](../ADR/ADR-015-World-Owned-Repeat-Loop.md). Второй тикет фазы 0. Разблокирует `JacobiPhiPass`: без цикла итерационный решатель в фреймворк не ложится.

Правки production-кода здесь **разрешены** (в отличие от ADR-014) и ограничены тремя местами: одно свойство в `SimPass`, цикл в `SimulationWorld.Update`, валидатор + его вызов в `Build`.

Референсы по месту:

- `Assets/Scripts/Runtime/SimulationWorld.cs:80–128` — цикл пассов, `ProfilingScope`, `SwapPingPongFields`. Это то, что меняется.
- `Assets/Scripts/Runtime/SimPass.cs:243–291` — база; `LastExecuteDispatched` (287), `Execute` abstract (290).
- `Assets/Scripts/Runtime/SimPass.cs:419` — `ShouldDispatch`, из-за которого проверка `LastExecuteDispatched` обязана быть внутри цикла.
- `Assets/Scripts/Runtime/FieldAccumPassValidator.cs` — образец отдельного статического валидатора, вызываемого из `Build`. Новую проверку делать так же, а не инлайном в `Build`.

### Шаг 0 — закрыть открытый пункт ADR-014 (одна строка кода)

Прогнать случай 3.3 Gaussian (`amp=0.05`, `σ=1.5`, carrier 1.7, 8 шагов) на поле `R32G32_SFloat` вместо `R16G16_SFloat`, ничего больше не меняя. Причина: измеренный `dCOM = 13.8575` (overshoot `+0.258`) расходится с записанным в ADR-013 `13.75` (overshoot `+0.15`) в 1.7 раза, а оценка шума квантования half по этому измерению — порядка `±0.1` текселя, то есть сравнима с самим сигналом.

- Если `dCOM` в `R32G32F` окажется около `13.75` — расхождение было квантованием. Тогда: оставить основной тест на `R16G16F` с вилкой как есть, добавить второй на `R32G32F` с более узкой вилкой, и дописать в `ADR-013` + `pass-catalog.md`, что при боевом `R16G16F` overshoot измерим только с точностью `±0.1`.
- Если останется около `13.86` — MCP-число снято при другой геометрии. Тогда пометить `13.75` в `pass-catalog.md` и `Techdebt.md` как неподтверждённое и заменить на измеренное, с указанием геометрии.

В отчёт — оба числа. Ядро не трогать в любом случае.

Попутно: дописать в `HarnessDiffuseTests` комментарий, что совпадение `3.73e-9` в проверках «CPU-оракул» и «симметрия» ожидаемо (CPU-эталон симметричен точно, поэтому асимметрия GPU-поля и есть его отклонение от эталона в той же клетке), и что пик `0.0385` против континуального `1/(4πDn) = 0.0398` — независимое подтверждение, что ядро считает диффузию, а не самосогласованно совпадает с копией своего же шаблона.

### Шаг 1 — `SimPass.RepeatCount`

```csharp
/// <summary>How many times World re-runs this pass per frame. Iterative solvers override it.</summary>
public virtual int RepeatCount => 1;
```

`virtual` property, **без** `[SerializeField]` в базе — обоснование в ADR-015 §1. Никакой существующий пасс это свойство не переопределяет: этот тикет вводит только механизм, `JacobiPhiPass` придёт в фазе F1.

### Шаг 2 — цикл в `SimulationWorld.Update`

Заменить `SimulationWorld.cs:95–106` на цикл из ADR-015 §2. Требования:

- Один `ProfilingScope` **на весь цикл**, не на итерацию.
- Имя сэмплера не менять, счётчик в него не добавлять (кеш `samplers` по пассу устареет при движении слайдера).
- `if (pass.LastExecuteDispatched) SwapPingPongFields(pass)` — **внутри** цикла. Наружу не выносить: `ShouldDispatch` вычисляется на каждом `Execute`, и вынесенная проверка даст число swap'ов, не равное числу диспатчей.
- `pass.RepeatCount` читать один раз перед циклом в локальную переменную, а не на каждой итерации.
- Ничего другого в `Update` не менять. Точечные фиксы (`!Enabled`-валидация, восстановление render target) — F0.4.

### Шаг 3 — валидация `RepeatCount >= 1` на Build

Отдельный статический валидатор по образцу `FieldAccumPassValidator`, вызываемый из `Build` рядом с существующей валидацией пассов. Падать с внятным сообщением: имя пасса, полученное значение, ссылка на ADR-015 §4. Не clamp'ить в рантайме — молчаливый no-op маскирует ошибку конфигурации.

Валидатор обязан быть тестируемым **без** сборки `SimulationWorld`/`EffectAsset`: принимать список пассов, а не `MonoBehaviour`. Иначе тест на него упрётся в ту же инфраструктуру, что и четыре сейчас красных `SimulationWorldDisabledPassInitializeTests`.

### Шаг 4 — харнес: `RepeatCount` по умолчанию

В `FieldTestHarness.RunPass` источником числа итераций становится `pass.RepeatCount`, а явный параметр остаётся как переопределение для эталонной стороны сравнения:

```csharp
void RunPass(SimPass pass, float deltaTime);              // repeat = pass.RepeatCount
void RunPass(SimPass pass, float deltaTime, int repeat);  // явное переопределение
```

Цикл внутри — тот же, что в World. Сверить построчно после правки World: расхождение здесь снова сделает тесты фикцией.

### Шаг 5 — тесты

Файл `Assets/Tests/Editor/RepeatCountTests.cs`, `[Category("GPU")]` где нужен харнес.

**5.1 Побитовое равенство — главный DoD.** Поле Scalar `R32_SFloat`, дельта в центре. Сравнить состояние поля после одного пасса с `RepeatCount = 6` и после шести последовательных одиночных исполнений того же ядра. Это буквально одна и та же последовательность диспатчей, поэтому утверждение — **точное равенство, допуск 0**. Не использовать `AssertApproximately`.

Стаб-пасс: проверить, `sealed` ли `DiffuseFieldPass`. Если да — не распечатывать (это правка production вне скоупа), а написать в тестовом файле стаб `FieldKernelPass` с `KernelName = "DiffuseField"`, теми же `FieldReads`/`FieldWrites` и `SetParams`, пушащим `DeltaTime` и `DiffusionRate`. Такой стаб проверяет семантику цикла, а не сам `DiffuseFieldPass` — для этого тикета это правильный объект проверки, и так и записать комментарием.

**5.2 Чётность.** После `RepeatCount = 2` и после `RepeatCount = 3` свежий результат обязан лежать в `Current` (сравнить с 2 и 3 одиночными исполнениями соответственно). Закрывает утверждение ADR-015 §2 о том, что чётность не является параметром корректности.

**5.3 `ShouldDispatch` внутри цикла.** Стаб, который диспатчит на первой итерации и отказывается на последующих (`ShouldDispatch` возвращает false после первого вызова). При `RepeatCount = 4` обязан произойти **ровно один** swap. Это тест на решение «проверка внутри цикла», то есть на причину, по которой отклонён вариант с циклом внутри пасса. Считать swap'ы можно по тому, в какой из двух текстур оказался результат, либо по счётчику в стабе — выбрать и обосновать.

**5.4 Дефолт не сдвинут.** Reflection по всем неабстрактным наследникам `SimPass` в сборке: `RepeatCount == 1` у каждого. Дешёвый guard от случайного переопределения. Образец обхода типов — в существующих контрактных тестах.

**5.5 Валидатор.** `RepeatCount = 0` и `-1` → исключение с именем пасса в сообщении. Через статический валидатор напрямую, без `SimulationWorld`.

### Шаг 6 — документация

- `DOC/pass-catalog.md`: раздел про `RepeatCount` с предупреждением из ADR-015 «Последствия» — **это итерации решателя, а не субшаги по времени**; `deltaTime` в каждую итерацию идёт одинаковым, поэтому наивное переопределение даёт эффективный шаг `N·dt`. Субшаги — отдельный механизм, которого нет.
- `DOC/capabilities.md`: одна строка про механизм.
- `DOC/status.md`: ADR-015.
- `Techdebt.md`: если шаг 0 изменил статус числа `13.75` — отразить.

### Отчёт

1. Результат шага 0: `dCOM` на `R16G16F` и на `R32G32F`, вывод о происхождении `13.75`.
2. Подтверждение побитового равенства в 5.1 (именно 0 расхождений, не «в пределах допуска»).
3. Число swap'ов в 5.3 и способ их подсчёта.
4. `sealed` ли `DiffuseFieldPass` и какой стаб в итоге использован.
5. Диff по production-коду — должен быть в трёх местах и только в них.
6. Состояние сьюта: сколько тестов, сколько красных. Четыре `SimulationWorldDisabledPassInitializeTests` ожидаемо остаются — они в F0.4.

### Вне скоупа

- `JacobiPhiPass` и любые fluid-пассы — фаза F1.
- Субшаги по времени, clamp `deltaTime` — F0.7.
- Точечные фиксы `!Enabled`, render target, NaN-guard'ы и четыре красных теста — F0.4.
- Переопределение `RepeatCount` в существующих пассах — ни в одном.
- Инспекторный UI сверх штатного `[Range]` на будущем `iterations`.
