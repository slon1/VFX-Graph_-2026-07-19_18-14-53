| Вопрос | Решение |

## 1. Что меняется относительно черновика

| Черновик | v2 | Почему |
|---|---|---|
| Фазы 1→2→3 (источник, цвет, хэш) | Хэш первым (P1), источник потом (P3) | Хэш самый рискованный и ни от чего не зависит |
| Ньютон первым, кинематика «опционально» | Кинематика первой, Ньютон в P9 | Цель: Rivalry-стиль. Цепочка `ClearVelocity` → force → `HeadingSteer` уже есть (ADR-012) |
| Хэш хранит только индексы | Плюс отсортированный снимок `pos`/`dir`/`team` | Убирает гонку чтения/записи и случайный доступ к памяти |
| Hillis–Steele (14–16 диспатчей) | Блочный скан Rivalry (3 кернела, до 65536 ячеек) | Проверен в Rivalry, меньше диспатчей |
| Поиск соседей без тора | Заворот ячеек + кратчайшее смещение | `BoxBounds` Wrap делает мир тором |
| `cellSize = 2` без радиусов | `minCellSize` + эффективный размер ячейки делит мир нацело; валидатор на радиусы | Иначе соседи теряются молча |
| Синхронизация сетки с `BoxBounds` как Techdebt | Валидатор на Build, жёсткая ошибка | Валидаторы уже умеют смотреть на соседние пассы |
| `ParticleColor` Float4 + `ParticleColorMode` | Палитра: `teamId` + 2D LUT (строка на команду) + существующий `value` | ADR-031 уже сделал `value` → LUT |
| Матрица Rivalry N×N | Паритет: параметры на команду | В Rivalry матрицы нет, это новая фича |
| `SwarmSource` по маске-решётке | `count` + форма (диск) + seed + `heading` | Решётка даёт артефакты; Rivalry спавнит `count` в круге |
| `SpatialHashDebugBinder` + шейдер | Счётчики ячеек в объявленное скалярное поле, показывать `DebugFieldQuads` | Ноль нового рендер-кода |
| Нет per-team скорости | `TeamHeadingSteer` читает `cruise`/`turn` из команд | В Rivalry `maxSpeed`/`maxTurnSpeed` на группу |
| Нет тестов силы против эталона | CPU O(N²) эталон против GPU | Проверяет и хэш, и тор, и формулы |

## 2. Архитектура

### 2.1 Цепочка пассов (целевой пресет)

```
BuildSpatialHash        // снимок pos/dir/team по ячейкам
ClearVelocity           // velocity = аккумулятор силы
BoidNeighborForce       // += sep + align + coh (без dt)
[NoiseAccum, TouchAccum]   // P8b, без dt
TeamHeadingSteer        // nlerp heading, flatten Y, velocity = heading * cruise[team]
Integrate               // position += velocity * dt
BoxBounds (Wrap)        // тор
HeadingToValue          // value для палитры (или Entropy, P8a)
```

Хэш строится по позициям с конца прошлого кадра (после Wrap) и по `heading` до steer. Это нужное свойство: снимок не меняется до конца кадра.

### 2.2 Ресурсы

- **`SpatialHashSet`** (`Assets/Scripts/Core/`, `IDisposable`). Владелец: `BuildSpatialHashPass` (прецедент: `ZeroMeanScalarPass` с `IDisposable`). В `Initialize` пасс кладёт его в `context.SpatialHash`. Потребитель в своём `Initialize` берёт `context.SpatialHash`; если `null`, бросает `InvalidOperationException` («добавьте Build Spatial Hash выше»). Это же ловит неправильный порядок. Второй builder: `Initialize` бросает, если `context.SpatialHash != null`. Валидаторы дублируют проверки понятным текстом.
  - Буферы (размер N частиц): `sortedIndex` (uint), `sortedPos` (float2 XZ), `sortedDir` (float2 XZ), `sortedTeam` (uint), `cellOf` (uint).
  - Буферы (размер C ячеек): `cellCount`, `cellStart`, `cellCursor`, плюс `blockSums`, `blockOffsets`.
  - Геометрия: `origin = center.xz - extents.xz`, `size = 2*extents.xz`, `res = floor(size / minCellSize)` по каждой оси (минимум 1), `cell = size / res`. Так `cell >= minCellSize`, и ячейки точно покрывают мир. Клампа к 3 **нет**.
  - Инварианты (ошибка, не коррекция): `res.x * res.y <= 65536` (блочный скан 256×256); при `wrap = true` ещё `res >= 3` по каждой оси (иначе заворот даёт одну ячейку дважды, соседи считаются дважды) и `maxRadius <= size/2` (однозначность кратчайшего смещения; при `cell >= radius` и `res >= 3` выполняется само). Проверять и в `Initialize` билдера (тесты зовут его без валидатора), и в валидаторе на Build.
  - Режим `wrap` (поле билдера): `true` для `BoxBounds` Wrap (заворот ячеек по модулю + `minImage`), `false` для Bounce (ячейки за краем пропускаются, `minImage` не применяется, `res >= 3` не требуется). Шов без соседей возникает только при `wrap = false` в Wrap-мире; на 25×25 это 96 из 625 ячеек, около 15%.
  - Статический `ComputeGrid(center, extents, minCellSize)` общий для пасса и валидатора. `res = floor(size / minCellSize * (1 + 1e-5))`, чтобы деление с ошибкой округления не теряло ячейку; проверки вида `radius <= cell` везде с относительным допуском `1e-5` (`radius <= cell * (1 + 1e-5)`), иначе корректный пресет «радиус 3, minCellSize 3» ругается на 1e-7.
  - Инвариант живых частиц: в проекте `ParticleSet.Count == Capacity` всегда (`EnsureCapacity` ставит `Count = capacity`, рост после создания буферов запрещён). «Призрачных» неспавненных частиц нет, диспатчи хэша и силы идут по `context.Particles.Count`. `SwarmSource` обязан делать `EnsureCapacity(sum count)` ровно один раз. Если когда-нибудь появится спавн меньше capacity, этот инвариант придётся пересмотреть отдельным ADR.
  - `Count == 0`: билдер ничего не выделяет и не диспатчит (буфер нулевого размера создавать нельзя).
- **`TeamProfile`** (`[Serializable]`, список `teams` на `EffectAsset`, максимум 8) и **GPU-буфер команд** `GraphicsBuffer<TeamParams>` в `SimulationWorld`, как `touchBuffer`. Перезаливается каждый кадр (виден Play-тюнинг). Доступ: `context.Teams`.
  - `TeamParams` (3×float4, stride 48): `radii (sep, align, coh, interGroupSepMult)`, `weights (sep, align, coh, 0)`, `motion (cruise, turn, 0, 0)`.
  - `TeamProfile` также хранит `Gradient color` и имя.
- Конструктор `SimContext` не ломаем: свойства `SpatialHash` и `Teams` с `internal set`. Тесты строят свой `SimContext` как раньше.

### 2.3 Формулы (порт Rivalry modern, XZ, `heading` вместо `vel`)

Для частицы с командой `t`, позиция `p`, соседа с командой `u`, `d = minImage(npos - p)`, `r2 = dot(d,d)`:

- Отсечка: `r2 >= maxRadiusSq(t)` или `r2 < 1e-6`: пропуск.
- Separation (если `r2 < sepR²`): `sep += (-d / (r2 + 1e-3)) * (u == t ? 1 : inter)`, `sepN++`.
- Alignment (только `u == t`, `r2 < alignR²`): `align += ndir`, `alignN++`; `dirSum += ndir` (для энтропии).
- Cohesion (только `u == t`, `r2 < cohR²`): `coh += d` (относительное смещение, а не `npos`, из-за тора), `cohN++`.
- Итог: `force = (sepN>0 ? sep/sepN * wSep : 0) + (dot(align, align) > 1e-6 ? normalize(align) * wAlign : 0) + (cohN>0 && dot(coh/cohN, coh/cohN) > 1e-6 ? normalize(coh/cohN) * wCoh : 0)`. Сравнение с квадратом длины, не с самой длиной: порог `1e-6` значит длина больше `1e-3`. Это отличие от Rivalry и от ранней формулировки `|align| > eps`. Для 5a брать квадрат, как в ТЗ.
- `velocity[id] += (force.x, 0, force.y)`.
- `entropy = saturate(1 - |dirSum| / dirN)` (P8a).
- Кап соседей `maxNeighbors` считает **посещённых** (как в Rivalry). Порядок 9 ячеек вращается на `id % 9`, чтобы кап не давал направленного смещения. Новое относительно Rivalry.
- `minImage(d) = d - size * round(d / size)` по каждой оси. Ячейки соседей берутся по модулю `res`. При `wrap = false` ячейка вне сетки пропускается, а не прижимается к последней.
- Индекс команды в кернеле — `min(teamId, 7)`. Буфер всегда из 8 слотов. В чужую команду частицу не пересаживать.

**Как steer использует силу (фиксируется в ТЗ P5b).** Источник истины — код кернела `HeadingSteer` (`DynamicsPasses.compute`, строки 83–103), а не пересказ ниже. Пять вызовов `UnitOr` (защита `force`, `h` до блендинга, `blended`, `h` после обнуления Y) переносятся без изменений. ТЗ P5b цитирует кернел дословно, и допустимо менять только: `TurnSpeed` → `turn[team]`, `CruiseSpeed` → `cruise[team]`, чтение `teamId` и `min(teamId, 7)`. `cruise < 0` и `turn < 0` запрещает валидатор с 5b. `turn == 0` значит `k = 0`: курс не идёт к силе, но Y обнуляется и вектор нормализуется, как в `HeadingSteer`. Пересказ ниже справочный, расхождение с кодом решается в пользу кода:
- `desired = normalize(force)`, если `dot(force,force) > 1e-12`, иначе `desired = heading` (при нулевой силе курс не меняется, скорость `cruise[team]`).
- `k = saturate(turn[team] * dt)`, `heading = normalize(lerp(heading, desired, k))`, дальше `y = 0` и повторная нормализация. Это nlerp к **направлению** силы: абсолютная величина силы не влияет на скорость поворота, значимы только отношения весов `sep : align : coh` и порог `1e-12`.
- Антипараллельный случай (`desired ≈ -heading`): NaN быть не может (`UnitOr` подставляет запасное значение). При `k < 0.5` курс не поворачивается (вектор сжимается и нормализуется обратно), при `k >= 0.5` (в том числе после лага кадра) мгновенно разворачивается на 180°. Это известное поведение, не баг; тестируется, чтобы случайно не сломать.

### P1. Spatial hash: ресурс, пасс, тесты (самая рискованная)

**Файлы (новые):**
- `Assets/Scripts/Core/SpatialHashSet.cs`: буферы, `ComputeGrid`, `Dispose`, `BindForRead(CommandBuffer, KernelHandle)`.
- `Assets/Scripts/Passes/SpatialHashPasses.cs`: `BuildSpatialHashPass : SimPass, IDisposable` (поля: `center`, `extents` XZ, `minCellSize`). `Reads`: Position, Heading, TeamId. Прямой `SimPass`, не `ParticleKernelPass` (несколько кернелов за один `Execute`).
- `Assets/Shaders/GPU/Passes/SpatialHashPasses.compute`: кернелы `HashClear`, `HashCount`, `HashScanBlocks`, `HashScanBlockSums`, `HashAddOffsets`, `HashScatter`.
- `Assets/Shaders/GPU/Includes/SpatialHash.hlsl`: `HashOrigin`, `HashSize`, `HashRes`, `CellOf(posXZ)`, `WrapCell`, `MinImage`.
- `Assets/Scripts/Runtime/SpatialHashValidator.cs`.

**Изменить:** `BuiltinAttributes.TeamId` (UInt, имя `teamId`), `AttrSets` (`PositionHeadingTeam`), `SimContext.SpatialHash`, `SimulationWorld.Build` (вызов валидатора рядом с `RepeatCountValidator`), `M3DDemoTools.PassLibraryPaths`.

**Изменить вне хэша (только для замера S10, полный список в ТЗ P1 §6):** `SimulationWorld` — сериализованное `renderParticles = true` и публичное свойство; при `false` `Update` пропускает `Execute` у `PrimitiveParticleBinder` (переключается в рантайме, без Rebuild). `EffectAsset` и `EffectAssetEditor` не трогаем: инспектор ассета частичные поля не рисует, а на устройстве инспектора нет. Плюс пробник: `HashProbeControls` (OnGUI-кнопки «хэш вкл/выкл», «рендер вкл/выкл», FPS) и меню `Tools/M3D/Create Spatial Hash Probe` (ассеты `HashProbe_30k`, `HashProbe_100k`). Поведение по умолчанию не меняется; существующие smoke-тесты проходят без правок.

**Кернелы:**
1. `HashClear`: `cellCount[c] = 0`.
2. `HashCount`: `cell = CellOf(pos)`, `cellOf[i] = cell`. При `wrap = true` индекс ячейки берётся **по модулю** `res` (`((c % res) + res) % res`): после `BoxBounds` Wrap позиция из-за округления может оказаться ровно на верхней границе (индекс `res`), и клампить её в последнюю ячейку нельзя. При `wrap = false` — clamp в `[0, res-1]`. `InterlockedAdd(cellCount[cell], 1)`. Без groupshared-хэша (оптимизация Rivalry нужна при ~450k, у нас не нужна).
3. `HashScanBlocks` / `HashScanBlockSums` / `HashAddOffsets`: порт блочного скана Rivalry (`GridUtils.compute`, блок 256). `HashAddOffsets` пишет и `cellStart`, и `cellCursor` (убирает `InitCellCounters`).
4. `HashScatter`: `slot = InterlockedAdd(cellCursor[cell], 1)`; пишет в `slot` сразу `sortedIndex`, `sortedPos`, `sortedDir`, `sortedTeam` (убирает отдельный `ReorderAgents`).

Итого 6 диспатчей.

**Валидатор (Build, `InvalidOperationException`):** не более одного включённого builder; builder выше всех потребителей; при `wrap = true` обязателен включённый `BoxBounds` в режиме Wrap с теми же `center/extents` по XZ (допуск 1e-3), иначе **ошибка** (без заворота в мире хэш завернёт частицы сам, и появятся фантомные соседи через шов; корректного сценария нет); при `wrap = false` включённый `BoxBounds`, если он есть, должен быть Bounce с теми же границами, иначе ошибка; инварианты сетки из §2.2 (`res >= 3` только при `wrap`, `res.x * res.y <= 65536`, `maxRadius <= size/2` при `wrap`); максимум радиусов команд `<= cell * (1 + 1e-5)` (проверяется, когда есть `teams`, то есть начиная с P4). **Предупреждение** (не ошибка): `wrap = false` и в эффекте нет `BoxBounds` — частицы могут вылететь за сетку и склеиться в краевых ячейках через clamp. Ошибкой не делаем: область могут ограничивать другие пассы (`SphereCollider`, `PlaneCollider`), которые валидатор проверить не может.

`RepeatCount`: потребители хэша и билдер **не переопределяют** `RepeatCount` (остаётся 1). Блоков повторения в проекте нет: `RepeatCount` повторяет один пасс подряд. Для `+=`-аккумулятора силы это значило бы двойной учёт, для билдера — лишнюю работу. Отдельного валидатора не нужно, достаточно контракт-теста `RepeatCount == 1`.

**Тесты (GPU EditMode, шаблон `PhysarumSteerGpuTests`, свой `ParticleSet` и `SimContext`):**
- Равенство множеств с CPU counting sort: для каждой ячейки множество `sortedIndex` в диапазоне `[cellStart, cellStart+cellCount)` равно эталонному. Порядок внутри ячейки **не** сравнивать (атомарный scatter недетерминирован).
- Снимок: `sortedPos[k] == position[sortedIndex[k]]`, то же для dir/team.
- Сумма `cellCount == context.Particles.Count`; `cellStart` монотонен. `Count == 0`: `Execute` не падает.
- Частицы за границей (`wrap = false`: clamp) и ровно на верхней границе (`wrap = true`: по модулю, частица в ячейке 0, а не в последней) и на следующем представимом числе ниже нижней границы (зеркальный случай: последняя ячейка, а не нулевая; `-1e-7` при координатах порядка 45 не представимо, брать `BitDecrement` или локальные координаты); ячейки с 0 и с многими частицами.
- Контракт: `RepeatCount == 1` у билдера.
- Размер сетки >256 ячеек (многоблочный скан) и ровно 256, 257.
- Тор: `ComputeGrid` даёт `cell >= minCellSize * (1 - 1e-5)` и `res*cell ≈ size` (относительный допуск `1e-5`, тот же, что в проверке радиуса; строгое сравнение упадёт на подобранных числах). Мир меньше `3*minCellSize` при `wrap = true`: `Initialize` бросает; при `wrap = false` работает. Сетка > 65536 ячеек: `Initialize` бросает.
- Валидатор: дубль builder, неверный порядок, расхождение с Wrap-`BoxBounds`.
- Контракт-тест имён кернелов (рефлексия, как в существующих).

**Гейт:** все тесты зелёные; ревью Claude кода кернелов построчно. После ревью владелец прогоняет на S10 замер одного хэша: пресет с `BuildSpatialHash` без силы на 30k и 100k частиц, FPS против того же пресета без хэша, **каждый вариант с рендером и с отключённым рендером частиц**. На 20–30k узким местом скорее окажется fill-rate, а не хэш; без разделения цифра о гипотезе ничего не скажет. Для отключения рендера и хэша служат кнопки `HashProbeControls` (см. «Изменить вне хэша»). Цифры S10 в этом плане (20–30k, ≥ 50 FPS) пока гипотезы, а не замеры; замер хэша — первая проверка гипотезы, до остальных фаз.

### P2. Отладка хэша без нового рендер-кода

- `HashCountsToFieldPass : FieldKernelPass`: пишет `cellCount` в объявленное скалярное поле, разрешение которого равно сетке хэша (валидатор: совпадение разрешения и области поля с сеткой).
- Показ: существующий `DebugFieldQuads`. Новых шейдеров и биндеров нет.
- Тест: поле равно CPU-гистограмме.

### P5. Сила соседей, steer, одно-командный пресет (три отдельных приёмки)

**5a** — [ADR-038](ADR/ADR-038-Boid-Neighbor-Force.md), [`todo-adr-034-p5a-neighbor-force.md`](last/todo-adr-034-p5a-neighbor-force.md). Где этот раздел короче ТЗ, делать по ТЗ. 5b и 5c в 5a не делать.

**5b** — [ADR-039](ADR/ADR-039-Team-Heading-Steer.md), [`todo-adr-034-p5b-team-heading-steer.md`](last/todo-adr-034-p5b-team-heading-steer.md). Где этот раздел короче ТЗ, делать по ТЗ. Пресет и Play в 5b не делать.

**Файлы:** `Assets/Shaders/GPU/Passes/BoidsPasses.compute`, `Assets/Scripts/Passes/BoidsPasses.cs`.

Приёмки идут по порядку, каждая со своим «принято» до начала следующей: **5a** сила + эталонные тесты; **5b** `TeamHeadingSteer` + тесты; **5c** пресет + Play-гейт.

- `BoidNeighborForcePass : ParticleKernelPass`, кернел `BoidNeighborForce`. `Reads`: Position, TeamId. `Writes`: Velocity (аккумуляция `+=`). Соседей читает **только** из снимка хэша. Параметры: `maxNeighbors` (по умолчанию 48). `SetParams` биндит хэш через уже существующий `PushParams` и команды через `BindBuffer`. `SetVector4` не добавлять.
- `TeamHeadingSteerPass : ParticleKernelPass`, кернел `TeamHeadingSteer`: как `HeadingSteer` (см. `DynamicsPasses.compute`), но `k = saturate(turn[team] * dt)`, `velocity = h * cruise[team]`. `HeadingSteer` не менять.
- Пресет `Assets/Effects/Boids_hash.asset`, меню `Tools/M3D/Create Boids Hash Effect`, одна команда, 10k частиц, `SimulationSpeed = 1`, Wrap `(0,0,0)`/`(45,0,45)`, `minCellSize = 3`. Цепочка из п. 2.1 без Noise/Touch. Стартовые числа из `Boids_Rivalry/Scripts/Configs/BoidGroupConfig.asset`: радиусы 3, веса sep/align/coh 1.2/0.8/0.6, cruise 6, turn 4. Поправить после первого Play.
- Регистрация compute в `PassLibraryPaths` и в сцене.

**Тесты (главные в плане):**
- **CPU-эталон O(N²)** (`BoidForceOracle` в тестах): N≈200 случайных частиц, 1–2 команды, `maxNeighbors = 0` (без капа): GPU `velocity` после `ClearVelocity`+силы равен эталону **с допуском, не на равенство**. Порядок слотов в ячейке недетерминирован (атомарный scatter), float-сложение не ассоциативно, поэтому суммы отличаются на уровне ошибки округления: относительный допуск (стартовое значение 1e-4, уточнить по первому прогону) плюс абсолютный пол. Чтобы тест не флакал: (1) конфигурации без почти полной компенсации `align`/`coh` (нормализация усиливает ошибку), (2) позиции с зазором от всех порогов радиусов и от `size/2` (иначе сосед по-разному попадает в расчёт на CPU и GPU), (3) фиксированный seed. Покрывает хэш, формулы и межкомандный множитель.
- **Тор:** две частицы по разные стороны шва `BoxBounds`; сила совпадает с эталоном через `minImage`.
- **`maxNeighbors = 0`** (без капа) отдельным тестом: именно на нём держится эталон, так что семантика «0 = без капа» проверяется явно, а не косвенно.
- **Счётчик срабатываний капа:** `BoidNeighborForcePass` имеет отладочный флаг `countCapHits` (по умолчанию `false`, при `false` атомика не выполняется). При `true` кернел делает `InterlockedAdd` в `uint[1]`-буфер пасса, когда частица остановилась на капе. Порядок внутри `Execute`, в одном command buffer: (1) `context.Cmd.SetBufferData` обнуляет счётчик в самом начале, (2) диспатч силы, (3) сразу после него `context.Cmd.RequestAsyncReadback`. Так каждое значение в колбэке относится ровно к одному кадру; задержка в 1–3 кадра влияет только на момент получения. Запрос из C# после `ExecuteCommandBuffer` не использовать. Каждый замер делится на `Count` своего кадра; пасс публикует `LastCapHitFraction` как скользящее среднее за окно (стартово 60 полученных замеров), а не одно значение. **Пока флаг выключен или не получено ни одного замера, свойство возвращает `-1` («не измерялось»), а не 0.** **Колбэк readback:** тихо выходит, ничего не добавляя в окно и не трогая буфер, если `request.hasError`, либо поколение пасса не совпало с запомненным при постановке запроса (счётчик поколения растёт в `Initialize`, `Dispose` **и `ResetCapHitWindow()`**; это покрывает Rebuild пресета, выход из Play, колбэк после `Dispose` и запрос, поставленный до сброса окна и вернувшийся после него: старый замер из периода до прогрева в окно не попадает, отдельного механизма не нужно), либо пасс уже освобождён. Частота запросов (однозначно): **один запрос на кадр**; если в полёте уже 4 и более запросов (число выбрано как собственное допущение, проверить на ревью 5a), замер этого кадра пропускается. При задержке readback 1–3 кадра окно в 60 замеров набирается примерно за 60–70 кадров. Окно считается по числу полученных замеров, а не кадров. Для гейта есть `ResetCapHitWindow()`: очищает окно и сбрасывает значение в `-1`. Тесты: `maxNeighbors = 0` даёт 0; `maxNeighbors = 1` в плотной конфигурации даёт долю около 1; `Dispose` с запросом в полёте не бросает исключений и не меняет окно; `ResetCapHitWindow()` при запросе в полёте не пускает старый замер в окно; при `false` свойство равно `-1` и счётчик не меняется; при `true` после замеров значение `>= 0`.
- **Кап:** при `maxNeighbors = 1` в плотной ячейке сила конечна (нет NaN), направление не смещено системно (статистический тест на симметричной конфигурации, допуск широкий). Стабильность набора от кадра к кадру тестом не гарантируется, см. риск «кап и дрожание».
- **Steer (5b):** `|heading| = 1`, `heading.y = 0`, `|velocity| = cruise[team]`; per-team различие скоростей. **Изолированная частица** (нет соседей, `force = 0`): `heading` не изменился, `|velocity| = cruise`. **Антипараллельная цель** (`desired = -heading`) при `k < 0.5` и при `k >= 0.5`: нет NaN, `|heading| = 1`, поведение как в §2.3. Масштаб силы (`force` и `1000*force`) даёт тот же `heading`. **Паритет с `HeadingSteer`:** при одной команде с теми же `turn` и `cruise` результат `TeamHeadingSteer` равен результату `HeadingSteer` на тех же входах (допуск `1e-6`), включая вырожденные: нулевая сила, нулевой `heading`, антипараллельная сила, сила с большой составляющей Y, `heading` с большой составляющей Y, `k = 1`.
- Контракт: имена кернелов, `RepeatCount == 1` у `BoidNeighborForcePass`; `Rebuild` пресета без `VisualEffect` (как `PhysarumWorldSmokeTests`).

**Чекпоинт 5a:** после зелёных тестов силы, **до `TeamHeadingSteer`**: ревью Claude и отдельное «принято».
**Чекпоинт 5b:** тесты steer зелёные, **до пресета**: «принято».
**До 5c:** тикет шести старых красных EditMode закрыт (см. §6). Гейт «весь EditMode зелёный» теперь означает 274/274 и ни одного нового красного.
**Гейт 5c:** Play `Boids_hash` через MCP (`editor_play`, `screenshot`, `get_performance_stats`): стая держит форму, нет NaN, нет шва на границе. Дрожание сил в плотных областях (риск капа) проверяется метрикой, а не на глаз: Play с `countCapHits = true`, записать `LastCapHitFraction` (скользящее среднее). Значение `-1` означает «не измерялось», и гейт 5c в этом случае **не пройден**. **Прогрев:** окно записывается после нескольких секунд Play (стартово 5 с), когда частицы разошлись из начальных дисков и плотность установилась; в начале прогрева вызвать `ResetCapHitWindow()`, а значение записывать после того, как набрано полное окно в 60 замеров. Стартовая гипотеза порога: менее 1% частиц, уточнить по первому замеру. Если доля выше и дрожание видно, лечить не вращением ячеек, а снижением плотности пресета или стабильным ключом (см. §5). ### P8. Допы из Rivalry (мелкие отдельные тикеты)

- **8a Энтропия:** атрибут `entropy` (Float1); `BoidNeighborForce` пишет `1 - |Σdir|/N` в том же цикле. `EntropyToValue` (или прямой выход в `value`) для палитры. Хаотичный доворот в `TeamHeadingSteer` пропорционально `entropy²` (параметр на команду `chaos`). Расширяет `TeamParams.motion.z`.
- **8b Noise/Touch без dt:** `NoiseAccumPass` и `TouchAccumPass`, аккумуляторы в `velocity` между силой и steer (юнит-направление или сила без dt, как в Rivalry). Существующие dt-пассы (`TouchForce`, curl) не использовать в этом окне (ADR-012).
- **8c Heatmap смешивания команд:** по аналогии с `ComputeCellMixingEntropy` Rivalry, результат в скалярное поле и показ через `DebugFieldQuads` (приём из P2). Не бесплатно: отдельный пасс проходит по частицам ячеек. Дешёвый вариант: счётчики по командам считать в `HashScatter` (`cellTeamCount[cell*8+team]`, один лишний `InterlockedAdd` на частицу), тогда heatmap это dispatch по ячейкам. Стоимость замерить, включать флагом.

## 6. Открытые детали (решу при ТЗ соответствующей фазы)

- Сливать ли P2 с P1. **Закрыто 2026-10-03: не сливать.** Замер S10: 100k ещё 60/60, цена хэша видна только на 500k (~6 FPS) и 1M (~4 FPS). P3 и P4 закрыты. P2 не отменена: отдельная фаза перед P5, на равномерном кубе пробника гистограмма плоская.
- Шесть старых красных EditMode — отдельный тикет, **закрыт** до начала 5c (полный EditMode 274/274 дважды подряд). Исходные причины: четыре `SimulationWorldDisabledPassInitializeTests` ждут предупреждение `PositionBuffer` от `VfxParticleBinder`, которого `SetupBinders` с ADR-031 не создаёт: поправить ожидание лога, саму проверку выключенного пасса не выкидывать. Два `PrimitiveParticleBinderTests` ищут по всему редактору живые `M3D_ParticleBillboard` и `M3D_ParticleBillboard_LUT`; чинить учёт чужих объектов, не ослаблять `Dispose`.
- Нужен ли `SetVector4` в базовом классе. **Закрыто в ТЗ 5a: не нужен.** Хватает `PushParams` и `BindBuffer`.
- Нужен ли `LutTextureUtility` или достаточно перегрузки конструктора.
