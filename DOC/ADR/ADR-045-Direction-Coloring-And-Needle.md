# ADR-045: Окраска частиц по направлению полёта и игольчатый билборд

**Статус:** предложено. «Принято» ставит владелец после C1 и после C2 отдельно.
**Дата:** 2026-10-10.
**Контекст:** M3D Framework, после [ADR-043](ADR-043-Team-Palette-Followups.md). Палитры команд: [ADR-041](ADR-041-Team-Palette.md). Источник идеи: проект `slon1/Boids_Rivalry`, шейдер `Assets/Shaders/BoidsInstanced.shader`.

## 1. Контекст

Сейчас цвет частицы считается так: пасс `HeadingToValue` пишет курс как угол (`value = atan2(h.z, h.x) / 2π + 0.5`), шейдер берёт `value` и выбирает цвет из LUT (строка команды). ADR-043 A4 убрал крап у пресета двух стай, но владелец сказал, что цвета выглядят хуже, чем в старом проекте, и просит окраску из него.

Старый шейдер (`BoidsInstanced.shader`, 2D, ось Y вверх), суть:

- в вершинном шейдере из скорости берётся направление `dir = normalize(vel)`;
- параметр смешивания зависит только от вертикальной компоненты: `t = dir.y * 0.5 + 0.5`;
- цвет `lerp(colorLow[team], colorHigh[team], t) * _MainColor`;
- квад вытянут вдоль скорости (ширина `boidScale * 0.5`, длина `boidScale * 1.5`, примерно 1:3), во фрагменте круговой спад `pow(saturate(1 - length(uv)), 2) * _Glow`, смешивание `Blend One One`, `ZWrite Off`, `_Glow = 0.2`.

Свойства схемы, важные для нас:

- **Непрерывность.** `t` монотонно зависит от вертикальной компоненты, разрыва нет. Проблема с курсом −x из A4 исчезает по построению.
- **Горизонтальный полёт даёт середину палитры.** Влево и вправо одинаковый цвет, различаются только летящие вверх и вниз.
- **Модуль скорости на цвет не влияет.**

## 2. Решение

Решение принято по ответам владельца 2026-10-10: схему можно применить ко **всем** эффектам с частицами в режиме `Primitive`, старый способ сохранять не обязательно; вертикаль экрана это мировая **Z**; цвета команд заданы ниже; форма иглы как в старом проекте.

### 2.1. C1: цвет по направлению (эта фаза подробная)

1. **Источник направления.** Вершинный шейдер читает буфер `velocity` (`BuiltinAttributes.Velocity`): `dir = normalize(velocity)`, `value = dot(dir, axis) * 0.5 + 0.5`. Для нулевой скорости (длина² меньше `1e-12`) `value = 0.5`. Ось `axis` нормируется в C# (нулевая ось заменяется на `(0, 0, 1)`).
2. **Дальше всё как есть.** `value` идёт в существующую цепочку: `saturate(value * scale)`, LUT, строка команды (A1–A3). Хелпер `ParticlePaletteColor` **не меняется**. Двухцветный переход `lerp(low, high, t)` это двухключевой градиент в строке LUT команды.
3. **Переключатель.** В `EffectAsset` два новых сериализуемых поля:
   - `ParticleColorSource particleColorSource` (`Value` = прежний путь через атрибут `value`, `Direction` = новый), **по умолчанию `Direction`**;
   - `Vector3 particleColorAxis`, по умолчанию `(0, 0, 1)`.
   Для существующих ассетов, у которых поля нет в файле, действует значение по умолчанию, так что **вид всех эффектов меняется без правки ассетов**.
4. **Откат.** Если выбран `Direction`, но у частиц нет атрибута `velocity` (источники без пассов), биндер молча переходит на прежнее поведение (`Value`, если есть `value`, иначе плоский цвет) и выставляет `UsesDirectionColor = false`.
5. **Масштаб значения.** В режиме `Direction` `_Scale` принудительно 1 (поле `particleValueScale` настроено под палитры скорости и исказило бы направление).
6. **Одиночные эффекты.** Без команд LUT собирается из `particleGradient` эффекта (как сейчас для `value`), t идёт по направлению. Градиенты существующих эффектов (например, `DefaultFireGradient` у `Boids_hash`) остаются, их можно править отдельно.
7. **Пресет двух стай.** Градиенты команд заменяются двухключевыми (в линейных значениях, как раньше):
   - команда 0: `colorLow` = красный `(1, 0, 0)`, `colorHigh` = синий `(0, 0.15, 1)`;
   - команда 1: `colorLow` = жёлтый `(0.98, 1, 0)`, `colorHigh` = зелёный `(0.02, 1, 0)`.
   Названия команд меняются на нейтральные («RedBlue», «YellowGreen»), «Fire/Ice» в пресете больше не отражает цвет.
8. **Режим `Vfx`.** Не затрагивается: VFX Graph красится своим графом.
9. **Пассы `HeadingToValue`** в готовых пресетах остаются в цепочках и теперь дают лишнюю работу (30 000 частиц, ничтожно). Чистка цепочек отложена в Techdebt.
10. **Стадия.** Цвет по-прежнему считается в вершине (A2), буфер скорости читается в вершинной стадии, 6 раз на частицу, как и `value`.

### 2.2. C2: игла (описана, детализируется после C1)

Решение фиксируется тут, чтобы C1 не противоречил C2. ТЗ C2 будет отдельным документом после «принято» C1.

- Квад вытягивается вдоль `velocity`, спроецированной на плоскость камеры (вектор `right`/`up` из `UNITY_MATRIX_I_V`), с соотношением сторон около 3:1; ширина и длина задаются в эффекте.
- Фрагмент: `needle = pow(saturate(1 - length(uv * 2 - 1)), 2)`, `rgb = color.rgb * needle * glow`; `glow` по умолчанию 0,2.
- Смешивание аддитивное `Blend One One`, `ZWrite Off`. Состояние смешивания задаётся свойствами материала (`_SrcBlend`, `_DstBlend`), которые выставляет биндер; прежний режим (alpha blend, квадрат) остаётся для `Value` и для эффектов без скорости.
- `_Color.rgb` умножает цвет (аналог `_MainColor`).
- Параметры в `EffectAsset` с значениями по умолчанию по старому проекту.

### 2.3. Что не меняется

`HeadingToValue` и его ядро, `ParticlePaletteColor` и его тесты, A3 (перепекание LUT команд), цепочки `Boids_hash` и пресет симуляции, VFX-путь.

## 3. Отвергнутые варианты

- **Новое compute-ядро `HeadingAxisToValue`, пишущее `value`.** Лишний пасс и буфер, а скорость в вершинном шейдере понадобится C2 так или иначе (вытягивание квада). Два чтения одного направления заменяются одним.
- **Удалить путь `Value`.** Он нужен эффектам без скорости и тестам A1–A3. Удаление перепишет много тестов без выигрыша. Остаётся как запасной.
- **Ось Y мира.** Камера пресетов смотрит сверху вдоль −Y, вертикаль экрана это Z. Ось задана параметром, значение по умолчанию `(0, 0, 1)`.
- **Включать новую окраску по эффектам вручную (по умолчанию выключено).** Владелец хочет её для всех; значение по умолчанию `Direction` даёт это без правки ассетов. Цена: тесты, косвенно зависящие от вида по умолчанию, придётся проверить.

## 4. Последствия

- Вид **всех** эффектов в режиме `Primitive` с атрибутом `velocity` меняется. Градиенты `particleGradient` остаются, но теперь их параметр это вертикальная компонента направления, а не значение пасса. Эффекты, цвет которых раньше нёс смысл (скорость в Physarum), его теряют; владелец это принял.
- Цвет не зависит от горизонтального направления. На первой секунде обе стаи в пресете двух стай летят по X и окрашены в середины своих палитр (`lerp(red, blue, 0.5)` и `lerp(yellow, green, 0.5)`).
- Циклические градиенты A4 и их тест теряют смысл для пресета двух стай и заменяются тестом двухключевых палитр.
- Один дополнительный буфер в вершинной стадии. Цена на S10 не измерена; замер по протоколу под нагрузкой (см. ADR-043 A2).
- `particleValueScale` в режиме `Direction` не действует.

## 5. Тесты

- `DirectionToValue` на compute-кернеле: ось Z: скорость вверх даёт 1, вниз 0, вдоль X 0,5, нулевая скорость 0,5, диагональ даёт `0,5 + 0,5·cos 45°`, масштаб скорости не влияет.
- Стенд рендера (новый файл, файл A2 не меняется): квады со скоростями вверх, вниз, вбок для двух команд, центр совпадает с хелпером при `value` из `DirectionToValue`.
- Биндер: режим `Direction` связывает `_Velocities`, выставляет `_UseDirection`, откат без `velocity`, прежние конструкторы остаются в режиме `Value`, нормировка и подстановка оси.
- Пресет двух стай: двухключевые градиенты (цвета, расстояние между командами, расстояние до фона, насыщенность и яркость как в A4).

## 6. Открытые вопросы

- Нужно ли будет подкрутить `particleGradient` существующих эффектов под вертикальную схему (владелец решит после Play).
- Значения ширины, длины и `glow` для C2 в разных эффектах.
- Как аддитивность сказывается на читаемости структуры стай в B3 (поэтому C2 идёт после B3).

## 7. Результат

C1 сделан, статус остаётся «предложено, C1 на проверке». C2 не начат.

Цвет в вершине берётся из `velocity` через `DirectionToValue`. По умолчанию `ParticleColorSource.Direction` и ось `(0, 0, 1)`. Нет буфера скорости — откат на прежний путь `value` или плоский цвет. Пресет двух стай на месте: команды RedBlue и YellowGreen, два ключа. Меню не запускалось. Паритет создателя на временном ассете: имена и ключи совпали, временный файл удалён.

Шаг созданного буфера `velocity` в Play на `Boids_Hash`: 12 байт. Тот же шаг проверяет тест биндера.

EditMode до правок 320/320, после 328/328. Новые тесты: направление, биндер, стенд. Существующие тесты не правились, кроме теста пресета двух стай. Красный цикл биндера: на заглушке 4 из 6 красные. Контроль стенда: подмена оси на `(0, 1, 0)` покрасила стенд, правка возвращена.

Скорость есть у всех эффектов с пассом, который читает или пишет атрибут `velocity` (рои, хэш, силы, Physarum, пружина к rest). Нет скорости, цвет не меняется: `Fluid2D*`, `Gray-Scott`, `Gray-Scott 1`, `TwistedCube` (только `Twist` по позиции). `Boids_hash200k` в этот список входит и в коммит не входит.

Play, пауза на пороге. На 1 с у двух стай мода пикселей левой стаи `(184, 79, 191)` против ожидания `(188, 77, 188)`, отклонение (−4, +2, +3), внутри ±4. Правая `(196, 255, 0)` против `(188, 255, 0)`, по красному +8, за допуском: соседние бины 187 и 179, стая на 1 с не строго горизонтальна. На 15 с внутри стай виден переход красный/жёлтый против синего/зелёного; единого «низ кадра = low» нет, стаи летят в разные стороны. `Boids_Hash`: почти чёрные частицы видны, на 15 с они собраны в тёмные головы нескольких стай; пикселей с каналом ниже 45 около 5% кадра вне фона, потому что яркий конец градиента занимает больше пикселей. Градиент в C1 не менялся, решение за владельцем (C1b). Physarum: частицы оранжево-коричневые вдоль следа, вертикальный переход палитры на кадре не читается. Отдельной сцены жидкости нет.

Вопрос 4. У пресетов со `TeamHeadingSteer` и у `HeadingSteer` буфер к отрисовке — это `heading × cruise`. `PhysarumSteer` тоже пишет скорость из курса (`moveSpeed`). `Boids_mk1` в снимки не входил: там нет steer, в буфере вектор силы.
