# ADR-048: `walkMode = 1` по умолчанию, `walk 0` и `walk 2` заморожены

**Статус:** принято владельцем 2026-10-19. Раздел «Результат» заполняет Grok по итогам F3c.
**Дата:** 2026-10-19.
**Контекст:** M3D Framework, ветка `feature/reynolds-boids`, план [plan-P7-perf-200k.md](../plan-P7-perf-200k.md). Связано с [ADR-047](ADR-047-Sorted-Order-Neighbor-Walk.md) (три режима обхода и замеры F3 на S10, §6), [ADR-046](ADR-046-Perf-Target-And-P6-Closure.md) (цель 200 000, метрика, правила замеров). ТЗ миграции: `DOC/last/todo-F3c-walk1-default-and-cleanup.md`.

## 1. Контекст

Фаза F3-measure2 закрыта замерами на S10 (каталог `DOC/MEASURE/ff2a194-331eee0d/`, сборка `ff2a194`, `dirty=1`, `powersave=0`, 1520×720, камера 46, Mali-G76). Три режима обхода соседей лежат в одной сборке: `walk 0` (прежний кернел), `walk 1` (поток на слот, объединённые диапазоны, ADR-047 §2), `walk 2` (то же плюс упакованная запись 16 байт, ADR-047 §7). Числа ниже взяты из ADR-047 §6.

| Показатель | `walk 0` | `walk 1` | `walk 2` |
|---|---:|---:|---:|
| S200 (200 000), профиль B, циклы на частицу | 139,1 | 40,2–41,2 | 41,4–41,6 |
| S200, расходящиеся / частичные чтения | 0,884 / 0,960 | 0,849 / 0,936 | 0,850–0,855 / 0,944–0,946 |
| 400k, кадр B / A, мс | 90,1 / 97,3 | 21,7 / 29,2–29,5 | 26,0 / 33,9–34,2 |
| 400k, профиль B, циклы на частицу | нет профиля | 37,5–37,8 | 45,1–45,3 |
| 600k, кадр B, мс | нет | 35,6 | 43,8 |
| 800k, кадр B, мс | нет | 51,6 | 62,1 |

1. **`walk 0` проигрывает в 3–4 раза** на 400k и в 3,4 раза по циклам на S200. Выигрыш `walk 1` держится при двух командах (64,9 мс против 68,4 мс на одной) и при насыщенном капе (`capfrac` 0,976–0,998 на всех проверенных сценах, от режима обхода не зависит).
2. **`walk 2` не быстрее `walk 1` ни в одной точке.** На 400k кадр B длиннее на 4,3 мс (+20%), циклы на +3,03 М; на 600k и 800k разрыв 8,2 и 10,5 мс. На S200 и на плотных 100 000 оба режима стоят на vsync, разница в циклах на S200 (около 0,15 М) в пределах шума.
3. **Причина — рассыпка, не обход.** Повтор цепочки хэша на 400k (`hashrep` 1/4/8): одна цепочка стоит 5,99 мс при `walk 1` и 10,7 мс при `walk 2`, добавка упаковки 4,7 мс. Остаток кадра (в основном обход) у `walk 2` легче на 0,6 мс, у порога шума 0,5 мс. После F3a потоки читают подряд идущие диапазоны слотов, поэтому склейка трёх потоков в один ничего не экономит: `beats` на частицу выросли с 25,0 до 26,6, расходимость не изменилась. Streamline диспатчи по именам не разделил, вывод держится на `hashrep`.
4. **Тепловой режим (Замер 4).** S200, режим A, десять минут, на зарядке: критерий «все окна ≤ 16,9 мс» не выполнен ни для `walk 1` (18,37 мс среднее, держит до окна 29, затем падение частоты с 702 до 433 МГц около 540 с, кадр около 26 мс, то есть около 38 FPS), ни для `walk 2` (18,13 мс). Прогоны шли при разном заряде (7→4% и 20→17%), поэтому сравнивать по ним `walk 1` и `walk 2` нельзя.

**Ограничения данных:** все замеры на сборке с `dirty=1`; частота GPU в коротких сериях не снималась (`activeMHz` в Streamline это циклы на время окна, не частота); профиль режима A на S200 в циклах не снят; прямого сравнения `walk 0` с базой `6ac1cad` на 100 000 (критерий 5 из plan-P7 §4) не было.

## 2. Решение

1. **По умолчанию `walkMode = 1`.** Значение задаётся в коде: `[SerializeField] private int walkMode = 1;` в `BoidNeighborForcePass`. Четыре ассета с явным `walkMode: 0` (`Boids_hash400k`, `Boids_hash400k_2teams`, `Boids_hash600k`, `Boids_hash800k`) переводятся на `walkMode: 1`. Шесть ассетов без поля (`Boids_hash`, `Boids_hash100k`, `Boids_hash100k_x4`, `Boids_hash200k`, `Boids_hash30k`, `Boids_hash_2teams`) берут значение из кода; это проверяет EditMode-тест (F3c, часть А).
2. **`walk 0` заморожен.** Кернел `BoidNeighborForce` и его тесты остаются: это эталон для тестов (оракул, побитовая решётка `GpuBitExact`), цель отката при нарушении предпосылки по радиусу (ADR-047 §2.5) и режим для A/B одним APK (`-m3d_walk 0`). Кернел не оптимизируется и не правится.
3. **`walk 2` заморожен.** Остаются `BoidNeighborForceSortedPacked`, `HashScatterPacked`, буфер `SortedPacked`, флаги `PackedRequested` и `PackedWritten`, режим `-m3d_walk 2`, тесты F3b. В пресеты `walk 2` не ставится, кандидатом по умолчанию не считается, дефект стоимости рассыпки не чинится. При `walk 0` и `walk 1` упаковка не пишется и ничего не стоит (проверено сторожевым значением в F3b).
4. **Что значит «заморожен».** Нет правок кернелов, никаких оптимизаций и новых функций. Допустимы только исправления ошибок корректности (с отдельным ТЗ) и механические правки, без которых проект не собирается. Тесты замороженных режимов остаются в обычном EditMode. Удаление кода не входит в это решение.
5. **Судьба `walk 2` и `walk 0`.**
   - **Тег.** В конце F3c на коммит, где `walk 2` заморожен (коммит Б), ставится аннотированный тег `walk2-frozen` и отправляется в `origin`. По нему режим можно вернуть одной командой.
   - **Удаление `walk 2`.** Кандидат на удаление после отчёта F5, отдельным ТЗ и отдельным коммитом: убрать `BoidNeighborForceSortedPacked`, `HashScatterPacked`, буфер `SortedPacked`, флаги `PackedRequested` и `PackedWritten`, ветку `walkMode == 2`, тесты F3b, документы. Если к отчёту F5 `walk 2` не понадобился, удаляем. Решение остаётся за владельцем.
   - **Пересмотр вместо удаления.** Только по новому профилю, который покажет, что чтение записи соседа стало узким местом, и только отдельным ТЗ с замыслом, при котором упаковка не добавляет случайную запись на частицу.
   - **`walk 0` остаётся**, пока в проекте нет другого эталона для тестов и другой цели отката по радиусу. Его удаление требует отдельного решения и переписывания тестов (оракул, `GpuBitExact`).
   - **Разрешение экрана не причина сохранять режимы.** Кернелы обхода это compute-диспатчи: их стоимость зависит от `N`, плотности, капа и кэша, а не от пикселей. В базе P7 режим B на 720 / 1080 / 1440 стоил 17,80 / 18,58 / 20,46 мс, рост даёт рамка URP. Для `walk 1` и `walk 2` на 1440p замеров нет; при желании проверяется одной серией режима B.
6. **Переключатель `-m3d_walk <0|1|2>` и поля `walk=` / `walkeff=` в `M3D_PERF` остаются без изменений.** Правило «walk fallback» в `summarize.ps1` сохраняется: оно защищает `walk 1` по умолчанию от тихого отката.

## 3. Отвергнутые варианты

- **Оставить `walk 0` по умолчанию.** Самый медленный режим стоял бы по умолчанию во всех пресетах без явного поля, в том числе в S200.
- **`walk 2` по умолчанию или для больших `N`.** Медленнее `walk 1` на каждой точке (400k, 600k, 800k), плюс 16 байт на частицу памяти и дополнительные флаги и откаты, при выигрыше обхода не больше шума.
- **Удалить `walk 0` и `walk 2` сейчас.** Теряется эталон тестов и A/B в одном APK. Владелец решил заморозить, а не удалять.
- **Оставить `walk 2` на случай высокого разрешения (4K).** Разрешение не влияет на стоимость compute-обхода (см. §2, п. 5); других данных в пользу `walk 2` нет.
- **Только значение в ассетах, без изменения кода.** Шесть ассетов не содержат поля, и любой новый ассет получил бы `walk 0`. Источником истины становится код, ассеты дублируют его явно только там, где поле уже было.

## 4. Последствия

- Пасс без явного `-m3d_walk` теперь исполняет `walk 1`. **Правило для замеров:** для строк `DONE`, снятых на сборках до коммита F3c без `-m3d_walk`, `walk` по умолчанию был 0 (для четырёх ассетов 400k–800k явно, для остальных из кода); источник истины — поле `walk=` строки `DONE`. После F3c без `-m3d_walk` это 1.
- **Риск тихого отката.** При `walk 1` и ячейке меньше максимального радиуса пасс один раз предупреждает и исполняет `walk 0`, то есть в 3–4 раза медленнее. Теперь это затрагивает любой пресет по умолчанию. Защита: предупреждение, `walkeff` в логе, отметка «walk fallback» в сводке и новый EditMode-тест на предпосылку для всех пресетов Boids.
- Раздел «Вопрос владельцу» в ADR-047 §6 закрыт этим ADR. Статус ADR-047: часть про `walk 1` (§2.1–2.6) принята; часть про `walk 2` (§2.7, §7) заморожена и рабочим режимом не принята.
- **Новая база для P7.** Профиль B на S200 при `walk 1`: 40,2–41,2 цикла на частицу (8,04–8,25 М циклов на кадр), против 139,1 у `walk 0` на той же сцене. Бюджет M2 из plan-P7 для режима «сила без рендера» (около 45–58 циклов на частицу) в этом режиме выполнен. Это не означает достижения M2: режим A на S200 в циклах не снят, тепловой режим не выдержан (п. 1.4). Достижение M1 и M2 фиксирует отчёт F5. Замер на чистом дереве (`dirty=0`) после F3c станет базой «после F3» (см. ТЗ).
- Остаётся открытым и переходит в F5 и техдолг: узкое место обхода соседей (около 24 из 34,5 циклов на частицу по двум размерам S200 и 400k), хэш (около 10 циклов на частицу), цена рендера (разность A−B: 7,8 / 12,0 / 15,9 мс на 400k / 600k / 800k), повтор теплового замера при заряде ≥ 50%.

## 5. Критерии приёмки F3c

1. EditMode зелёный, число тестов до и после записано, прежние числовые ожидания не менялись.
2. `git diff` по `Assets/**/*.compute` пуст.
3. Все десять эффектов Boids загружаются с `WalkMode == 1` (тест), предпосылка по радиусу выполнена у всех.
4. Play без `-m3d_walk`: `walk=1`, `walkeff=1`, предупреждений об откате нет; вид `Boids_Hash` и `Boids_Hash_2Teams` совпадает с видом при `walk 0`.
5. Документы не содержат утверждения «`walkMode` 0 по умолчанию» (кроме исторических записей с датой).
6. Тег `walk2-frozen` создан на коммите Б и отправлен в `origin`, хеш записан в §6.

## 6. Результат

Сделано 2026-10-19.

Коммит А `b6ef2fd43249567e219f05e98884197c62f4f3d5`: поле `walkMode = 1`, четыре ассета (`Boids_hash400k`, `Boids_hash400k_2teams`, `Boids_hash600k`, `Boids_hash800k`) на `walkMode: 1`, тест `BoidsHashPresetsWalkDefaultTests`. Коммит Б — эта запись документов. Аннотированный тег `walk2-frozen` стоит на коммите Б. Хеш тега в этот файл не вписан: запись хеша внутрь того же коммита меняет хеш. Его даёт `git rev-parse walk2-frozen`.

EditMode до правок А1: 376 прошло, 0 упало. После коммита А: 377 прошло, 0 упало. Новый тест `EveryNeighborForcePreset_IsWalk1_AndFitsTheCell`: десять эффектов, у каждого `WalkMode == 1` и предпосылка радиуса через `TeamRadiusPlayCheck`.
