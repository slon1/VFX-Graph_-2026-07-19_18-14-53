# ADR-058: полевая сила соседей (дальнее поле на хэше текселя)

**Статус:** предложен (2026-11-02), пересмотрен 2026-11-03 (вторая редакция). Принятие или отклонение ставит владелец после гейта P8.1, в этот файл вносится отдельным разделом «Результат».
**Дата:** 2026-11-02, редакция 2026-11-03.
**Контекст:** M3D Framework. Сила соседей: [ADR-038](ADR-038-Boid-Neighbor-Force.md). Обход по отсортированному снимку: [ADR-047](ADR-047-Sorted-Order-Neighbor-Walk.md). Кап: [ADR-052](ADR-052-Accepted-Neighbor-Cap.md). Спатиальный хэш: [ADR-034](ADR-034-Spatial-Hash-And-Teams.md). Генерик P2G: [ADR-002](ADR-002-Generic-P2G-Scatter.md), [ADR-005](ADR-005-Presence-Density-P2G-Scatter.md). План: [`plan-P8-field-neighbors.md`](../plan-P8-field-neighbors.md). Модель: `DOC/MEASURE/p8-field-model/`.

## Что изменилось во второй редакции

1. Цель 400 000 частиц, две стаи, не ниже 30 FPS в начале прогона, и устранение взаимного проникновения стай (решение владельца 2026-11-03). Прежние 128 м и 500k сняты.
2. Основной вариант: **лёгкий, без окна из центроидов**. Хэш с ячейкой равной текселю поля (R/t=3), сбор поля gather-ом или скаттером (A/B в микробенче), свёртка по диску, чтение 2–3 билинейных выборок. Окно 5×5 вынесено в эскалацию (§5).
3. Каналы сумм позиций убраны: CIC сохраняет первый момент.
4. Обновление поля раз в K кадров и, возможно, интерполяция между версиями поля.
5. Новая сцена P400c; пресет `Boids_hash_2teams` пересоздан с R=3.
6. Бюджет пересчитан под 400k (§1).

## 1. Зачем

Цикл по соседям в `BoidNeighborForcePass` доминирует в кадре и дорожает с капом линейно (F5.3, S200: 6,99 / 18,92 / 28,96 мс за точку обхода при капе 48 / 128 / 192; в циклах на частицу 23,60 и 99,90 из 41,35 и 126,79). Кап обрывает обход на первых клетках в порядке `start = i % 9`, и стаи проходят друг сквозь друга. В CPU-модели с рецептом `Boids_hash` (R=3, веса 1,2 / 0,8 / 0,6, чужие ×4, 1500 + 1500 частиц) контакт между стаями на t=5 с без капа 5,2% (чужие 0,34%), при капе 48 62–68% (21–23%). Кап 192 только на separation даёт 29%. Владелец: кап 192 не показатель, стаи проникали и при нём.

Сила одна и та же на GPU и в модели: `F = sep/sepN · wS + unit(Σ headings) · wA + unit(mean displacement) · wC`, alignment и cohesion только по своей команде, separation по всем с множителем чужих.

**Бюджет (400k, 30 FPS).** 33,3 мс при 700 МГц это около 23,3 млн циклов, то есть около 58 циклов на частицу. Рендер около 13,7 (замер 3, разность A−B 7,8 мс на 400k), остальной кадр без силы 17,75 (хэш около 10). На силу остаётся **около 27 циклов на частицу**; сегодня обход капа 48 стоит 23,60. Цель: цена не выше капа 48, без его пересечения стай. Троттлинг не учитывается (решение владельца).

## 2. Решение

Периодический мир (`wrap = 1`). Параметры для `R = 3`: тексель поля `t = R/3 = 1 м`, радиус свёртки R (диск из 25 смещений при `d < R`; 29 при `d ≤ R`, для потенциала разницы нет, так как `ψ(R)=0`; для счётчиков граница фиксируется одинаково в модели и на GPU). Все три радиуса равны R у обеих команд; это проверяет валидатор поле-пути. Команд ровно две.

### 2.1. Данные за кадр обновления

1. **Хэш с ячейкой `t`.** `BuildSpatialHashPass` с `minCellSize = t`. Центры текселей поля лежат в нижних углах ячеек хэша: тексель `i` стоит в `origin + i·t`. Тогда четыре тексель частицы это углы её ячейки. Ограничение: `MaxCells` = 65 536, то есть **мир до 256 м** при `t = 1 м`.
2. **Сбор поля (способ выбирается микробенчем P8.1-А по полному кадру):**
   - **gather:** поток на тексель читает диапазоны четырёх ячеек вокруг своего угла (по строкам индекс `y·Res.x + x`, значит два непрерывных диапазона; на шве тора диапазон разбивается), считает билинейные (CIC) веса каждой частицы и пишет на команду `N`, `Hx`, `Hz`. Без атомиков, детерминированно. Каждая частица читается четыре раза за кадр (около 32 МБ на 400k);
   - **скаттер:** для каждой частицы четыре угла CIC в `uint`-накопитель с фиксированной точкой, как в [ADR-002](ADR-002-Generic-P2G-Scatter.md), три канала на частицу (до 12 атомиков на частицу). **Хэш не нужен**, а он стоит около 10 циклов на частицу.
   
   Сравнивать нужно полные кадры «сила без рендера»: победа скаттера по хэшу может перекрыть его проигрыш по атомикам.
3. **Свёртка поля** (поток на тексель `c`, смещения `o` в диске радиуса R):
   - `A_g(c) = Σ H_g(c+o)` (вектор), `Ng(c) = Σ N_g(c+o)`, `Ntot(c) = Σ (N_0+N_1)(c+o)`, `K_g(c) = Σ N_g(c+o)·(o·t)` (вектор). **Суммы позиций не нужны:** CIC сохраняет первый момент (`Σ w_k·c_k = p`), поэтому `K` из `N` по центрам текселей точен, кроме границы диска, где у обхода тоже жёсткая отсечка;
   - потенциал `W_g(c) = Σ N_g(c+o)·ψ(|o·t|)`, где `ψ(d) = ½·ln((max(d, r0)² + ε) / (R² + ε))`, `ε = 0,001` (как в ADR-038), `r0 = t`; внутри `r0` ядро плоское;
   - `Φ_a(c) = Σ_g m(a,g)·W_g(c)`, `m(a,g) = 1` для своей команды, иначе `interGroupSeparationMultiplier` своей команды;
   - градиент `G_a(c)`: центральная разность `Φ_a` по x и по z, делённая на `2t`.
   
   Каналов на тексель шесть (`N`, `Hx`, `Hz` на команду). Цена по площади: 50 176 текселей × 25 тапов × 6 каналов около 19 чтений на частицу при 400k, это большая часть бюджета (§4).
4. **Обновление раз в K кадров** (`K ∈ {1, 2, 3}`, параметр пресета; `ShouldDispatch` в пассах хэша, сбора и свёртки). Чтение силы идёт каждый кадр. Необязательно: **два буфера поля и линейная смесь предыдущей и текущей версий по фазе внутри интервала** (вторая выборка на частицу). Гипотеза: снимает ступеньки силы на кадрах обновления (§3). **Оговорка ([ADR-059](ADR-059-P8-1-0-Scene-Baseline-Model-Checks.md) §2.3):** смесь показывает версию, устаревшую в среднем на K кадров, то есть платит запаздыванием; выигрыш проверяет модель.

### 2.2. Сила (поток на частицу, команда `a`, запись `velocity[i] += float3(F.x, 0, F.z)`)

- Четыре угла дальнего текселя с теми же CIC-весами `w_k`, что у сбора: `Gs = Σ w_k·G_a(c_k)`; `Ns = Σ w_k·Ntot(c_k) − 1`; `As = Σ w_k·A_a(c_k) − h_i`; `Ng = Σ w_k·Ng_a(c_k) − 1`; `Ks = Σ w_k·(K_a(c_k) + Ng_a(c_k)·(центр(c_k) − p_i))`.
- `F_sep = Gs / Ns · wS` при `Ns > 0,001`; `F_align = unit(As) · wA` при `|As|² > 1e-6`; `F_coh = unit(Ks / Ng) · wC` при `Ng > 0,001` и `|Ks/Ng|² > 1e-6`.
- Ближнего поля и окна **нет**.

### 2.3. Исключение собственного вклада (выведено, проверить тестом)

Депозит и чтение используют одни и те же билинейные веса, ядро `ψ` чётное, а центральная разность антисимметрична, поэтому собственный вклад в `Gs` и в `Ks` сокращается алгебраически: двойная сумма `Σ_k Σ_j w_k·w_j·[ψ(c_k−c_j+e) − ψ(c_k−c_j−e)]` антисимметрична по `k↔j` и равна нулю. Для `Ks` вклад обнуляется свойством `Σ w_k·c_k = p`. Остаются поправки: вычесть `h_i` из `As` и по единице из `Ns` и `Ng`. Условие: симметричное окно свёртки. **При устаревшем поле (K ≥ 2) депозит сделан на прежних позициях, самовклад сокращается не точно**; на плотной стае он делится на `N` порядка сотен, на краю стаи заметнее. Тест P8.1 сверяет упрощение с полной формой на K=1.

### 2.4. Новые сущности

- `FieldNeighborSet` (в `Assets/Scripts/Core/`): ресурс, принадлежит пассу сбора, как `SpatialHashSet` принадлежит `BuildSpatialHashPass`; не ресурс мира.
- Пассы сбора, свёртки и силы в `Assets/Scripts/Passes/FieldNeighborPasses.cs`; кернелы в `Assets/Shaders/GPU/Passes/FieldNeighborPasses.compute`.
- **Валидатор поле-пути.** Один радиус R у всех команд и правил, команд ровно две, `R/t ≥ 3`, мир не больше `MaxCells`. **Существующая проверка `SpatialHashValidator.RequireWithinCell` (радиус не больше ячейки хэша) бросает исключение при R=3 и ячейке 1 м, поэтому для цепочек с полевыми пассами её нужно условно отключить** (проверка остаётся для цепочек с `BoidNeighborForcePass`).
- Диагностика: `-m3d_fieldrep N` и `-m3d_fieldstage build|conv|force|all`, повтор стадии в скрэтч по образцу `-m3d_forcerep` (F5.1). `RepeatCount` пассов остаётся 1.

Существующие `BoidNeighborForcePass`, его кернелы, `TeamParams` и пресеты не меняются. Полевой путь это отдельная цепочка пассов в отдельных пресетах.

## 3. Что показала модель

Источник: `DOC/MEASURE/p8-field-model/`, 3000 частиц, R=3, арена 90 м с переносом, 5 seed. Все числа CPU. GPU не измерен. Полные таблицы 60 и 30 FPS в плане §2.

**60 FPS** (контакт / чужие, t=5; шум курса t=5 / t=15):

| Вариант | t=5 | шум |
| --- | --- | --- |
| эталон без капа | 5,2% / 0,34% | 0,0054 / 0,0017 |
| кап 48 | 62–68% / 21–23% | |
| потенциал, без ближнего поля (режим 7, G=90) | 1,3% / 0,03% | 0,0088 / 0,0046 |
| векторное ядро, без ближнего поля (режим 1) | 0,5% / 0,00% | 0,0131 / 0,0043 |
| потенциал + окно 5×5 + цикл по своей ячейке (режим 9) | 1,9% / 0,08% | 0,0075 / 0,0028 |

**30 FPS**, режим 7, прогон 2026-11-03:

| Вариант | t=5 | t=15 | шум t=5 / t=15 |
| --- | --- | --- | --- |
| эталон | 4,7% / 0,32% | 6,2% / 0,25% | 0,0110 / 0,0071 |
| обновление каждый кадр | 1,0% / 0,02% | 2,6% / 0,12% | 0,0192 / 0,0105 |
| раз в 2 кадра | 0,5% / 0,00% | 1,2% / 0,01% | 0,0229 / 0,0116 |
| раз в 3 кадра | 0,8% / 0,01% | 0,6% / 0,01% | 0,0249 / 0,0151 |

Что из этого следует:

1. Alignment и cohesion на поле совпадают с эталоном и безопасны.
2. Separation на гриде с малым капом не воспроизводит поведение (кап 48: 49%, кап 192: 29% контакта). **Потенциал без ближнего поля даёт контакт ниже эталона при любом интервале обновления: цель «не проникают» выполняется в модели без окна.**
3. Шум курса выше эталона при том же FPS: 1,75× при K=1, 2,1× при K=2, 2,3× при K=3 (на t=15: 1,5 / 1,6 / 2,1×). Часть добавки может быть пилой от ступенчатого обновления. Метрика не меряет «живость».
4. Потенциал и векторное ядро для дальней части равноценны по поведению; потенциал шумит меньше.
5. Плотность ядра стаи в эталоне: медиана own-плотности (конус h=1,5) 19–31 на м² на t=5 и 23–41 на t=15. Это плотность равновесия сил, не спавна.

## 4. Чего модель не покрывает

1. **Цена на GPU.** Gather (около 32 МБ чтения на 400k) против скаттера (до 12 атомиков на частицу, хэш не нужен); цена свёртки по площади (около 19 чтений на частицу при мире 224 м); мало потоков при сборе (16–50 тыс.) и длинный цикл по частицам ячейки. Всё в микробенче P8.1-А.
2. **Масштаб.** Одна геометрия: две команды, 3000 частиц, арена 90 м. Проверка на 24 тыс. и на P400c.
3. **Интерполяция между версиями поля** (гипотеза, в модели не проверялась).
4. **Шаг.** Модель считала шаги 1/60 и 1/30 с. На устройстве `simulationSpeed` умножает шаг: решение владельца 2026-11-03 для P400c это 1.
5. **Классические пресеты и точки.** `TeamClassicSteer`, `AlignFromVelocity`, точки роя не входят в P8 (решение владельца).
6. **Разные радиусы** правил и команд. Поле-путь требует равенства; раздельные можно ввести позже (отдельное расширение валидатора и свёртки).
7. **«Живость».** Шум курса выше эталона на 40–130% во всех полевых вариантах, решает Play.
8. **Тепловой режим.** Устойчивые 30 FPS при троттлинге (433 МГц, ADR-047 замер 4) недостижимы; владелец решил игнорировать пока.

## 5. Альтернативы

| Вариант | Итог на модели | Решение |
| --- | --- | --- |
| Давление по плотности как основное separation | держит равновесную плотность, шум 2,5–4× эталона | отвергнуто как основное; в P8.4 опция регулятора |
| Screened Poisson | по числам равен потенциалу с окном; 8–16 зависимых проходов | отвергнут |
| Дальняя часть векторным ядром `d/r²` | по поведению равна потенциалу, шумит больше | допускается, если на GPU векторная свёртка дешевле |
| Дальняя часть суммой гауссиан | две гауссианы дают ошибку профиля силы 25% | P8.4, при большем R/t |
| Кольцо сенсоров | не проверялось | P8.4 |
| **Окно 5×5 из центроидов + цикл по своей ячейке (бывший основной вариант)** | шум курса 1,4–1,6× эталона, контакт 1,9% / 0,08% | **эскалация P8.1-W.** Требует хэша с ячейкой 0,5 м (мир не больше 128 м) и чтения порядка 800 Б на частицу (около цены обхода капа 48); по оценке в бюджет 400k при 30 FPS не входит |
| Поле + точный обход по хэшу с ячейкой r0 | поведение ближе всего к эталону, 245 кандидатов в среднем | запасной вариант при NO-GO (отдельное ТЗ), по цене не проходит |
| Меньший тексель (R/4) | не проверялся | эскалация P8.1-W, около 1,8× по площади |

## 6. Влияние на код

- **Новое:** `FieldNeighborSet`, пассы сбора / свёртки / силы, один compute-файл, валидатор, условное отключение `RequireWithinCell` для полевых цепочек, пресеты `Boids_hash_2teams_field` (малая сцена 3000, мир 90 м) и `Boids_hash_P400c_field` и их двойники на обходе для базы, сцена P400c, аргументы `-m3d_fieldrep` и `-m3d_fieldstage`, тесты EditMode, зонд поведения (Editor).
- **Не трогается:** `BoidNeighborForcePass` и `BoidsPasses.compute`, `TeamParams`, `SwarmSource`, `TeamHeadingSteerPass`, существующие пресеты и сцены, включая сцены 400k и `Boids_hash.asset`, `TeamRadiusPlayCheck` (для поле-пути отдельная проверка).
- **Ветка.** P8 идёт на `feature/p8-field-neighbors` от `experiment/align-from-velocity` (`d58fc64`), начало отмечено тегом `milestone-p8-start` (решение владельца 2026-11-03: без worktree, всё текущее состояние проекта). Классический хвост P9 (ADR-054…057) остаётся в коде нетронутым и в P8 не используется.
- **Пресет `Boids_hash_2teams`:** по решению владельца радиусы 9 откатываются; ассет и сцену пересоздала штатная фабрика 2026-11-03, закоммичено в `a122e69` (R=3, веса 1,2 / 0,8 / 0,6, по 1500, `simulationSpeed` 1, ячейка 3). Тест `Preset_MatchesTwoTeams` (ждёт версию `521a98b`) может остаться красным и в P8 не чинится.
- **Взаимодействие с хэшем.** В полевом пресете хэш один, с ячейкой `t` (или отсутствует, если победит скаттер); `BoidNeighborForcePass` в нём не стоит. `HashCountsToFieldPass` в полевом пресете не используется.

## 8. Как вернуться

Полевой путь не заменяет старый и включается только пресетами. Откат это удаление пресетов и пассов; обход остаётся рабочим. Условное отключение `RequireWithinCell` действует только при наличии полевых пассов.
