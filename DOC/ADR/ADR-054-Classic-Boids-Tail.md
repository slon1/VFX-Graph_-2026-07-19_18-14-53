# ADR-054: классический хвост боидов (инерция, границы скорости, избегание препятствий)

**Статус:** принят 2026-10-30 (P9.1, P9.2). P9.3 отложена, P9.4 по результатам.
**Дата:** 2026-10-28.
**Контекст:** M3D Framework, ветка `feature/reynolds-boids`. Закрывает первый пункт P9 из `plan-Reynolds-Boids-v2.md` («Ньютонов вариант»), но не в форме `v += force·dt` без границ: форма выбрана ближе к Reynolds. Связано с [ADR-038](ADR-038-Boid-Neighbor-Force.md), [ADR-039](ADR-039-Team-Heading-Steer.md), [ADR-045](ADR-045-Direction-Coloring-And-Needle.md), [ADR-048](ADR-048-Default-Walk-Mode.md), [ADR-049](ADR-049-Swarm-Point-Forces.md), [ADR-053](ADR-053-Sum-Separation.md).

## 1. Контекст

**Как устроен кадр сейчас** (`Boids_hash`): `BuildSpatialHash`, `HashCountsToField`, `ClearVelocity`, `BoidNeighborForce` (walk 1), [`SwarmPointForce`], `TeamHeadingSteer`, `Integrate`, `BoxBounds` (Wrap), `HeadingToValue`.

- `velocity` внутри кадра это **аккумулятор сил без `dt`**: `ClearVelocity` обнуляет, три обхода и `SwarmPointForce` прибавляют.
- `TeamHeadingSteer` берёт из суммы только направление, доворачивает `heading` на `saturate(turn·dt)` и ставит `velocity = heading · cruise`. Скорость не состояние, а константа команды; инерции нет.
- Хэш и alignment читают `heading`. Раскраска по направлению (ADR-045) читает `velocity` в конце кадра.

**Чего хочет владелец.** Классические боиды: скорость хранится между кадрами, силы дают ускорение, у скорости есть верхняя и нижняя граница. Три правила остаются как есть, alignment остаётся по направлению (`heading`), не по скорости соседей. Дополнительные правила: притяжение к цели (уже есть, `SwarmPointForce`, ADR-049) и избегание препятствий. Сначала минимальной ценой, затем по результатам.

**Что уже есть и не нужно делать заново.**
- Притяжение к цели: `SwarmPointForce` (до 16 точек, вес со знаком, радиус, край).
- Отталкивание от чужой команды: множитель `interGroupSeparationMultiplier` в separation (ADR-042). Отдельного радиуса бегства нет, он потребовал бы открыть замороженные обходы (см. §3).
- Отталкивающая точка ADR-049 **не годится как препятствие**: сила пружины `d · w · профиль` растёт от нуля в центре до максимума у края плато, барьера на поверхности нет.

> Примечание 2026-10-28 ([ADR-055](ADR-055-Swarm-Spring-Force.md)): сказанное относится к пружинному пассу. У нормализованного SwarmPointForce длина силы постоянна на плато, и отталкивающая точка с большим отрицательным весом может служить мягким препятствием; нужен ли отдельный пасс препятствий, решается в Play P9.2.

## 2. Решение

### 2.1 Физика хвоста

Новый пасс `TeamClassicSteerPass` (ядро `TeamClassicSteer`) заменяет `TeamHeadingSteer` **в новых пресетах**. `TeamHeadingSteer` и все существующие пресеты не меняются. За кадр:

```
a  = velocity[i] * forceGain[team]            // сумма сил кадра; Y не используется
a  = truncate(a, maxForce[team])              // если maxForce > 0
v  = inertialVelocity[i]                      // состояние между кадрами
(если |v| ≈ 0: v = heading * (minSpeed + maxSpeed) / 2)   // старт и Rebuild
v += a * dt;  v.y = 0
dir   = |v| > 1e-6 ? v / |v| : heading        // XZ
speed = clamp(|v|, minSpeed[team], maxSpeed[team])
v = dir * speed
inertialVelocity = v;  heading = dir;  velocity = v
```

Свойства, на которых держится решение:
- **Веса не пересчитываются.** Сумма сил по-прежнему собирается теми же пассами с теми же весами. `forceGain` это один множитель на команду, переводящий «вес порядка 1» в ускорение. Соотношение sep : align : coh и весов `SwarmPointForce` сохраняется.
- **Устойчивость к лагу.** Шаг ускорения ограничен `maxForce · dt`, затем скорость зажимается в границы. При любом `dt` результат конечен и `|v| ∈ [minSpeed, maxSpeed]`.
- **Границы скорости.** Верхняя режет разгон, нижняя не даёт стае встать. Крейсерской цели нет: между границами скорость свободна (классика).
- **Курс производный.** После шага `heading = normalize(v.xz)`, `Y = 0`. Хэш (снимок `heading` на начало кадра) и alignment видят реальное направление полёта. Раскраска ADR-045 читает `velocity`, которая после хвоста равна реальной скорости.
- **Известное поведение, не баг.** Нижняя граница не даёт развернуться на месте: при силе, строго противоположной скорости, частица тормозит до `minSpeed` и летит дальше по прямой; разворот идёт только через боковую составляющую силы. Тестируется, чтобы случайно не сломать (аналог антипараллельной заметки §2.3 плана v2).
- **Минимальный радиус поворота** примерно `maxSpeed² / maxForce`. Для радиусов взаимодействия 3 и `maxSpeed` 8 нужно `maxForce` порядка 20; при 12 радиус около 5. Числа §2.5 гипотезы.

### 2.2 Данные

- **Атрибут** `BuiltinAttributes.InertialVelocity = new AttributeId("inertialVelocity", AttributeType.Float3, true)`. Регистрируется автоматически нулями из `Reads`/`Writes` пасса (`AutoRegisterAttributes`), поэтому «ноль = не инициализирован» работает штатно. `SwarmSource` (ADR-036) не меняется и скорость не пишет.
- **`TeamParams` 48 → 64 байта.** В конец добавляется `Vector4 Classic = (minSpeed, maxSpeed, maxForce, forceGain)`. Старые три `float4` не двигаются. `Motion.z` остаётся за `chaos` из P8a, `Motion.w` не занимается. Меняются: структура в C# (`TeamProfile.cs`), `Upload`, структура `TeamParams` в `BoidsPasses.compute`, `Stride = 64`. Буфер `BoidReadTeamParams` (3 × `float4`) **не расширяется**.
- **`TeamProfile`**: поля `MinSpeed`, `MaxSpeed`, `MaxForce`, `ForceGain`. Стартовые значения-гипотезы: 4, 8, 12, 5 (подобрать в Play, см. §2.5). Старые ассеты десериализуются с этими значениями по умолчанию; `Classic` читает только новое ядро.
- **Валидатор** (в `SpatialHashValidator`, рядом с `RequireNonNegative(cruise/turn)`): все четыре поля `>= 0`; при включённом `TeamClassicSteerPass` ещё `maxSpeed > 0` и `minSpeed <= maxSpeed`, иначе ошибка; пустой список команд при этом пассе ошибка (как для `TeamHeadingSteer`). Ошибка, если в эффекте включены **оба** пасса, `TeamHeadingSteerPass` и `TeamClassicSteerPass` (оба пишут `velocity` и `heading`). В `ValidateTeams` поля `>= 0` и `maxSpeed`/`minSpeed` идут в существующий цикл по профилям, проверка «оба пасса» стоит до раннего `return` (ниже он выходит при непустом списке команд), ошибка пустого списка в нижнем цикле.
- **`SwarmPointValidator`**: `TeamClassicSteerPass` учитывается там же, где `TeamHeadingSteerPass` (предупреждение, если `SwarmPointForce` стоит после шага). Текст называет реальный пасс шага; для `TeamHeadingSteerPass` он прежний.
- **Единицы `velocity`.** Внутри кадра до хвоста `velocity` это сумма сил, после хвоста реальная скорость. Любой пасс между силой и хвостом, читающий `velocity` как скорость, ошибся бы; в пресетах таких нет, это записывается в `pass-catalog.md`.

### 2.3 Чего нельзя трогать

Ядра `BoidNeighborForce`, `BoidNeighborForceSorted`, `BoidNeighborForceSortedPacked` (walk 0/1/2), `SwarmPointForce`, `TeamHeadingSteer`, `HeadingSteer`, `ClearVelocity`, `Integrate`, `BoxBounds`; хэш и его ресурсы; `SwarmSource`; все существующие `.asset` (`Boids_hash*`, `Boids_mk1*`); `Boids_Rivalry/`. Правила git §4 плана v2 действуют (чужие незакоммиченные файлы не трогать, добавлять пути явно).

В `BoidsPasses.compute` допустимы ровно три вида правок: одна строка в `struct TeamParams` (`float4 Classic;` последним полем), строка `#pragma kernel TeamClassicSteer` (и `SwarmObstacleForce` в фазе P9.3) и блок новых функций и ядер **в конце файла**. `git diff` по файлу не затрагивает текст других ядер. Новый `.compute` не заводить (иначе правка `passLibrary` во всех сценах, как в ADR-049 §3).

### 2.4 Избегание препятствий (фаза P9.3, после ответа на §7.1)

Рекомендуемая форма: статические круглые препятствия, заданные в редакторе, по образцу точек ADR-049.

- **Данные.** `SwarmObstacle` (`[Serializable]`): `positionXZ`, `radius > 0`, `margin >= 0` (зона вокруг поверхности, по умолчанию 3), `weight` (по умолчанию 4). `EffectAsset.SwarmObstacles` (максимум 16), буфер из 16 структур по 32 байта `(x, z, radius, margin)` и `(weight, 0, 0, 0)`, заливка при инициализации и каждый кадр, `SimContext.SwarmObstacles` и `SwarmObstacleCount`. Всё по образцу ADR-049 §2.5.
- **Сила.** Для препятствия `k`: `d = MinImage(p − c_k)`, `s = |d| − R_k`, `n = d/|d|`, `prof = saturate(1 − s/margin_k)` (внутри круга `prof = 1`), `f += n · weight_k · prof`. Если `|d| < 1e-5`, вклада нет (направление не определено). `velocity += float3(f.x, 0, f.y)`, без `dt`, команда не читается, `velocity.y` не меняется.
- **Пасс** `SwarmObstacleForcePass`, ядро `SwarmObstacleForce`, один диспатч, цикл по препятствиям внутри ядра, диспатча нет при нуле препятствий. Стоит между `SwarmPointForce` и `TeamClassicSteer`.
- **Приоритет.** Силы соседей ограничены (alignment и cohesion единичные, separation растёт как 1/r), поэтому вес препятствия выше суммы соседских сил даёт ему приоритет у поверхности без отдельного арбитража. `forceGain` умножает и эту силу, а `maxForce` обрезает сумму. Настоящее распределение бюджета `maxForce` по приоритетам (Reynolds) отложено: оно потребовало бы считать препятствия внутри ядра хвоста.
- **Валидатор.** Предупреждение, если `margin < maxSpeed² / (2 · maxForce)` (эвристика: меньше пути торможения); предупреждение, если пасс стоит не между силой и хвостом; предупреждение при нескольких таких пассах.
- **Жёсткая страховка** не входит. В проекте есть `SphereCollider` (один шар на пасс, выталкивает позицию и отражает скорость); при необходимости его можно добавить в цепочку руками. В хвосте `velocity` перезаписывается, поэтому коллайдер должен стоять после хвоста.

### 2.5 Стартовые числа (гипотезы, не расчёт)

| Параметр | Старт | Откуда |
| --- | --- | --- |
| `minSpeed` / `maxSpeed` | 4 / 8 | коридор вокруг прежнего `cruise` 6 |
| `forceGain` | 5 | предельная сумма соседских сил около 2,6 (ADR-049 §2.9), даёт порядка 13 против `maxForce` |
| `maxForce` | 12 | радиус поворота `maxSpeed²/maxForce` порядка радиусов взаимодействия |
| веса sep/align/coh | 1,2 / 0,8 / 0,6 | как `Boids_hash`, не менять |
| вес препятствия | 4 | выше суммы соседских сил (4 · 5 = 20 > `maxForce`) |

Поправить после первого Play. Если стая дрейфует к одной из границ скорости, сужать коридор, а не добавлять правило.

## 3. Отвергнутые варианты

- **Буквальный `velocity += force·dt` без нормализации и без `forceGain`.** Сила в `velocity` не имеет масштаба ускорения (separation растёт как 1/r, alignment и cohesion единичные); те же веса дали бы другую стаю, пришлось бы заново калибровать всё, включая точки ADR-049.
- **Желаемая скорость `cruise · normalize(force)` и `lerp` к ней** (мой первый набросок). Возвращает скорость к постоянной цели; владелец выбрал классику с границами.
- **Персистентная `velocity` и отдельный буфер силы** (вариант А у Grok). Меняет адресат записи в живом walk 1 и в `SwarmPointForce`. Новый атрибут скорости ничего из этого не открывает.
- **`v += force·dt` внутри кернела обхода** (вариант Б у Grok). Открывает замороженные walk 0/2, повторяет вынос цикла из P9.
- **Вынос цикла соседей в `BoidForces.hlsl`.** Не нужен: Ньютону нужен другой хвост, не другой обход. Формула силы повторена в трёх кернелах, вынос затронул бы все три.
- **`maxAccel` в `Motion.w`.** Хватило бы одного поля, но классике нужны четыре числа; расширение `TeamParams` дешевле, чем занимать слоты, зарезервированные под P8a.
- **Выравнивание по скорости соседей сразу.** Нужны скоростной снимок хэша и правка формулы во всех трёх обходах плюс новый оракул. Откладывается до результатов P9.2 (см. §6).
- **Избегание чужой команды отдельным радиусом бегства.** Требует цикла по соседям, то есть правки замороженных обходов и риска для бюджета S200. Пока достаточно множителя `interGroupSeparationMultiplier`.
- **Отталкивающая точка ADR-049 как препятствие.** Нет барьера на поверхности (§1).

> Примечание 2026-10-28 ([ADR-055](ADR-055-Swarm-Spring-Force.md)): сказанное относится к пружинному пассу. У нормализованного SwarmPointForce длина силы постоянна на плато, и отталкивающая точка с большим отрицательным весом может служить мягким препятствием; нужен ли отдельный пасс препятствий, решается в Play P9.2.
- **Опережающее избегание Reynolds (луч по курсу, пересечение с кругом).** Дороже и тоньше в настройке; для круглых статических препятствий достаточно зоны вокруг поверхности.

## 4. Последствия

- **Цена.** Один дополнительный диспатч хвоста вместо `TeamHeadingSteer` (тот же набор потоков), плюс чтение и запись `inertialVelocity` (12 байт на частицу в каждую сторону). `TeamParams` вырастает на 128 байт. Цикл обхода не меняется. Замер S200 по новой базе делает владелец после P9.2, информационно.
- **Тесты.** Единственная правка существующих тестов: в `TeamProfileTests.cs` тест `Stride_Is48` содержит два ожидания (`TeamParams.Stride` и `Marshal.SizeOf<TeamParams>()`), оба становятся 64, тест переименовывается в `Stride_Is64`. Остальные тесты берут `TeamParams.Stride` как константу. Любая другая правка существующего ожидания это остановка и вопрос.
- **Половинная сила (F5a, не реализована).** ADR-049 §4 отмечает, что для неё нужен постоянный буфер силы. `inertialVelocity` это буфер скорости, не силы, они не конфликтуют.
- **Поведение.** Новые пресеты выглядят иначе, чем `Boids_hash`: плавные повороты, разгон и торможение, стая может дрейфовать между границами. Вид принимает владелец.
- **P8 (отталкивание между стаями, матрица пар).** Не решается этим ADR.

## 5. Критерии приёмки

**Общие (каждая фаза).** EditMode зелёный, число тестов до и после записано, не используется `git add -A`, правила §4 плана v2.

**P9.1 (хвост и юнит-тесты, без пресета).**
1. `git diff` по `BoidsPasses.compute` соответствует §2.3; ассеты в `Assets/Effects` не изменены; единственная правка существующих тестов это `Stride_Is48` (два ожидания, §4).
2. Тесты ядра (GPU EditMode, образец `TeamHeadingSteerTests`):
   - границы скорости: при случайных силах, силе 1e6 и `dt` до 10 всё конечно и `|v| ∈ [minSpeed, maxSpeed]`;
   - инерция: сила в кадре 1, ноль в кадре 2 (между кадрами `ClearVelocity`), скорость сохраняется;
   - обрезка: `|Δv| ≤ maxForce · dt` при неактивных границах; `maxForce = 0` не обрезает;
   - `forceGain` линеен (вдвое больше сила равна вдвое большему `gain`);
   - независимость от разбиения `dt` при постоянной силе и неактивных границах (два полушага равны одному в допуске);
   - старт: нулевой `inertialVelocity` и нулевая сила дают `|v| = (min+max)/2` вдоль `heading`;
   - нулевая сила скорость не меняет, `heading = normalize(v)`;
   - антипараллельная сила: торможение до `minSpeed`, направление сохранено, нет NaN;
   - Y: сила и `heading` с большой Y дают `v.y = 0`, `heading.y = 0`, `|heading| = 1`;
   - команды: разные границы у двух команд, `teamId > 7` читает команду 7;
   - вырожденный ввод (нулевые `heading`, `inertialVelocity`, сила) даёт конечный результат;
   - **якорь к существующему поведению:** при `minSpeed = maxSpeed = c`, `maxForce = 0`, очень большом `forceGain` и `dt = 1` направление совпадает с `TeamHeadingSteer` при `turn · dt = 1` (допуск 1e-4; `inertialVelocity = 0`, `|F.xz| ≥ 1`).
3. Контракт: имя ядра уникально во всей библиотеке, `RepeatCount == 1`, `Reads`/`Writes`, `TeamParams.Stride == 64`, `Upload` заполняет `Classic`, `Motion` не изменён.
4. Валидатор: отрицательные поля, `minSpeed > maxSpeed`, `maxSpeed = 0`, пустой список команд, оба пасса вместе, предупреждение о порядке для `SwarmPointForce`.

**P9.2 (пресет и Play).**
1. `Boids_hash_classic.asset`, меню `Tools/M3D/Create Boids Hash Classic Effect`: рецепт `Boids_hash` с заменой `TeamHeadingSteer` на `TeamClassicSteer`, `walk 1`, 3000 частиц, одна команда, числа §2.5, `SimulationSpeed = 1`. Существующие рецепты и ассеты не меняются.
2. World-smoke с readback (метрика, не глаз): 300 кадров, все `velocity`, `position`, `heading` конечны, `|v|` в границах, средняя скорость внутри коридора, нет шва на границе тора.
3. Play (Grok делает скриншоты и фиксирует числа, решение о виде принимает владелец): `Boids_hash` против `Boids_hash_classic` на одном seed, 15 с; вариант с тремя точками из критерия 4 ADR-049.
4. Подбор `forceGain`, `maxForce`, границ записывается в журнал `DOC/last/play-p9-classic.md`; изменения весов соседей не допускаются.
5. Устройство (владелец, информационно): S200, режим B, цикл на частицу против 40,59 (сборка `cb661ba`) или против новой базы по решению владельца.

**P9.3 (препятствия, после §7.1).** По образцу критериев ADR-049: диффы только добавляют, тесты ядра (знак, профиль, внутри круга, шов тора, `|d| < 1e-5`, независимость от `dt`, `velocity.y`, сумма нескольких препятствий, нет диспатча при нуле), валидатор, Play с одним и тремя препятствиями: стая огибает, нет проникновения в центр при выбранных числах, нет скопления на тыловой стороне.

**Разведка А.**

### Принятие

2026-10-30, голова до закрытия `228af563abd06a42f5a6ac637cc6a62e69530080`, коммит ТЗ `c533ad855ed874706e203a5369b43e0456be1f7b`. Снос скорости к верхней границе принят: к кадру 300 около 78% частиц у `classic` и 73% у `classic_points`. Трение в хвост не добавляется. Нижняя граница почти не срабатывает. Если позже понадобится живой коридор, пути — поле `drag` внутри `TeamClassicSteer` (предположительно `Motion.w`, по умолчанию 0) или alignment по скорости соседей (P9.4). Существующие `Drag` и `SpeedLimit` не годятся: они меняют `velocity`, а хвост каждый кадр читает `inertialVelocity`.
