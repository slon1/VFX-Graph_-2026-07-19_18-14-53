# ADR-046: Цель производительности 200 000, метрика в циклах и закрытие P6

**Статус:** предложено. «Принято» ставит владелец после выполнения F1.
**Дата:** 2026-10-16.
**Контекст:** M3D Framework, ветка `feature/reynolds-boids`. Связано с [ADR-040](ADR-040-Boids-Hash-Preset-And-Play-Gate.md) (хэш и обход соседей), [ADR-041](ADR-041-Team-Palette.md) (палитра), [ADR-042](ADR-042-Two-Team-Preset.md) (пресет двух стай), [ADR-043](ADR-043-Team-Palette-Followups.md), [ADR-045](ADR-045-Direction-Coloring-And-Needle.md). План работ: [plan-P7-perf-200k.md](../plan-P7-perf-200k.md).

## 1. Контекст

1. **Замеры стали воспроизводимыми.** После выяснения, что прежние числа снимались в режиме энергосбережения, Grok собрал систему E1 (параметры командной строки, штамп сборки, предполёт, серия, Streamline CLI). Серия ABABC на трёх разрешениях (сборка `6ac1cad`, `dirty=1`, `dirtyhash=f3017014`) показала разброс повторов 0,03–0,29 мс, три профиля Streamline показали частоту GPU 690,0 / 676,5 / 624,9 МГц.
2. **База 100 000 частиц, `maxNeighbors` 48** (`DOC/MEASURE/6ac1cad-f3017014/`): кадр «сила и рендер» 19,77 / 20,34 / 21,90 мс, «только сила» 17,80 / 18,58 / 20,46 мс, «только рендер» 16,72 / 16,79 / 16,77 мс (1520×720, 2280×1080, 3040×1440). Профиль режима «только сила» на 720: около 12,3 М циклов GPU на кадр (около 123 цикла на частицу), расходящихся инструкций 0,85, частичных чтений 0,96, атомиков 200 800 на кадр (две на частицу).
3. **P6 в плане** (палитра 6a и пресет двух стай 6b) принята визуально 2026-10-08. С тех пор выяснилось, что критерий 6b был слабым, что запасной шаг ×8 по CPU-модели вредит, и что «проход сквозь» у пресета, скорее всего, следствие слепоты капа, а не множителя (все три утверждения по CPU-модели `DOC/MEASURE/p6-cpu-model/boids_model.cpp`, это не GPU). Пункт плана про замер S10 палитры потерял смысл: риск fill-rate снят переносом цвета в вершину (A2) и расчётом цвета по направлению (C1). Режим «только рендер» на базе 16,72 / 16,79 / 16,77 мс без длинных кадров: рендер 100 000 частиц укладывается в один интервал vsync на всех разрешениях (разность средних кадров «сила и рендер» минус «только сила» убывает с разрешением из-за квантования vsync и ценой рендера не считается).
4. **Владелец** (2026-10-16) поставил цель 200 000 частиц на S10 и решил, что стаи по умолчанию отталкиваются, при этом матрицу взаимодействий (бегство, огибание, отталкивание, преследование) оставил на потом.

## 2. Решения

### 2.1. P6 закрывается

P6 считается закрытой после выполнения F1. Условия: ADR-042 errata 1 (критерий, отзыв шага ×8, формулировка журнала), закрытие замера палитры в ADR-041 §5, правки `plan-Reynolds-Boids-v2.md`. Оставшиеся пункты не блокируют закрытие и переходят в P7 (производительность) и P8 (отталкивание между стаями и матрица): StableSymmetric, повтор рычага `maxNeighbors`, размер ячейки.

### 2.2. Цель и метрика

1. **Цель:** 200 000 частиц, `maxNeighbors` 48, 1520×720, S10, условия протокола замеров. Отметки: **M1** не менее 30 FPS (обязательна), **M2** не менее 60 FPS (ориентир, не обязательна).
2. **Основная метрика:** циклы GPU на частицу в кадр в режиме «сила без рендера» (Streamline; от частоты GPU не зависит, от числа частиц не зависит только при той же плотности, сцена S200). Кадр и доля длинных кадров вторичны. Бюджет (оценка для сцены S200 с той же плотностью, перемерить): M1 около 100–115, M2 около 45–58; нижняя граница вилки учитывает вычет рендера, который пока не измерен. M1 это обязательство, M2 ориентир.
3. **База:** `6ac1cad-f3017014`, 123 цикла на частицу. Числа старых серий (`d9bba9c`, `27c7c4c`, `df9748d`, `ee2ce26` и `logcat*.txt`) в текущих сравнениях не используются.

### 2.3. Правила замеров и приёмки изменения кода

1. Сравнения на разрешении 1520×720, серия `ABABC` (A: сила и рендер, B: только сила, C: только рендер) и профиль Streamline режима B. Высокие разрешения только как редкая проверка.
2. Порог шума: разница меньше `max(2 × разброс, 0,5 мс)` или 0,03 по доле длинных кадров не считается эффектом.
3. Изменение обхода принимается по критерию из `plan-P7-perf-200k.md`: силы `walk 1` совпадают с `walk 0` в допуске 1e-4 по компонентам силы; если допуск существующих тестов жёстче, для `walk 1` пишутся новые тесты, `walk 0` и существующие тесты не меняются. Циклы на кадр, расходимость и частичные чтения падают, кадр не растёт.
4. Состояние экрана `Dozing` на старте **не делает точку недействительной** (правило отменено: приложение прогревается из этого состояния, 60 с прогрева достаточно). `wakefulness` фиксируется как информация. Остальные проверки (`applied`, `devbuild`, `powersave`, `build`, отсутствие предупреждений) остаются.
5. Сравнение «до и после» кода по возможности внутри одного APK через переключатель параметром командной строки (`-m3d_walk` и подобные), чтобы исключить влияние грязного дерева и пересборки.

### 2.4. Поведение двух стай по умолчанию: отталкивание

Целевое поведение пресета двух стай: стаи отталкиваются и не проникают друг в друга. Текущий пресет задуман так же (отталкивание через `interGroupSeparationMultiplier`), но по CPU-модели ведёт себя как проход сквозь (контакт 65% на 5 с) из-за подвыборки соседей капом по посещённым. Механизм (бюджеты соседей по классам отношений либо симметричная выборка `StableSymmetric`) выбирается после оптимизации обхода по замеру и должен укладываться в будущую матрицу N×N (запись `правило[A → B]` с радиусами и видом правила). Номер ADR-044 остаётся за этим выбором, сейчас файл не создаётся.

### 2.5. Снимок соседей: A/B закрывается решением

Сравнение отсортированного снимка с чтением живых `position/heading/teamId` не проводится. Снимок остаётся: после перехода на порядок потоков по `SortedIndices` (F3) потоки читают данные из отсортированных массивов по построению, а чтение живых буферов это косвенный случайный доступ. Запись снимка стоит около 24 байт на частицу в кадр. В F3 запись соседа упаковывается в 16 байт (позиция `float2`, направление 2×snorm16, команда), `SortedIndices` остаётся отдельным `uint` (нужен для записи силы обратно частице), поэтому пункт техдолга про неиспользуемую запись `SortedIndices` закрывается. Пересмотреть решение, если профиль после F3 покажет, что запись снимка заметна.

### 2.6. `minCellSize`

`MinCellSize` это нижняя граница размера ячейки. В пресетах она задана равной радиусу взаимодействия (3, например в `Boids_hash100k`), значение 2 это лишь значение по умолчанию в пассе, на этих сценах оно не используется. Меньше радиуса значение ставить нельзя: сетка становится мельче, обход 3×3 теряет соседей дальше одной ячейки (валидатор только предупреждает). Больше радиуса значение только добавляет кандидатов. Подбор `minCellSize` из плана снимается. Настоящий рычаг это отношение размера ячейки к радиусу (ячейка R/2 с обходом 5×5), он требует другого цикла обхода и проверяется на CPU-модели в F5.

## 3. Отвергнутые варианты

- **Реализовать `StableSymmetric` сейчас.** Он обходит всех кандидатов в девяти ячейках, то есть противоречит цели по производительности, а механизм отталкивания может оказаться другим (бюджеты по классам отношений). Отложено до P8.
- **Серия точных замеров на нынешнем коде.** База уже воспроизводима, дополнительные серии не дадут нового знания. Нужны только недостающие профили (режимы C и D) и доля капа на 100 000.
- **Повтор рычага `maxNeighbors` сейчас.** Результат зависит от реализации обхода, снимать после F3.
- **Оставлять правило про `Dozing`.** Тесты показали, что оно ничего не защищает.
