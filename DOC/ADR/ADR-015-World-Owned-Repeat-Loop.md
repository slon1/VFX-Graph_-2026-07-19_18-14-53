## ADR-015: World-Owned Repeat Loop

**Статус:** Принято (реализовано)
**Дата:** 2026-08-23
**Контекст:** M3D Framework, фаза 0 подготовки к Stable Fluids (F0.1)
**Дополняет:** [ADR-001](adr-001-field-resources-m2a.md) §3 (владение swap)
**ТЗ:** [`todo-ADR-015.md`](../last/todo-ADR-015.md)

### Контекст

Итерационный решатель давления — это один и тот же кернел, применённый к полю несколько десятков раз за кадр. Сейчас фреймворк такого не умеет: `SimulationWorld.Update` проходит список пассов ровно один раз, а `Execute` объявлен `sealed override` в `ParticleKernelPass` (`SimPass.cs:322`) и `FieldKernelPass` (`SimPass.cs:495`), то есть пасс физически не может записать больше одного диспатча за вызов.

Три способа это обойти, и два из них ломают инварианты:

1. **Положить цикл внутрь пасса.** Требует распечатать `sealed Execute` либо дать пассу писать N диспатчей за вызов. Тогда между итерациями нужен swap, а swap принадлежит World (ADR-001 §3) — пасс либо начнёт свапать сам, либо World сделает **один** swap после N диспатчей. Второе даёт ошибку чётности: при нечётном N `Current` укажет на текстуру, в которую последний диспатч не писал. Это именно тот класс дефекта, от которого предупреждает комментарий в `SimulationWorld.cs:100–102`.
2. **Положить 40 экземпляров пасса в `EffectAsset`.** Работает без правок кода и абсолютно нечитаемо в инспекторе, а число итераций перестаёт быть параметром.
3. **Цикл в World.** `Execute` остаётся `sealed`, «один вызов = не более одного диспатча» сохраняется, swap остаётся у World.

Выбран третий.

### Решение

#### 1. `SimPass.RepeatCount` — virtual, не сериализованное поле базы

```csharp
/// <summary>How many times World re-runs this pass per frame. Iterative solvers override it.</summary>
public virtual int RepeatCount => 1;
```

Именно `virtual` property, а **не** `[SerializeField] private int repeatCount` в `SimPass`. Причина: `SimPass` сериализуется полиморфно и его поля попадают во все ~30 пассов — и в данные, и в инспектор `EffectAsset`. Слайдер «repeat» у `PlaneColliderPass` или `IntegratePass` не имеет смысла и приглашает выставить его в 2 «посмотреть, что будет». Пассы, которым счётчик нужен, объявляют свой сериализованный параметр с осмысленным именем и диапазоном:

```csharp
[SerializeField, Range(1, 80)] private int iterations = 40;
public override int RepeatCount => iterations;
```

#### 2. Цикл в `SimulationWorld.Update`, проверка `LastExecuteDispatched` — внутри цикла

```csharp
using (new ProfilingScope(commandBuffer, sampler))
{
    int repeat = pass.RepeatCount;
    for (int r = 0; r < repeat; r++)
    {
        pass.Execute(context, deltaTime);
        if (pass.LastExecuteDispatched)
        {
            SwapPingPongFields(pass);
        }
    }
}
```

Проверка `LastExecuteDispatched` обязана быть **внутри** цикла, по итерации. Соблазн вынести её наружу («пасс либо диспатчит, либо нет») неверен: `ShouldDispatch` (`SimPass.cs:419`) — virtual и вычисляется на каждом `Execute`, поэтому одношотный пасс вроде `SeedScalarDiskPass` может отдиспатчить на первой итерации и отказаться на второй. Вынесенная проверка дала бы число swap'ов, не равное числу диспатчей, — то есть ту же ошибку чётности, из-за которой отклонён вариант 1.

Побочное следствие, которое не требует отдельной обработки: при `WritePingPong` каждая итерация читает `Current` и пишет `Next`, после чего свапает, поэтому после любого числа итераций — чётного или нечётного — свежий результат лежит в `Current`. Чётность не является параметром корректности.

#### 3. Один `ProfilingScope` на весь цикл, имя сэмплера без счётчика

Область профилирования охватывает цикл целиком, а не каждую итерацию. Иначе 40 итераций Jacobi дают 40 одноимённых GPU-маркеров: таймлайн становится нечитаемым, а сами `BeginSample`/`EndSample` из накладных расходов превращаются в измеримую статью.

Имя сэмплера остаётся `pass.DisplayName`, без `×N`. `samplers` — словарь по пассу, имя формируется один раз при первом кадре (`SimulationWorld.cs:89–93`), поэтому счётчик в имени устарел бы при первом же движении слайдера. Число итераций видно в инспекторе и в `pass-catalog.md`.

#### 4. `RepeatCount < 1` — ошибка на Build, не clamp в рантайме

Пасс с `RepeatCount = 0` молча не делает ничего. Это тот же класс молчаливого no-op, ради которого писался ADR-003, и рантайм-clamp до 1 его только маскирует. Проверка идёт туда же, где уже живёт валидация запросов пассов в `Build`, и падает с явным сообщением.

Выключенные пассы **пропускаются** — тем же `pass == null || !pass.Enabled`, что Update, Initialize и аллокация accum-буферов. Включение без Rebuild даёт молчаливый no-op у любого пасса (`sealed Execute` выходит на `!kernel.IsValid`). F0.4 этот контракт **не** пересматривает: четыре красных теста были ошибкой голого `VisualEffect` без `PositionBuffer`, а не пропуском Initialize.

#### 5. Что `RepeatCount` **не** делает

Он не превращает `WriteInPlace` в допустимый режим для стенсильных операций. Внутри одного диспатча соседние тексели читают и пишут одну и ту же текстуру без порядка — повторение диспатча этого не лечит. Jacobi обязан быть `WritePingPong`, требование ADR-001 не меняется.

### Отклонённые варианты

**Цикл внутри пасса** (распечатать `sealed Execute` или разрешить N диспатчей за вызов) — см. Контекст §1: либо swap переезжает в пасс против ADR-001 §3, либо возникает ошибка чётности.

**N экземпляров пасса в `EffectAsset`** — число итераций перестаёт быть параметром, инспектор нечитаем. Остаётся полезным как **эталон в тесте**: результат `RepeatCount = 6` обязан побитово совпадать с шестью последовательными одиночными исполнениями.

**`[SerializeField]` в базовом `SimPass`** — засоряет данные и инспектор всех пассов параметром, осмысленным для двух.

**Отдельный `IterativeSolverPass`-базовый класс** — иерархия уже двухуровневая (`SimPass` → `ParticleKernelPass`/`FieldKernelPass` → конкретный), третий уровень ради одного свойства не оправдан, и он не совместим с тем, что итерации могут понадобиться и частичному пассу.

### Последствия

- (+) Разблокирует `JacobiPressurePass` и вообще любой итерационный решатель, не трогая `sealed Execute` и не перенося swap.
- (+) `Execute` остаётся «не более одного диспатча за вызов» — инвариант, на который опирается вся логика `LastExecuteDispatched`.
- (+) Изменение локализовано: одно свойство в `SimPass`, один цикл в `Update`, одна проверка в `Build`.
- (−) Становится тривиально легко выйти за бюджет диспатчей: 40 итераций на 256² — это 40 диспатчей на один пасс. Поэтому счётчик обязан быть виден в инспекторе и записан в `pass-catalog.md` для каждого пасса, который его переопределяет.
- (−) `deltaTime` передаётся в каждую итерацию одинаковым. Для Jacobi это правильно (итерации решают одну и ту же линейную систему внутри одного шага по времени), но для пасса, который наивно переопределит `RepeatCount`, это означает N шагов по времени длиной `dt` каждый, то есть эффективный шаг `N·dt`. Записать предупреждением в `pass-catalog.md`: `RepeatCount` — итерации решателя, не субшаги по времени. Субшаги — отдельная задача и отдельный механизм.

### Проверяемость

DoD опирается на харнес из [ADR-014](ADR-014-GPU-Numeric-Test-Harness.md): результат одного пасса с `RepeatCount = N` сравнивается с N последовательными одиночными исполнениями того же пасса. Это буквально одна и та же последовательность диспатчей, поэтому утверждение — **побитовое равенство**, а не совпадение в пределах допуска.
