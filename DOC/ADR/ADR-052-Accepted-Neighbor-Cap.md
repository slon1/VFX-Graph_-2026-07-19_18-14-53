# ADR-052: цена обхода и кап соседей: повтор пасса силы, серия капа, кап по принятым (отложен)

**Статус:** предложено, редакция 2 (после F5.0, коммит `fd553cb`). Кернел `Accepted` (§2.1–2.4) отложен; F5.1 сужен до `forcerep`.
**Дата:** 2026-10-22 (редакция 1: 2026-10-21).
**Контекст:** M3D Framework, ветка `feature/reynolds-boids`, план [plan-P7-perf-200k.md](../plan-P7-perf-200k.md), фаза F5. Связано с [ADR-046](ADR-046-Perf-Target-And-P6-Closure.md) (целевое поведение двух стай, M1/M2), [ADR-047](ADR-047-Sorted-Order-Neighbor-Walk.md) (обход `walk 1`), [ADR-048](ADR-048-Default-Walk-Mode.md) (`walk 0` и `walk 2` заморожены).
**Номер:** 052 назначен как следующий после ADR-051. Номер 044 зарезервирован под P8 (Techdebt 10n), номер 049 в `DOC/ADR/` отсутствует; владелец подтверждает номер при приёмке.

## 1. Контекст

Кап `maxNeighbors` в `walk 1` считает **посещённые слоты** (`visited`): каждый кандидат, прошедший защиту от самого себя (`r2 >= 1e-6`), расходует кап, даже если лежит за радиусом (`r2 >= maxR2`). Ячейка равна максимальному радиусу, девять ячеек покрывают `9R²`, круг радиуса `R` занимает `πR²`, то есть около 35% посещённых слотов принимаются. В насыщенном капе (доля частиц с капом 0,976–0,998 на всех проверенных сценах) кап тратится в основном на дальних, и чужие внутри радиуса отсекаются порядком обхода (`start = i % 9`).

Идея F5: считать кап по **принятым** (`r2 < maxR2`). На CPU-модели двух стай по 1500 при капе 48 владелец получил падение контакта на 5 с с 65% до 17% и доли чужих с 23% до 0,6%. Цена на GPU неизвестна, правило меняет поведение стай.

### 1.1. Результат F5.0 (CPU-модель, коммит `fd553cb`)

Модель `DOC/MEASURE/p6-cpu-model/boids_model.cpp` расширена девятым аргументом `maxVisited` (потолок посещений, только режим 1) и статистикой слотов; три плотности спавна, 24 варианта правила, сиды 1–5, 360 прогонов. Регрессия старых режимов 0–3: 20 из 20 прогонов совпали построчно. Независимая перепроверка Claude (модель переписана заново) воспроизвела таблицы до сотых на всех трёх плотностях.

Плотность (1), t = 5 с, среднее по пяти сидам:

| правило | контакт % | чужие % | слотов, среднее | p95 / максимум |
|---|---:|---:|---:|---|
| visited, кап 48 (сейчас) | 61,2 | 20,7 | 47,6 | 48 / 48 |
| visited, кап 128 | 24,2 | 2,23 | 125,7 | 128 / 128 |
| accepted, кап 48, без потолка | 22,9 | 0,98 | 107,3 | 253 / 548 |
| accepted, кап 48, потолок 192 | 23,0 | 0,58 | 100,6 | 192 / 192 |

Разброс контакта у visited-128 по сидам 3,3–36,7, то есть различия меньше примерно 6 пунктов на пяти сидах не разрешаются (изменение `discR` на 3·10⁻⁵ сдвигает средний контакт на плотности (2) с 18,8 до 25,0).

Гейт отчёта F5.0 (в редакции 1 ТЗ) дал «писать кернел»: условие (б) выполнено (100,6 слота против 125,7, на 20% ниже), условие (а) не выполнено, условие 2 выполнено. **Этот вывод не принят**, по трём причинам:

1. **Среднее число слотов не мера цены на GPU.** Волна платит за самую долгую нить. Оценка «цена волны» = ширина волны × максимум `visited`, нити волны подряд идущие слоты в порядке ячеек (модельная оценка, не замер; значения из `F5-wave-proxy.md`, два знака):

   | t = 5 с | visited-128 (8 / 16 / 32 нити) | accepted-48, потолок 192 (8 / 16 / 32 нити) | разница |
   |---|---|---|---|
   | плотность 1 | 127,00 / 127,57 / 127,84 | 163,49 / 175,44 / 183,46 | +29…+44% |
   | плотность 2 | 126,99 / 127,38 / 127,60 | 143,50 / 153,79 / 163,11 | +13…+28% |
   | плотность 3 | 127,43 / 127,71 / 127,96 | 171,99 / 180,75 / 186,17 | +35…+45% |

   В потолок 192 упирается 12% обходов на плотности (1), и такие обходы встречаются почти в каждой волне.
2. **При равном поведении выигрыша нет** (плотность 1, t = 5 с, цена волны на 16 нитях):

   | поведение | visited: контакт / чужие, цена | accepted-64 с потолком: контакт / чужие, цена |
   |---|---|---|
   | как у visited-128 | 24,23 / 2,23, 127,57 | 27,36 / 1,83, 127,30 (потолок 128) |
   | лучше | 15,90 / 0,77, 159,51 (кап 160) | 12,95 / 0,26, 156,14 (потолок 160) |
   | ещё лучше | 6,00 / 0,23, 190,88 (кап 192) | 6,68 / 0,14, 181,25 (потолок 192) |

   Разница около 5% и меньше, это меньше шума. Поведение определяется числом слотов, которое приходится прочитать, а не тем, что считает кап.
3. **Условия гейта не различают варианты.** Условие (а) недостижимо: ширина min–max visited-128 равна 33 пунктам, порог 67, средний контакт 24. Условие (б) опирается на среднее. Выбор потолка 192 зависит от разницы в 0,15 пункта (потолок 128 отпал с контактом 37,15 при границе 37,00).

Ограничения оценки волны: все слоты считаются одинаково дорогими (принятый слот делает силу и дороже отброшенного); порядок нитей в модели равен порядку ячеек, на GPU порядок слотов внутри ячейки задают атомики (ADR-048 §6). Это гипотеза, она меняет знак ожидаемого выигрыша и переносит бремя доказательства на кернел. Проверяет её только захват на GPU (условие возврата в §3).

Следствие для M2 (грубая линейная оценка, к проверке в F5.3): visited-128 читает в 2,7 раза больше слотов, чем visited-48; если обход даёт около 24 из 41 цикла на частицу, выходит около 80 циклов против бюджета M2 около 45–58. Исправление поведения до уровня visited-128 вероятно стоит M2.

## 2. Решение

### 2.1. Правило `capMode = 1` («по принятым»). **Отложено**

Сохранено как спецификация на случай возврата. Для каждого кандидата после пропуска `r2 < 1e-6`, в таком порядке:

1. `maxVisited > 0 && visited >= maxVisited` → остановка, причина «потолок» (`capped = 2`).
2. `visited++`.
3. `r2 >= maxR2` → следующий кандидат (не принят).
4. `maxNeighbors > 0 && accepted >= maxNeighbors` → остановка, причина «кап принятых» (`capped = 1`).
5. `accepted++`, накопление `sep`, `align`, `coh` как в `walk 1`.

«Принят» означает `r2 < maxR2`. Порядок ячеек, `start = i % 9`, слияние диапазонов, сдвиг тора и защита по радиусу не меняются. Модель F5.0 реализует это правило в режиме 1.

### 2.2. Кернел, потолок, счётчики (§2.2–2.4 редакции 1). **Отложено**

Новый кернел-дубликат `BoidNeighborForceSortedAccepted`, поля `capMode` и `maxVisited`, четыре счётчика в `CapHits`, аргументы `-m3d_capmode` и `-m3d_maxvis` в F5 не реализуются. Кернелы `walk 0`, `walk 1`, `walk 2`, `HashScatter*` и структура `NeighborWalk` остаются нетронутыми.

### 2.3. Повтор пасса силы `forcerep` (F5.1)

Streamline не режет диспатчи по именам, поэтому цена обхода отделяется повтором, как для хэша (`hashrep`). Первый диспатч обычный. Повторы 2…R внутри того же `Execute` запускают тот же кернел с теми же привязками, кроме `velocity` (скрэтч-буфер `float3[N]`, обнуляется перед повторами, stride равен stride `velocity`) и `CountCapHits` (0 на повторах). Кернелы не меняются; запись `+=` в RW-буфер не даёт компилятору выбросить обход, `velocity` и счётчики не искажаются. Диапазон 1..16, аргумент `-m3d_forcerep`. Счётчик повтора отдельный (`ForceRepeatCount`) и не переопределяет виртуальный `SimPass.RepeatCount`: мир вызывает `Execute` ровно `RepeatCount` раз и прибавил бы силу к `velocity` столько раз.

### 2.4. Серия капа (F5.3)

Сетка для `capMode 0` (существующий `-m3d_maxn`): 32 / 48 / 64 / 96 / 128 / 192. К запрошенным 32/48/64/128 добавлены 96 и 192: по модели поведение переламывается между 96 (контакт около 35%) и 160 (около 16%), а 192 даёт верхний край. Прежняя тройка 32/48/64 снята на старом обходе и на 100 тысячах и к этому пункту не относится. Цена обхода считается по циклам Streamline и по `forcerep` (§2.3), потому что `walk 1` на S200 стоит на vsync 16,72 мс и кадр в миллисекундах не различает ячейки.

### 2.5. Отчёт

F5 завершается отчётом о расстоянии до M2 (60 кадров/с, кадр не длиннее 16,7 мс, около 45–58 циклов на частицу в режиме «сила без рендера» на S200; не обязательна). Известная точка: `walk 1`, S200, сила без рендера, около 41 цикла, кадр 16,72 мс на vsync. Циклы режима с рендером на S200 не сняты; расстояние считает отчёт после серии. В отчёт входит сравнение измеренной цены обхода с оценкой §1.1.

## 3. Отвергнутые и отложенные варианты

- **Кернел `Accepted` (отложен).** CPU-оценка не показывает выигрыша по цене при равном поведении (§1.1). **Условие возврата:** захват Streamline на опорной ячейке показывает, что обход упирается в арифметику, а не в чтение слотов (загрузка арифметического конвейера выше конвейера загрузки/сохранения), либо серия F5.3 показывает, что цена `visited-128/192` недопустима при поведении, которое нужно сохранить.
- **Ветвление по `CapMode` внутри `BoidNeighborForceSorted`.** Один uniform-переход в самом горячем цикле может изменить регистры и циклы без правила, поэтому при возврате используется кернел-дубликат (практика F3a, F3b).
- **Считать «принятыми» только вложивших в силу.** Для чужих `align` и `coh` не копятся, счёт зависит от пары команд.
- **Сила через кадр для половины частиц (чётность `id`) и проверка ячейки R/2.** Исключены владельцем: его тесты показали малую эффективность. Журнал этих тестов в репозитории не найден.
- **Потолок как функция плотности.** Усложняет оракул и сравнение серий без доказанной пользы.

## 4. Последствия

- В F5 нет нового правила поведения; значения `maxNeighbors` 96/128/192 используются только в серии и в Play-проверке и по умолчанию не меняются.
- Выбор значения капа для поставки (поведение против цены) решается отдельным ADR после отчёта F5; его вход: Play-отметка владельца и цена обхода.
- Лишний буфер `float3[N]` выделяется только при `forcerep > 1`. `CapHits` остаётся одним `uint`, читатель и сброс не меняются.

## 5. Критерии приёмки

1. F5.0 закрыт (`fd553cb`) с исправлением F5.0b: CSV читается, оценка волны воспроизводима из репозитория.
2. F5.1 (`forcerep`): EditMode зелёный (число до и после); ноль изменённых строк в `walk 0`, `walk 1`, `walk 2`, `HashScatter*`; результат при `forcerep 4` равен результату при 1 точно, и через мир, и прямым вызовом.
3. F5.2: Play принят владельцем отдельно для `maxNeighbors` 128 и 192.
4. F5.3: серия на S10 и отчёт о расстоянии до M2.

## 6. Результат
