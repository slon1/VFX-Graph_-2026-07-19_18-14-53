# План P8: полевая сила соседей вместо обхода

**Статус:** предложено 2026-11-02, пересмотрено 2026-11-03 (вторая редакция: цель 400k при 30 FPS, лёгкий вариант без окна, новая сцена). Решения владельца 2026-11-03 в §8.
**ADR:** [ADR-058](ADR/ADR-058-Field-Neighbor-Force.md).
**Основа:** CPU-модель `DOC/MEASURE/p8-field-model/` (README там же), база замеров F5.3 (`DOC/MEASURE/521a98b-a9d40c4d/F5-report.md`) и замер 3 на 400k (`DOC/MEASURE/ff2a194-331eee0d/20261019-1822/`), цели M1 и M2 из [plan-P7-perf-200k.md](plan-P7-perf-200k.md).
**Роли:** Claude проектирует и ревьюит, Grok исполняет (в том числе захваты Streamline скиллом), Play смотрит владелец.

## 1. Проблема и цель

**Проблема.** Обход соседей в `BoidNeighborForcePass` доминирует в кадре, а его цена растёт с капом почти линейно: на S200 одна точка обхода стоит 6,99 / 18,92 / 28,96 мс при капе 48 / 128 / 192 (около 0,15 мс на слот). В циклах на частицу (режим «сила без рендера», F5.3): кап 48 даёт 41,35 за кадр, из них обход 23,60; кап 192 даёт 126,79, из них 99,90.

**Кап меняет поведение.** В CPU-модели (рецепт `Boids_hash` / `Boids_hash_2teams` с R=3, веса 1,2 / 0,8 / 0,6, чужие ×4) кап 48 даёт контакт между стаями 62% на t=5 против 5,2% без капа: стаи проходят друг сквозь друга. Кап 192 только на separation даёт 29%. **Решение владельца 2026-11-03: кап 192 не показатель, стаи при нём тоже проникали друг в друга.** Принятое в F5.2 визуальное «192 лучше 48» этим не отменяется, но эталоном для P8 служит поведение без капа.

**Цель.** Три правила боидов на полях вместо цикла по соседям. Два условия приёмки:
1. **400 000 частиц, две стаи, не ниже 30 FPS** (в начале прогона; троттлинг и падение частоты GPU пока не учитываются, решение владельца 2026-11-03).
2. **Стаи не проходят друг сквозь друга** (метрики контакта и чужих по зонду модели и по Play). Пересечение, вызванное капом, должно исчезнуть.

**Бюджет 400k при 30 FPS.** 33,3 мс при 700 МГц это около 23,3 млн циклов, то есть **около 58 циклов на частицу на весь кадр**. Рендер около 13,7 (замер 3: разность A−B 7,8 мс на 400k, `walk` 1). Остальной кадр без силы 17,75, из них хэш около 10 (профиль D и F5.3). На полевую силу остаётся **около 27 циклов на частицу**. Сегодняшний обход капа 48 стоит 23,60. Поэтому цель по цене: **не дороже сегодняшнего капа 48, без его пересечения стай**.

База «сегодня» на 400k (замер 3, `Boids_Hash_test400k_2teams`, кап 48, `walk` 1): кадр без рендера 22,3 мс, с рендером 30,1 мс (около 33 FPS). Это сцена мира 729 м, обе команды в одном диске, и **для полевого пути она не годится** (см. §3, сцена P400c). Её числа служат ориентиром, а не базой сравнения.

## 2. Что проверено на модели

Все числа из CPU-модели, 3000 частиц, две команды, R=3, арена 90 м с переносом, 5 seed. Подробности и команды в `DOC/MEASURE/p8-field-model/README.md`. **На GPU ничего не измерено.**

**60 FPS** (шаг 1/60 с), контакт / чужие на t=5, шум курса за шаг на t=5 / t=15:

| Вариант | контакт / чужие, t=5 | шум курса, t=5 / t=15 |
| --- | --- | --- |
| эталон без капа | 5,2% / 0,34% | 0,0054 / 0,0017 |
| кап 48 (как сейчас) | 62–68% / 21–23% | |
| потенциал и градиент, без ближнего поля (режим 7, G=90) | 1,3% / 0,03% | 0,0088 / 0,0046 |
| всё на векторном ядре, без ближнего поля (режим 1) | 0,5% / 0,00% | 0,0131 / 0,0043 |
| поле + точный обход r0=1,5 по хэшу | 1,9% / 0,06% | 0,0067 / 0,0022 |
| потенциал + окно 5×5 из центроидов + цикл по своей ячейке (режим 9) | 1,9% / 0,08% | 0,0075 / 0,0028 |
| давление как основное separation | 2–12% | 0,0136–0,0224 / 0,0075–0,019 |

**30 FPS** (шаг 1/30 с), режим 7 без окна, прогон 2026-11-03 (добавлены переменные `M_FPS`, `M_UPD`):

| Вариант | контакт / чужие t=5 | t=15 | шум курса t=5 / t=15 | число стай (команда 0 / 1) |
| --- | --- | --- | --- | --- |
| эталон без капа | 4,7% / 0,32% | 6,2% / 0,25% | 0,0110 / 0,0071 | 3,6 / 3,6 |
| поле, обновление каждый кадр | 1,0% / 0,02% | 2,6% / 0,12% | 0,0192 / 0,0105 | 4,8 / 4,4 |
| раз в 2 кадра | 0,5% / 0,00% | 1,2% / 0,01% | 0,0229 / 0,0116 | 4,4 / 5,0 |
| раз в 3 кадра | 0,8% / 0,01% | 0,6% / 0,01% | 0,0249 / 0,0151 | 4,4 / 5,2 |

Выводы:
1. Стаи расходятся при любом интервале обновления. **Условие приёмки 2 в модели выполняется без ближнего поля.**
2. Шум курса относительно эталона на том же FPS: 1,75× при обновлении каждый кадр, 2,1× раз в 2, 2,3× раз в 3 (на t=15: 1,5 / 1,6 / 2,1). Порог «шум не больше 2×» выбран исполнителем модели и «живость» не мерит, решает Play. Гипотеза: часть добавки это ступенчатые скачки поля на кадрах обновления, их должна снять интерполяция между двумя версиями поля. **В модели не проверено** (P8.1-0).
3. Alignment и cohesion на поле совпадают с эталоном; separation на гриде с малым капом не работает.
4. Окно из центроидов снижает шум курса до 1,4–1,6× эталона, но стоит чтения порядка 800 Б на частицу (около цены обхода капа 48) и требует мелкой ячейки хэша 0,5 м; в бюджет 400k оно, по оценке, не помещается (§5, P8.1-W).
5. Модель маленькая: 3000 частиц, одна геометрия. Масштаб до 400k проверяется отдельно (P8.1-0).

## 3. Фазы

Каждая фаза заканчивается гейтом. Следующая начинается после слова владельца «принято».

### Сцена P400c (новая)
Существующие сцены 400k (`Boids_hash400k_2teams`, мир 729 м, обе команды в одном диске радиуса 361 м, `simulationSpeed` 2) для поля не годятся: при тексель 1 м (R/t=3) нужно 531 441 тексель против `MaxCells` 65 536, а перемешанные стартовые диски не позволяют показать «стаи не проходят друг сквозь друга». Они остаются неизменными как референс.

P400c это новый пресет и сцена рядом с ними:
- 2 × 200 000, рецепт `Boids_hash`: радиусы 3/3/3, веса 1,2 / 0,8 / 0,6, множитель чужих 4, `cruise` 6, `turn` 4, `particleSize` 0,5;
- **`simulationSpeed` 1** (решение владельца), мир с переносом, **224 м** (50 176 текселей при t=1 м, не больше 256 м);
- два диска навстречу друг другу, как в `Boids_hash_2teams`: центры симметрично на оси X, курсы ±1, плотность спавна в пределах 25–40 на м² (равновесие модели 19–41), расстояние между краями дисков не меньше R·4. Числа фиксирует ADR-059 §2.1: радиус 45 м, центры ±55 м (спавн-плотность около 31 на м²);
- базовые прогоны «сегодня» (кап 48, кап 192, `walk` 1) снимаются на **этой же** сцене и сборке.

## 4. Метрики и определения

- **Основная метрика:** циклы GPU на частицу в кадр, режим «сила без рендера» (Streamline профиль B), как в F5.3 и P7. Остальной кадр (профиль D) 15,7–17,8 циклов на частицу.
- **Цена по стадиям:** дифференцированием по повторам стадии, как `-m3d_forcerep` в F5.1: `-m3d_fieldrep N` и `-m3d_fieldstage build|conv|force|all`. Две точки (1 и 4) на стадию. Стоимость способа сбора поля сравнивать по **полному кадру**, потому что от него зависит наличие хэша.
- **Сравнение только на одной сцене и одной сборке.** Опорные числа F5.3 и замера 3 сняты на мирах 729 м при спавне 0,49–0,98 на м². На P400c плотность на порядок выше, поэтому базу (кап 48, кап 192) пересчитывают на ней же.
- **Точность силы поля** измеряется не метриками стаи, а сравнением с силой полного обхода без капа на одном снимке положений: медианная и p95 ошибка по модулю и по углу, отдельно для внутренности стаи и края.
- **Поведение:** метрики модели (контакт %, чужие %, число стай, поляризация, шум курса за шаг). Определения в README модели. Шум курса сравнивается с эталоном **при том же FPS**. Приёмка по режиму, не побитово.

## 5. Главные риски (подробно в ADR-058 §4)

1. **Цена свёртки по площади.** На 50 176 текселях, 25 тапах и 6 каналах это около 19 чтений на частицу при 400k, то есть большая часть бюджета в 27 циклов. Рычаги: K=2–3, пропуск пустых текселей (стая занимает около 60% мира), префиксные суммы по строкам диска. Мерить в А.
2. **Атомики на Mali-G76 против gather.** Gather читает каждую частицу четыре раза (около 32 МБ на кадр на 400k), скаттер даёт до 12 атомиков на частицу в плотных текселях. Что дешевле, неизвестно: микробенч А. Скаттер не требует хэша.
3. **Устаревание поля.** При K ≥ 2 шум курса растёт до 2,1–2,3× эталона (модель). Самовклад при устаревшем поле сокращается не точно. Интерполяция между версиями поля пока гипотеза.
4. **Площадь мира и плотность.** Равновесная плотность стаи 19–41 на м² задаёт размер мира: 400k занимают около 16 000 м². Мир P400c 224 м даёт запас под пустоту между стаями, но не больше 256 м (`MaxCells`).
5. **Тепловой режим.** Устойчивые 30 FPS при 400k и троттлинге (433 МГц) недостижимы: 14,4 млн циклов на кадр это около 36 на частицу при 400k, рендер и остальной кадр уже дают около 31. Решение владельца: в начале, без троттлинга, игнорировать пока. Запись для P8.3.
6. **«Живость».** Шум курса выше эталона на 40–130% во всех полевых вариантах. Метрики не говорят, дрожание это или живость, решает Play.
7. **Модель маленькая:** две команды, 3000 частиц. Масштаб проверяет P8.1-0.

## 6. Что не входит

- Правка существующих кернелов обхода (`walk 0/1/2`), выбор значения капа, `walk 2`.
- Классический хвост P9 (`TeamClassicSteer`, `AlignFromVelocity`, ADR-054, ADR-057) и точки роя: P8 только для рецепта `Boids_hash` (курс из команды), решение владельца 2026-11-03.
- Давление, Poisson, кольцо сенсоров как основная схема (в P8.4 только как опции).
- Новые разрешения экрана, смена порогов M1 и M2, учёт троттлинга.
- Миры больше 256 м и больше двух команд.
- Изменение существующих пресетов 400k и их сцен.

## 8. Решения владельца

**2026-11-03 (первая редакция):** миры не больше 128 м, две команды достаточно, единый радиус R допустим, раздельные можно ввести позже.

**2026-11-03 (вторая редакция, заменяет первую в части мира и цели):**
1. P8 только для рецепта `Boids_hash` (курс из команды). Классический хвост и `AlignFromVelocity` не входят.
2. Цель: поднять число частиц до 400 000 (вместо 500 000 на первом шаге) при FPS не ниже 30 и убрать взаимное проникновение стай. Кап 192 не показатель: стаи проникали друг в друга.
3. Устойчивые 30 FPS нужны только в начале, троттлинг и падение частоты пока игнорируются.
4. Тест на новой сцене P400c (два диска навстречу, мир 224 м, `simulationSpeed` 1); существующие сцены 400k остаются референсом.
5. Радиусы 9 в `Boids_hash_2teams` откатываются: ассет пересоздаётся штатной фабрикой `Tools/M3D/Create Boids Hash 2 Teams Effect` (R=3/3/3, веса 1,2 / 0,8 / 0,6, по 1500, `simulationSpeed` 1, ячейка 3, поле 30×30).
6. База ветки P8: `feature/reynolds-boids` («ньютоновские» боиды); P8 не опирается на классический хвост P9. Работа на новой ветке `feature/p8-field-neighbors`, ветка `experiment/align-from-velocity` не трогается.
